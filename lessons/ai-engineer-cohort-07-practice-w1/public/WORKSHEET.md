# W1 实践工作单 · CareKind 项目启动

配套实践第一课；具体代码任务需在老师提供的真实 starter 上确认。所有练习数据用 synthetic data；下面的流程是拟议课堂例子。

## 1. Frame · 8 分钟

- 用户 / 角色：
- 具体场景：
- 当前困难（有材料就给来源，没有就标假设）：
- 可观察成功标准：
- 本周范围：
- Non-goals：完整 UI、完整业务 MVP、产品模型调用、真实护理系统写回。

建议用“记录草稿需人工检查并明确确认”的场景讨论责任边界。不得把模型推断当护理事实。

## 2. Specify · 10 分钟

写一页 Product Brief：目标与范围、流程、数据与来源、模块职责、红线与验收、任务清单。

流程至少画出开始、用户动作、系统响应、成功、失败、人工确认点。本周只定义业务流程，代码任务另选一个小改动。

| 条件 Given | 动作 When | 可观察结果 Then | 检查方式 |
|---|---|---|---|
| 一份合成教学草稿 | 进入拟议 review 流程 | 展示待检查状态，不能冒充已确认事实 | W1 spec review；后续实现测试 |
| 内容为空 | 尝试确认 | 显示错误，不进入确认状态 | W1 spec review；后续实现测试 |
| 尚无适当角色的人工确认 | AI 建议直接保存/写回 | 该操作被禁止，保留待 review 状态 | W1 risk review；后续实现测试 |

以上是建议产品契约，不代表 starter 已实现。小改动自己的验收标准必须另写。

## 3. Ground · 10 分钟

Repo Map：只填从实际文件读到的内容。

| 项 | 真实路径 / 命令 | 如何确认 | 未确认项 |
|---|---|---|---|
| 项目入口 | | | |
| 本地启动 | | | |
| 数据 / schema | | | |
| 本次改动位置 | | | |
| 相关测试 | | | |

最少规则：仅 synthetic data；不把密钥放进代码/Prompt/日志；不改变既有 URL/API；不替人确认事实；不清理或回退别人未提交工作。

停止条件：不清楚业务事实；改动超出允许文件/契约；测试或启动前置无法确认。先记录并求助，不能让 Agent 猜过去。

## 4. Build · 17 分钟

从实际 starter 中选择一个可控小修改：优先文档纠错或已存在的简单校验。先检查它确实存在、确实有问题，再决定；不预设虚构路径。

- 任务：
- 允许修改：
- 不允许改变：
- 成功 / 失败验收：
- 对应测试或手工检查：

给 AI 的三段任务说明：

> 先只读当前项目规则、README、入口、schema 与相关测试。输出真实路径的 Repo Map，以及仍未确认的内容。不要改文件，不要输出密钥或真实个人数据。

> 基于已确认的 Brief，提出一个最小改动计划。说明可改文件、保持的契约、成功/失败验收、测试方式和停止条件。计划经我确认后再实现。

> 执行已确认的小改动，保持其他工作。输出 scoped diff、实际运行的检查及结果、未验证内容；不要自行部署、写回真实系统或确认业务事实。

## 5. Evaluate + Safeguard · 12 分钟自查与讲师点评

- Diff 是否只涉及允许范围？
- 是否改变 URL/API、业务含义、数据权限？
- 是否出现真实个人资料或密钥？
- 成功路径和失败路径各有什么证据？
- 检查真的运行了吗？预期 / 实际输出分别是什么？
- 人工 reviewer、结论、未解决问题是什么？

只选：通过 / 未通过 / 未验证。写明理由和证据。测试没跑不等于通过。

## 6. Operate · 10 分钟汇报

提交：Product Brief、Workflow、Acceptance/Test Plan、Repo Map、Rules、Task Board、Scoped Diff、Test Result、Human Review。

| 任务 | Owner | 状态 | 验收证据 | 下一步 |
|---|---|---|---|---|
| | | Todo / Doing / Review / Done | | |

汇报用 60 秒：解决什么、改了哪里、证据是什么、还缺什么。W2 从这份产品契约展开 UI 与 Design System。
