# W2 可复制材料 · CareKind 混合团队

本材料为课堂模板。使用已登录订阅的Codex/Claude Code会话，所有示例为合成数据；不调用付费模型API，不发送员工消息，不写生产。

## 一、给管理Agent的计划任务

读取项目README、PRD、DESIGN.md、现有组件、候选状态契约和当前任务。目标是CareKind记录→送审→确认的模拟UI。
先输出计划草稿：任务ID、成果、Owner、执行者、依赖、允许修改范围、验收动作、证据、Reviewer、停止条件。
不要假设人员能力或任务量；缺少人员信息先补问。找出共享文件与接口冲突，按依赖安排。
确认前不发送任务、不修改代码、不改变业务规则、不部署。

## 二、执行任务Brief

任务：CK-UI-02 / 记录页面。Owner：B；Reviewer：C。
目标：字段校验、保存草稿、送审的模拟UI。
范围：记录页面；共享tokens和组件由A维护，路径从真实仓库读取。
上下文：PRD、DESIGN.md、候选契约、当前组件与README。
完成：空记录有提示；保存后仍Draft；送审进Review；失败保留输入；窄布局和键盘可用。
产出：diff、同尺寸before/after、操作证据、实际检查与未验证项。
升级：共享接口不符、需要修改他人文件、权限不明，带证据报告Owner/集成人。

## 三、任务拆解Skill模板

```markdown
---
name: carekind-task-plan
description: 当需要把已确认的CareKind UI需求拆成多人或多Agent任务计划时使用；输出草稿，不发送或自动执行任务。
---
# 输入
PRD、当前设计系统、候选契约、人员职责/任务量、任务与仓库规则。
缺少信息先补问；不知道的人员或规则写待确认。
# 步骤
1. 提取成果、验收与non-goals。
2. 确认共享接口/组件及Owner；建立依赖。
3. 拆可独立验收的任务，写负责人、执行者、Reviewer与允许范围。
4. 检查重叠写入、未知权限、缺证据与阻塞。
5. 输出任务表、依赖关系、待确认项和建议顺序。
# 输出
ID | 成果 | Owner | 执行者 | 依赖 | 允许范围 | 验收 | 证据 | Reviewer | 状态
# 检查
每项有责任人；依赖无循环；共享文件归属明确；验收可观察。
# 边界
只起草。未经授权不发送、不改人员记录、不改变业务契约、不部署。
```

让Agent帮你在当前项目的Skill目录写入并依据会话实际支持方式调用。模板本身不代表已安装；不同会话的触发入口先核查。
第一次输入完整需求，再删掉一个角色或契约，检查它是否补问。保留结果与修订。

## 四、另外两种Skill方向

- 汇报整理：输入自然语言进展与证据；输出任务ID、完成项、阻塞、依赖、待决策、证据缺口。未有回执不标已接单；未验收不标Done。
- 交付检查：输入任务卡、diff、截图、操作/测试记录；逐项对照验收，输出通过/未通过/未验证、理由、Owner和下一步。AI判断交给人收口。

## 五、冲突消息与交接

给A和集成负责人：CK-UI-02的status=pending与组件要求state=Review不一致。
证据：实际类型位置、输入样例、截图。影响：送审后的状态不可见。
请按当前契约确认版本与修改范围。未裁决先保持本人文件范围。
决定之后：更新共同契约与看板 → 通知B/C → 接入 → 复查 → 回收证据。
若真实Lab未出现冲突，可记录一次组件交接，不制造冲突。

## 六、30分钟Lab

0–5：确认任务、Owner、依赖、共享组件与候选契约。
5–23：A规范/组件；B记录页；C复核与检查。各自让Agent读取当前上下文后执行。
23–30：集成一条UI路径，记录空/错/失败/未保存/保存、角色与窄布局；交给Reviewer。
独立学员依次执行A/B/C任务或使用会话支持的子任务，自己检查全部结果。
实际启动命令从项目README读取。没有项目先建立最小fixture前端，参考课件P37演示，不宣称不存在的starter已就绪。
