## 0. 为什么必须讲这一块

现在的 L13 教学员造出：规则文件 + 裁决表 + 六条检查 + 一条 CI。

**但它没回答一个学员回去第一天就会撞上的问题：**

> 「我建好了。**然后呢？AI 在哪？它凭什么读我这些文件？它能改吗？谁拦着它？**」

不回答，学员造出来的是一个**没有消费者的文档仓库**，
正是这节课开头那四句症状里的第五种死法。

**这一块的定位：不是讲架构美学，是补上"这套东西活着需要的周边"。**

---

## 1. 交底五问（本模块骨架）

```
1  有哪些仓？        拓扑 + 为什么必须分开 + 权限怎么隔离
2  给它什么权限？    读什么 / 写什么 / 谁批准 / 怎么记录
3  接哪些外部系统？  连接器与 MCP，以及为什么它不能定时跑
4  它有哪些技能？    双层结构 + 一个技能的十节规格
5  怎么维护？        检查怎么长大 / 漂移怎么查 / 谁能改规则
```

**五问有顺序，不能打乱：** 先有仓（东西放哪），才谈权限（谁能动），
才谈连接（够不够得着外面），才谈技能（会干什么活），最后谈维护（怎么不烂掉）。

## 2. 第一问 · 有哪些仓

### 2.1 三个仓，职责完全不同

```
┌─────────────────┐   规则仓        稳定的运营定义
│  规则仓          │   写权限：极少数人
│  rules/ people/  │   main：强制 PR + 禁 force push + 管理员也受约束
│  AUTHORITY.md    │   ← 今天你造的就是这个
│  check.mjs  CI   │
└─────────────────┘
         ▲ 读
         │
┌────────┴────────┐   记录        每天的工作状态
│  记录          │   写权限：所有人
│  一人一天一个文件 │   main：不强制 PR（否则不会 git 的人交不了）
│                  │        但禁 force push + 禁删分支（归档不可改写）
└─────────────────┘
         ▲ 读
         │
┌────────┴────────┐   产品仓        真正的业务代码
│  产品仓（N 个）  │   **agent 只读，绝不写**
└─────────────────┘
```

### 2.2 为什么必须是三个而不是一个

| | 规则仓 | 记录 | 产品仓 |
|---|---|---|---|
| 内容变化频率 | 几个月一次 | 每天 | 每天 |
| 改错了多久发现 | 可能几个月 | 当天 | CI 当场 |
| 谁来写 | 少数人 | 所有人，包括不用 git 的 |  工程师 |
| **要不要强制 PR** | **要** | **绝不能要** | 要 |
| agent 能不能写 | 能（有白名单） | 能（有白名单） | **不能** |

**最后两行是分仓的真正理由。** 规则和状态对分支保护的要求**正好相反**，
塞一个仓里必然牺牲一边，而被牺牲的通常是不会 git 的那一半人。

### 2.3 产品仓那条线是最容易被忽略的一条

**agent 读产品仓是对的，也是应该鼓励的。写是绝对禁止的。**

理由不是怕它写坏，是**权限边界要跟责任边界对齐**：
规则仓的规矩管不了产品仓的合并流程，产品仓有自己的审查人和自己的 CI。
一个 agent 同时能写两边，等于把两套互不相干的审查制度短路了。

> **这一格给学员的动作：在指令文件里写死"不许写产品仓"，并列出仓库名。**
> 这是全部权限设计里最便宜、收益最高的一条。

## 3. 第二问 · 给它什么权限

### 3.1 读权限：白名单，而且全是只读命令

工具权限文件（`.claude/settings.json`）里的放行列表，**只放只读检查类命令**：

```
git status / diff / log / show / branch / fetch / rev-list
ls / find / grep / wc / sort / head / tail / jq
你自己那两个脚本（check.mjs / 漂移检查）
```

三条设计原则：

| 原则 | 为什么 |
|---|---|
| **只放不改状态的命令** | `git fetch` 在里面，`git pull` 不在。前者只取，后者会动你的工作区 |
| **共享的进仓库，个人的不进** | 共享白名单提交，个人覆盖放 `settings.local.json` 并 gitignore ,, 🔖 **这条对，但留了个洞：被 gitignore 的那份没有任何人见过。L17 §1.5 补个人层裁决** |
| **白名单不是安全边界，是省事边界** | 它减少确认弹窗，**不阻止任何事**。真正的边界在 §3.2 |

### 3.2 写权限：一条一条开，每一条都要有人具名批准

**这是整个治理方案里最值钱的一格。**

写权限不是一个开关，是**一张明细表**。每一行是一类写操作，每一行都要回答四个问题：

| 问题 | 例 |
|---|---|
| 写到哪 | 邮箱草稿 / 仓库提交 / 工单系统 / 聊天 |
| 谁批准的 | 一个具体的角色，不是"团队同意" |
| **批准立在什么上面** | 一封能重新打开来读的邮件？还是一通电话？ |
| 什么时候可以升级 | 从"每次有人盯着"到"无人值守"，要什么证据 |

**第三行是最关键的，而且它反直觉。**

> 真正起作用的限制，**不在"谁按那个按钮"，在"这项批准立在什么上面"。**
> 后者读者可以核查，按钮不能。

所以写权限表里**允许出现强弱不同的两行，而且要标出来**：

```
行 A  往工单系统写   批准依据：一封邮件，任何人都能重新打开来读
行 B  往聊天发通知   批准依据：一通电话，由提出这个需求的人转述
                     ⚠️ 这是一项批准在仍然算作批准的前提下，最弱的形式
```

**把 B 那行的弱标出来，比把它伪装成跟 A 一样，安全得多。**

> 🔖 **这张表后面被改两次：**
> **L15 §1.3** 把它按「撤不撤得回来」**重排**成不可逆清单；
> **L17 §1.5** 把它从一张变成「**一张共享 + 每人一行差异**」,,
> 因为「谁批准的」写的是角色，而执行的是一个具体的**执行者**，**中间那一跳这张表管不了**。

### 3.3 四条通用禁令（跟批准无关，谁批都不行）

写权限表之外，还要有一组**"不是没批准，是不可批准"**的事：

```
1  不从活跃度、消息长度、在线时长推断投入或产出
2  不给人打分、排名、互相比较
3  不把私人聊天和邮件当成汇报数据
4  不在没有人明确确认的情况下改负责人、日期、优先级、承诺
```

**为什么要单独列出来：** 否则"我问过了、批准了"就能授权它们。
**把它们写成禁令而不是待批项，这句话就用不上了。**

### 3.4 草稿和发送之间那条线

一个具体到可以直接抄的判例：

| 行为 | 判定 | 为什么 |
|---|---|---|
| 在操作者**自己的**邮箱里建一封草稿 | **算起草** | 它没到任何人手里，移动之前可见，不可逆那一步由人执行 |
| 发送 | **禁止** | 不可逆，且到了别人那里 |
| 往仓库提交一个文件 | **不触发通信禁令** | 但它是归档，受另一条留存规则管 |

> 这三行要一起讲。学员最容易犯的错是把第三行当成第二行（不敢让它提交），
> 或者把第一行当成第二行（不敢让它起草）。**两种错都会让这套东西没法用。**

## 4. 第三问 · 接哪些外部系统

### 4.1 连接器清单（按"它为什么需要"排，不按产品名排）

| 它要干的事 | 需要接什么 | 没有会怎样 |
|---|---|---|
| 知道现在有哪些活、谁负责、什么时候到期 | 工单系统 | 它只能看文件，看不见真实进度 |
| 把结果告诉人 | 聊天工具 | 只能写文件，没人会去看 |
| 起草对外沟通 | 邮箱 | 少一类产出，不致命 |
| 看技术交付证据 | 代码托管 | 说不出"做完了没有" |

### 4.2 这一节最重要的一句：交互式登录撑不过定时任务

**这条决定了什么能自动、什么不能。**

```
上面这些连接器，多数是「点一下同意屏」授权的。
这种授权一定会过期。
而定时运行的时候，没有人可以去点那个同意屏。
```

**推论链，要完整讲给学员：**

```
定时跑的技能，需要的是服务凭据，不是交互式连接器
   ↓
没有服务凭据之前，定时跑的结果是，
   令牌过期那天返回一个空结果
   ↓
空结果读起来像「今天没什么可报的」
   ↓
而真实情况是「今天什么都没查」
   ↓
所以：宁可全部由人触发，也不要一个会静默失败的定时任务
```

**代价必须一起说：** 由人触发意味着**技能追不上你**。没人开会话就没人被提醒。
兜底不是加定时器，而是"**下次有人来的时候，告诉他哪个已经结束的周期没有报告**"。

> ⭐ 这一格直接接上第十一节（定时无人值守）。
> **L11 教的是"它不在场怎么做对"，这里给的是"什么情况下根本不该让它不在场"。**

> 💳 **这一格留了一笔债，而且上面已经认了：「技能追不上你」。**
> **这笔债在 L15 还**（`VIBE_CODING_MASTER_L15_BLUEPRINT.md` §0.1 第六条 / §5.4）。
> L15 第四幕的全部内容就是「**凭什么可以开定时任务**」：三道门（该不该开）+ 三道自检（开了在不在跑）。
> ⚠️ **讲 L14 的时候这一格不要讲成"定时任务不能用"**，要讲成"**现在还不能用，条件下节课给**"。

### 4.3 连接失败必须自带修复步骤

每次外部连接失败的输出里必须有三件事，**第三件通常是缺的**：

```
1  哪个连接器挂了，且说明这是认证问题，不是没有数据
2  这次运行没能覆盖什么，「所以本次结论不成立」
3  恢复它的确切一步，不是「检查一下设置」
```

**为什么第三条必须有：** 没有补救办法的报错让读者去猜，
而猜就是"**它现在坏了**"变成"**它一直是坏的**"、然后这个技能就没人用了的过程。

## 5. 第四问 · 它有哪些技能

### 5.1 双层结构，而且这一刀是承重的

| 层 | 放什么 | 回答什么问题 |
|---|---|---|
| **规范层**（`ai-skills/*.md`） | 这条规则为什么存在、什么被禁、谁批的 | **为什么** |
| **执行层**（`.agents/skills/<名>/SKILL.md`） | 做什么、什么顺序、用哪条查询 | **怎么做** |

两层之间用**相对符号链接**连到 agent 会读的目录，**只有一份拷贝，不是两份**。

> **两份拷贝就是"可执行版和它的规范开始互相不认"的开始。**
> Windows 或不支持符号链接的环境：单目录 + 一条"两边必须一致"的检查。
> **注意这是降级，不是等价，它把"单副本"换成了"两副本加一条检查"。**

### 5.2 执行层携带流程，指向规则，绝不复述规则

一个反面教训值得讲：早期版本因为要跑在云端定时任务上（零上下文启动、跟不了指针），
被迫把规则全文抄进技能文件。后来取消了定时任务，**这份重复立刻被删掉**。

> **重复只在被迫的时候出现。前提一消失，就要立刻还债。**

> ⭐ **这段教训是 L15 第四幕第 3 段的全部论证来源**，讲 L14 时可以轻带，但不要删：
> 定时任务读不到你的会话，所以它只有两条路 ,, **抄规则全文（两份，必然漂移）**
> 或者 **第一步去拉那个远端（一份）**。
> **后者唯一成立的前提，就是 L13 造的那个你改不了的远端。**

### 5.3 一个技能必须定义的十节（可直接当 checklist）

```
1  trigger              什么时候触发
2  数据来源             它读什么
3  必需输入             缺了就不能跑的东西
4  输出结构             产物长什么样
5  人类审批人           具名，不是"团队"
6  允许的写操作         白名单，表外的一律禁止
7  失败与重试           几次、多久、失败了报什么
8  审计记录             这次跑了什么，留在哪
9  隐私边界             明确不碰什么
10 验收测试             可当场验证的断言
```

**第 10 条最容易被跳过，也最值钱。** 好的验收测试长这样：

```
删掉缓存 → 重新问一次，而且不报错
调用者的名字跟花名册里的近似匹配 → 仍然问，不推断
查询连续失败 → 报 FAILED，绝不报 0
后面几页拉取失败 → 报「不完整」，不报成功
```

### 5.4 结果必须有四种状态，不能只有"有/没有"

| 状态 | 含义 | 必须报成 |
|---|---|---|
| `ok` | 成功，找到 n 条 | n |
| `zero` | 成功，确实是空 | **0（真零）** |
| `partial` | 成功但不完整 | n，**标注不完整** |
| `failed` | 重试后仍失败 | **FAILED，绝不报 0** |

**规则：分支判断看错误，不看结果集长度。** 工具报错和空结果是两件事。

> **静默的空结果是这类系统的头号杀手：**
> 连接过期 → 查询返回空 → 报告显示"本期无异常" → 所有人以为一切正常。

### 5.5 技能的组合方向是反的，这一格容易想错

多数技能**消费**记录（读工单、生成报告）。但会有一个技能**生产**记录（帮人起草每日更新）。

**生产型技能放在它输出落地的那个仓库里**，不放在规范仓，
它是可执行的，而且它在输出落地的地方运行。

**但规范仓的写操作总表里仍然要列它。** 因为指令文件声称"所有被允许的写都在这张表里"，
**一个只在代码所在地登记的写操作，就是一个没人找得到其批准门禁的写操作。**

## 6. 第五问 · 怎么维护

### 6.1 检查是长出来的，不是设计出来的

**三条规矩，第一条最重要：**

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **新检查从真发生过的错来，不从想象来** | 凭想象加的是噪音，两周后被注释掉；从事故反推的每一条都有人愿意维护 |
| 2 | **硬失败和提示必须分开** | 全设成失败 = 天天红 = 没人再看 |
| 3 | **改流程 = 同一次改动里同时改检查** | 一处更新另一处没更新的规则，比没更新的规则更糟，因为没人分得清哪个是当前的 |

### 6.2 三层自动化，各管各的

```
每次会话   会话启动钩子        只报告这份检出落后多少，永不自动拉取，永远退出 0
                               ⚠️ 一个会阻塞会话的新鲜度警告，比它警告的陈旧本身更糟

每次 PR    一致性检查          绿了才能合。顺便把缺口总数贴在 PR 摘要上
                               ⚠️ 这一层是唯一真正的硬政策

每周一次   权限漂移检查        比对实际权限和规则里写的权限
                               ⚠️ 这一层必须用服务凭据，不能用交互式连接器（§4.2）
```

> **注意中间那层和两边的差别：** 钩子是提醒，漂移是巡检，
> **只有中间那层能让一个改动进不来。**

### 6.3 漂移检查为什么"只数数、不点名"，以及它为什么反而更强

因为个人账号映射属于身份目录、不进规则仓，漂移检查**不能按人查**。
限制反而逼出了更强的检查形态：

```
一个不是组织成员的协作者   ← 不需要任何人知道那是谁，就能抓到一条离职残留
在职人数 == 账号数         ← 不一致就报，谁缺账号让人去查
规则仓可推送人数 == N      ← 多一个就是漂移
记录 main 有保护         ← 存在即是漂移（它故意不该有）
外部协作者数 == 0
久未接受的邀请             ← 未接受的邀请不携带账号，人仍然拿不到权限
```

> 🔖 **L17 §1.6 在这条上加一层**：它看得见**账号**，看不见那个账号背后是**人、人的 agent、还是一个定时任务**。
> 离职清单五类里，这条只覆盖得了第 1 类。

**更重要的是写清楚它看不见什么：**

> 身份提供商与单点登录、邮件组、共享盘、日历系列、共享凭据。
> **高风险的残留恰恰在那里，不在这里。** 那几类需要人走一遍清单。

### 6.4 谁能改规则，以及提案路径为什么不走 PR

| | 选择 | 理由 |
|---|---|---|
| 谁能写规则仓 | 极少数人 | 规则要慢、要审、要可回溯 |
| **提案怎么提** | **不走 PR，走一次会** | **被规则约束的人不都是 git 用户。用 PR 门槛过滤提案，等于按工具而不是按价值过滤** |
| 代价 | 规则演进吞吐量绑在那次会上 | **必须承认，不要假装没有** |

**判断依据（给学员带走的，不是结论）：**

```
你的规则使用者里，不用 git 的占比是多少？
> 一半   → 提案路径必须离开 git
< 两成   → PR 提案可以接受，但要留一条非 git 的兜底
```

### 6.5 谁来合并：人工审批往往是失效模式，不是保障

**这一格反直觉，但论证很硬，值得完整讲：**

```
1  那个按钮从来就不是控制点
   如果本来就不要求审批人、也没有自动检查，
   一次为了等人而扣住的合并，增加的是延迟，不是审查

2  它不是一次审查
   没有人真的在读这些改动。
   一个被执行、却从不被真正行使的步骤，
   会训练所有人把它当成形式，这比没有它更糟

3  被扣住的合并会让仓库说谎
   一个改动挂了三天，那三天里文件写着「只起草，不发送」，
   而实际上它已经在按一份已经合并的授权发送了。
   那次延迟什么也没阻止，它生产了一份有据可查的自相矛盾
```

**结论：把关口放在"检查绿不绿"上，不要放在"谁点了合并"上。**
检查是可核查的，按钮不是。

### 6.6 诚实是一种维护手段

```
缺口不许用合理的猜测去填
CI 每次把缺口总数贴在改动摘要上，后面跟一句「这是故意的」
文件状态标成「生效」之前，不许残留任何缺口
```

**第三条是这套东西唯一一个会堵住人的地方，也是它真正的产出所在。**
