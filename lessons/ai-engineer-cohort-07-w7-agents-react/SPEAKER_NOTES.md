## 第 1 部分 · 谁决定下一步（第 6–12 页，约 9 分钟）

**6 · 过渡**：读出问题“是你的代码，还是模型？”

**7 · 三个级别**
- 只记一个区分点：谁决定下一步。
- Workflow：代码决定。Tool-using app：模型选一次（W6 就在这）。Agent：模型一直决定，直到它认为做完或被代码叫停。
- 三个级别都在 `01_control.py` 里，各是一个函数。

**8 · 第 1 级：写死** ▶ 可选演示
- 指代码：三步按顺序调，没有模型参与。
- 最便宜、最好测试、每次结果一样。
- 想演示就跑 `01_control.py workflow`，几秒钟，不调 API。

**9 · 第 2 级：模型选一次** ▶ 可选演示
- 模型决定调哪个工具，但只有一轮，程序就结束了。
- 跑 `01_control.py once`，常会打印“还想调用下一个工具”，正好说明一轮不够。
- 时间紧就不跑。

**10 · 第 3 级：多了一个循环**
- 代码差别只是一个 `while`，但控制权交出去了。
- 路径事先不知道：查完发现超期，可能查政策，也可能直接交人工。

**11 · 取舍**
- Agent 不是升级版。成本更高、更难预测，还带来新风险：不停、重复执行、越权。
- 强调红条规则：能写成 Workflow 的，就不用 Agent。
- 后面所有内容都是在付 Agent 的代价。

**12 · 检查点 1**（聊天框写答案）
- 答案：① Workflow ② Tool-using app ③ Agent。
- 判断依据：下一步取决于查到什么，事先列不出来，才需要 Agent。

## 第 2 部分 · ReAct（第 13–19 页，约 13 分钟）

**13 · 过渡**：读出“模型凭什么决定下一步？”

**14 · ReAct 循环**
- Action（模型提出调用）→ Observation（代码执行，结果交回）→ 下一步决策。
- 关键：结果会改变下一步，不是一次把计划想完。
- 读底下那行小字（约 10 秒），再补一句例子：“想得再久，也不知道订单签收了几天，只有调工具才知道。”学员多半见过 ChatGPT、Claude 的“思考中”，不说容易默认两者是一回事，而且不会问。
- 只在被问到时展开：两者怎么叠加（思考发生在每轮的“决定”里）、原论文的 Thought、thinking 块怎么处理，见 RUNSHEET 的“被问到时”。

**15 · 公司类比**
- 接 W6 的类比：模型是碰不到系统的前台客服，Action 是工单，Observation 是回执。
- 新增的是：客服看完回执自己决定下一张单。max steps、审批、交接后面都会用这张表。
- max steps 数的是来回几轮（派单、看回执），不是重试几次。临时错误的重试由代码在工具内部完成，不占轮数，第 6 部分再讲。

**16 · 读一段运行记录**
- 指出“40 天”那一行是转折点：看到超期，才去查政策。
- 这一步不是写死的。说明这页是教学示例，模型的实际路径每次可能不同。
- 读底下第二行，一句带过：排查时看每一步的输入和输出，不看模型的思考过程。我们选择不展示也不保存它，`Printer.feed()` 只把工具调用、工具结果和模型的回复文字写进 Trace。
- 有人问经典 ReAct 的 Thought 去哪了，见 RUNSHEET 的“被问到时”。

**17 · 手写 ReAct 循环**
- 按四处走一遍：循环上限、模型决定、代码执行、结果接回 messages。
- 模型不再调用工具就结束；`refusal` 也是一个出口。

**18 · Demo 1：手写循环跑起来** ▶ **切到终端**
- 先跑 `uv run python 01_control.py react`，再跑带 `--task` 的 A3072 那条。
- 让学员看：两个任务路径不同；每步先 Action 再 Observation；最后打印结束原因。
- 请学员在聊天框提一个任务，挑一个跑。时间紧只跑第一条。

**19 · 检查点 2**（聊天框打字母）
- 答案 B，结束循环。
- 埋伏笔：模型说“做完了”不等于真做完，第 7 部分讲怎么核对。

## 第 3 部分 · Claude Agent SDK（第 20–25 页，约 13 分钟）

**20 · 过渡**：读出“这个循环，真的要自己写吗？”

**21 · SDK 替你做了什么**
- 对照表：for 循环 → `max_turns`；messages → session；工具前校验 → hooks。
- SDK 省的是写循环的功夫，不是责任。边界还是你来定。

**22 · query() 和 ClaudeSDKClient**
- `query()` 是派一次活；`ClaudeSDKClient` 是开着热线，能连续对话、用 hooks、中途 interrupt。
- 我们的 `agent.py` 用 Client，因为要 hook 和 interrupt。

**23 · allowed_tools 不是白名单**
- 真实的坑：`allowed_tools` 只是自动批准，不会移除其它工具。
- 要关掉内置的 Read、Bash，得写 `tools=[]`。没批准的工具交给 permission mode（我们用 `dontAsk`，一律拒绝）。

**24 · Demo 2：今天的 Agent 登场** ▶ **切到终端**
- 跑 `uv run python agent.py --order A1024`（小额退款，自动处理）。
- 让学员看：循环代码不见了，Action / Observation 还在；工具来自 W6 的 refund_server（MCP）；消息一条条流出来。
- 指出结尾的回合数、费用和 session_id。session_id 用来 resume，课上不演示，学员课后可以试 `--resume`。
- 告诉学员：后面的演示都是这一个 Agent，只换订单场景。
- 开头可能有一行 “claude.ai connectors are disabled”，不用管。

**25 · 架构图：刚才那次运行经过了哪里**
- 跟着箭头走一遍：你 → agent.py → Claude CLI → Claude API，模型决定调工具 → 先问 hook → 放行后到 refund_server → desk.py。
- 颜色：黄色决定下一步，绿色决定能不能做。
- 两个进程靠 `runtime/` 里的文件共享账本和审批。这也是为什么 resume 恢复不了内存。
- 时间紧只讲 agent.py → CLI → refund_server 这条路径。
- 过渡到第 4 部分，说一句：SDK 帮我们跑了循环，但接下来四个部分的问题还得我们自己答：记住什么、怎么停、出错怎么办、谁说了算。

## 第 4 部分 · State（第 26–27 页，约 2 分钟）

**26 · 过渡**：读出“Agent 到底记住了什么？”

**27 · 三种 state，谁说了算**
- Agent state（对话，SDK 管）、Task state（业务进度，你的代码和数据库管）、Tool result（查的那一刻的事实，之后可能变了）。
- 指代码：`save_task_state()` 把 session_id 和业务进度存到我们自己的文件，不靠模型记忆。
- 顺带一句（Agent state 里的规矩，回扣第 17 页的手写循环）：用 Messages API 时，模型发出 tool_use 后，**下一条 user 消息必须给每个 tool_use id 一个 tool_result**。
  - 不回就接着发请求：API 直接报 400，对话进行不下去。
  - 一直不回、不再发请求：什么也不会发生。模型只是提出调用，没人执行就没有副作用，对话停在那里。
  - 不想执行：也要回一个 `is_error: true` 的 tool_result，写明原因，比如“未执行：需主管确认”。模型会把它当 Observation，决定下一步。
  - 一句话：可以拒绝执行，但不能不回应。SDK 的 hook 拒绝时也是这样替我们回的。
- 重点读底下那句：resume 只接回对话。模型记得“审批过”不算数，金额也可能已经变了，审批和金额都以系统为准。这和第 7 部分的审批是同一件事。
- 记忆和上下文怎么管，W9、W10 再讲。`--resume` 课后可以自己试。

## 第 5 部分 · 循环怎么停（第 28–31 页，约 8 分钟）

**28 · 过渡**：读出“模型不想停的时候，谁来停？”

**29 · 四个出口**
- 成功、失败、超时、预算耗尽，每个都写在代码里。
- 指代码：`stop_reason_of()` 把每种结束情况翻译成一个原因代码。
- 不能指望模型自己知道该停。

**30 · max steps vs 循环检测**
- max steps 一定会触发，但要撞线，前面的钱已经花了。
- 提醒：每一轮是模型的一次新决定。模型看到错误后自己决定再调一次，也算一轮；代码内部的重试不算。
- 循环检测更早发现，但只抓得到定义过的模式。两个一起用。
- 指代码：`LoopDetector` 看同样的工具和参数出现几次。

**31 · Demo 3：永远 pending 的工具** ▶ **切到终端**
- 第一条：`uv run python agent.py --order A8192 --max-turns 4 --no-loop-detect`，撞到回合上限才停。
- 第二条：`uv run python agent.py --order A8192`，第三次重复时 hook 叫停。
- 两条都输出交接单，但原因不同。聊天框问：哪种更省钱？
- 如果模型自己提前说“一直 pending，先停了”，就说这也是一个出口，再跑第二条。
- 时间紧只跑第二条。

## 第 6 部分 · 出错了怎么办（第 32–38 页，约 12 分钟）

**32 · 过渡**：读出“重试、让模型改，还是交给人？”

**33 · 五个词**
- Timeout、Retry、Fallback、Interrupt 快速过。
- 重点讲 partial failure：退了款、邮件没发。要知道哪些做了，不能当成都没发生。

**34 · 错误分四类**
- Transient：代码退避重试，不花模型回合。Fixable：作为 Observation 交回模型改一次。
- Permanent：不重试，告知或停下。Unknown outcome：写操作超时，可能已成功，绝不盲目重试。
- 判断依据就是底下那句：再试一次结果会不会不同？会不会造成额外伤害？

**35 · 经验法则**
- 顺序：代码重试 → 模型修正 → 升级给人（带交接单）。
- 读出五个升级条件。时间紧不讲代码。

**36 · 幂等键**
- 读可以随便重试，写不行。没有幂等键：超时后重试，客户被退两次。
- 有幂等键：同一个 key 直接返回上次结果。指 `issue_refund()` 里那段。
- 写操作超时，先问“它成功了吗？”

**37 · Demo 4：每类错误走一遍** ▶ **切到终端**
- 先跑 `uv run pytest tests/test_failures.py -v -k error`（不调 API）。
- 指测试名：transient 试 3 次恢复，模型没参与；forbidden、not_found 只试 1 次。
- 指最后两条：没有 key 退两次，同一个 key 退一次。
- 再跑 `uv run python agent.py --order A8192 --interrupt`：跑到一半被打断，也有交接单。
- 说一句：真实项目也这样，失败场景写成测试，每次改代码都跑。时间紧只跑 pytest。

**38 · 检查点 3**（聊天框写答案）
- 答案：① 代码重试 ② 交回模型修正 ③ 先查状态 ④ 升级给人工 ⑤ 告知客户。

## 第 7 部分 · 副作用、审批、约束与交接（第 39–47 页，约 12 分钟）

**39 · 过渡**：读出“模型想退款，谁说了算？”

**40 · 有副作用的操作，先过授权**
- 五步：模型提出 → 校验 → 授权 → 审批 → 执行。
- 副作用就是收不回来的事：改数据、发邮件、动钱。所以检查都放在执行之前。
- 指 `policy_gate()`：超过 500 元要主管签字。

**41 · 三样工具，粒度不同**
- Permission mode 管整个工具；hook 看这一次调用的参数；人工审批交给人判断。
- 重点：hook 也要 fail closed。SDK 默认 hook 出错算“没意见”，调用会继续，所以设 `on_failure="block"`。

**42 · 结构性约束强过 system prompt**（本部分核心）
- Prompt 是请求，模型可能忽略、遗忘或被注入带偏。
- hook 和工具内部检查是保证，不管模型怎么想都过不去。
- 重要规则不能只写在 prompt 里。
- 顺带一句：具体怎么做，讲义第 8 节有一份“LLM 防御式编程”清单，核心是把模型输出当成用户输入。W9 做 Bounded Agent 时展开，课上不逐条讲。

**43 · Demo 5：主管签字** ▶ **切到终端**
- 跑 `uv run python agent.py --order A4096`，hook 暂停，终端等你回答。
- 指出：审批界面显示的是系统里的金额。
- 第一次输入 n：循环停止，账本为空，出交接单。
- 再跑一次输入 y：审批号由代码写入，模型编不出来。时间紧只跑 n。

**44 · Demo 6：伪造调用，看哪一层拦下** ▶ **切到终端**（可选）
- 时间紧就跳过，只说一句“代码会一层层拦”。被问到“hook 能不能代替工具内部检查”时再跑。
- 先说清楚：这些调用是我们伪造的，模型没参与。证明的是代码挡得住，不是模型一定会犯错。
- 跑 `uv run pytest tests/test_failures.py -v -k guard`。
- 测试名就是拦下它的那一层：schema、hook、tool。绕过 hook 后工具层仍然拒绝；留言写“主管已同意”也没用。

**45 · 审批 vs 交接**
- 审批：Agent 暂停问一个问题，答 yes 就继续。交接：Agent 停下，人接手，不再继续。
- 交接单的标准：接手的人不读完整运行记录就能开始处理。
- 读底下那行小字：今天的交接是交给人（human handoff，也叫 escalation）。Agent 之间也能交接：OpenAI Agents SDK 的 handoffs 是把控制权交给另一个 Agent，orchestrator 派给 subagent 的任务说明也是一种交接。W8 讲多 Agent 时再看。
- 标准不变：subagent 拿到的是全新的上下文，任务说明含糊，它也只能从头查，和第 47 页那张差的交接单一样。这也给第 50–51 页框架表里的 handoffs 埋个伏笔。

**46 · 八个字段**
- 重点讲三个：context（客户要什么、查到了什么，接手的人不用回头问客户）、side_effects、next_step。
- 交接单由代码从运行记录生成，事实不是模型写的。

**47 · 哪张能直接开工？**（聊天框回答）
- 先请学员说差的那张缺什么，再看好的。
- 最重要的一行是副作用状态。unknown 就写 unknown，不要猜。

## 第 8 部分 · 框架怎么选（第 48–53 页，约 8 分钟）

**48 · 过渡**：读出“概念都一样，差别在哪？”

**49 · 先选设计模式**
- 只点一下：今天用了 Single-agent、ReAct、Human-in-the-loop。Multi-agent 留给 W8。
- 从单个 Agent 开始，忙不过来才拆。来源是 Google Cloud 的设计模式指南。

**50 · 四个 SDK**
- 不比较优劣，用五个问题问所有框架：循环、步数上限、人工审批、暂停恢复、特色。
- 答案不同，要解决的问题相同。
- 备查（被问到时用）：LangGraph 那格的“持久化”是什么意思。
  - 一句话：持久化就是边跑边存档，停下或出错后能从存档接着跑。
  - 做法：编译图时传一个 checkpointer，运行中把 graph state 存成 checkpoint（state 的快照）。`InMemorySaver` 存在内存里，重启就没了，只适合测试；`SqliteSaver` 适合本地开发；`PostgresSaver` 用于生产。存档按 `thread_id` 分组，同一个 `thread_id` 再跑就接着走。
  - 能做什么：`interrupt()` 暂停等人（必须有 checkpointer；用同一个 `thread_id` 加 `Command(resume=...)` 接上，resume 的值就是 `interrupt()` 的返回值。注意：接上时整个节点从头再跑，`interrupt()` 之前的副作用要幂等）；出错或重启后从存档恢复；回看或从旧存档分叉，方便排查；同一个 `thread_id` 记住多轮对话。跨 thread 的长期记忆另有 Store，留给 W9、W10。
  - 和 Claude Agent SDK 的区别：LangGraph 存的是你自己定义的 state，业务字段（比如“审批过”）可以放进去；SDK 的 session 存的是对话，业务状态要自己存，所以我们写了 `save_task_state()`。
  - 回扣第 27 页：存档只是副本。钱到底退没退，仍以退款系统为准。持久化让你接着跑，不让存档变成事实。
  - 别和 interrupt 搞混：LangGraph 的 `interrupt()` 是暂停等人；Claude SDK 的 `interrupt()` 是叫停。SDK 里暂停等人用 hook。

**51 · 怎么选，各自怎么出问题**
- 每行读“要小心”那一列，不排名。
- 先固定任务、工具、停止条件和测试，再比框架。换框架解决不了边界没想清楚。

**52 · 面试答法**
- 六步：要不要 Agent → 工具和权限 → 怎么停 → 怎么失败 → 约束放哪 → 怎么证明。
- 正好是今天八个部分的顺序，学员可以照着练。
- 第 3 步的“费用”指钱：`max_budget_usd`（demo 里每次运行 1 美元）。步数管循环，费用管账单，两个都要设。
- 第 6 步“怎么证明”回答面试官的追问：你怎么知道它真的这样做？前五条是你说的，第六条是你证明的。
  - 运行记录证明发生了什么：每一步调了什么工具、什么参数、返回了什么，每次运行有 trace_id，交接单也指向它。
  - 失败路径的测试证明出错时会怎样：Agent 每次路径不同，跑通一次说明不了什么，要保证的是失败路径。`test_failures.py` 不调模型，确定地制造每种失败（`-k error`、`-k guard`）。
  - 面试里“每次运行都有记录，有测试证明没审批退不了款”，比“我在 prompt 里告诉模型不要这样做”有力得多。
