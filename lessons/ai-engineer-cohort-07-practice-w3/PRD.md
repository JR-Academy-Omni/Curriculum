P04：不是养老专家，也能把需求做对 · 先承认不知道，再用可核查的来源补上；Claude 帮整理，不替代专家。

P07：本周只做这一条：从一位老人到一次确认 · vertical slice：从界面一路打通到数据库的一条完整流程，而不是每层各做一点。
P08：三个端，共用一套 API 和数据库 · 架构图：护理端（护士、护理员，手机）、养老院管理端（院管理员、主管审核）、平台端 Super Admin，家属端虚线待做；经同一 API 的身份→角色→养老院→状态检查，写入带 facilityId 的数据库；启动密钥来自环境变量加 KMS。
P09：按功能拆开：API 里有哪些模块 · 详细架构：认证与账号、养老院与员工、老人与排班、护理记录、审计、配置与密钥（本周）；录音与转写（W4 起）、AI 模型路由（W12 起）虚线；底层数据库、KMS、对象存储、任务队列、外部 AI 供应商。
P10：AI 部分怎么接进来：Agent、RAG、记忆 · Agent Harness（W11）包住有边界的 CareKind Agent（W9），工具为 RAG（W7）、长期记忆（W10）、业务工具、语音转写（W4）；模型调用经模型路由（W12）到外部供应商；右侧评估流水线（W6）；AI 输出回到 Draft → Review → Confirm。均依据 outline.json C7P04/C7P07/C7P10/C7P11/C7P12。
P11：为什么要 Super Admin，它能做什么 · 左：为什么需要、没有它会怎样；右：开通/停用养老院、创建院管理员、角色和权限模板、配置与密钥、审计查询、受控排障。
P12：每个架构决策，都写清为什么 · 决策 → 理由 → 本周怎么验收。
P13：一条业务链，用一个例子走一遍 · 从老人档案到审核确认共 7 步：每一步是什么、谁来做、留下什么。
P14：先核查项目的起步代码（starter） · starter：已经搭好登录、数据库、API、路由和测试框架的起步代码，先看清它有什么。
P15：key 在哪台机器上，决定谁能改线上 · 本机的 Claude Code 能读到 .env：.env 里是哪套 key，它就能改哪套环境。
P16：CI/CD：代码从你的电脑到线上的流水线 · CI 与 CD 定义；CI 泳道：本机写代码 → push/PR → 自动检查 → Code Review → 合并 main；CD 泳道：部署测试环境 → 验收 → 人工审批 → 发布线上 → 线上验证与回滚；失败分支；为什么要、key 放哪、和 Claude 的关系。
P17：一条 workflow 是怎么跑的 · GitHub Actions 示例流程图：触发 → 并行检查任务（类型检查、单元测试、E2E、构建）→ 部署测试环境 → 人工审批 → 部署线上；失败分支；yml 示意与 workflow、on、job、needs、environment 关键字说明。
P18：先让 Claude 出计划，你看过再动代码 · 在 Claude Code 里先用计划模式：只读代码、写计划，不改文件。
P19：记录一条活动，要挂对老人、班次和任务 · 同一条活动，必须知道是给谁做的、哪个班、哪项任务。
