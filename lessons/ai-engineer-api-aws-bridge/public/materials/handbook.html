技术栈与运行位置

HTML、CSS 与 JavaScript

HTML 定义标题、段落、输入框等结构；CSS 控制布局、字体和颜色；JavaScript 负责响应事件、调用 API 和更新页面。浏览器取得资源后解析和执行它们，形成用户看到的页面。不是所有页面都需要 React。

React、组件与状态

React 是构建 UI 的 JavaScript 库。组件把页面组织成记录列表、表单、按钮等可组合部分；输入和返回结果可以保存在状态中，状态变化后更新对应 UI。这里讲浏览器交互主线，React 也有服务端渲染能力；Next.js 等框架可能同时包含客户端与服务端代码，应看实际执行位置。

JavaScript 与 Node.js

JavaScript 是语言；浏览器和 Node.js 是不同的执行环境。浏览器提供页面与 DOM 等能力，Node.js 让 JavaScript 在浏览器之外运行，可用于 HTTP 服务、脚本和开发工具。二者可使用同一种语言，但运行位置、API 与权限不同。

后端框架与宿主

Express、NestJS 等框架帮助组织 Node.js 应用的路由、校验与业务处理。Node.js 是运行时；操作系统、容器或云计算承载运行中的进程。后端也可以选 Python、Java 等语言和相应框架，不必为了这节课改栈。

页面加载与业务请求

首次加载时，浏览器向资源服务取得 HTML、CSS 与 JavaScript。页面开始交互后，保存按钮可以发送 POST API 请求，再根据 JSON 响应更新 UI。两类请求都可在 Network 中观察。SSR、首屏取数与框架路由可能调整组织方式，仍应按请求目标和执行位置判断。

开发工具、构建与生产执行

Vite 等工具在开发阶段提供资源转换与更新，构建阶段生成生产资源。Node.js 可用于运行这类工具；客户端 JavaScript 在生产中由浏览器执行。Node.js 同样可以独立运行后端服务。构建成功、启动开发服务和运行生产业务是不同的事情。

Web Server、Nginx 与 Node HTTP 服务

服务器或容器承载进程。Nginx 是一个 HTTP 服务进程；Node.js 应用是另一个进程。浏览器请求静态资源时，Nginx 可以直接返回文件；请求 /api/ 时，它可以转发到 Node 应用监听的端口，再将响应送回浏览器。Node HTTP 应用也可不经过 Nginx 直接接收请求。

Web Server 可以指提供 HTTP 响应的软件。Nginx 可直接返回静态文件，或把 /api/ 请求反向代理给单独的 Node.js 应用进程。Node.js 自身也可以提供 HTTP 服务，所以 Nginx 并非每个项目都必须具备的一层。不要把 Node.js 理解成运行在 Nginx 内部的脚本插件。

1. 先看成果，再拆系统

打开护理记录实操，列表中已经有完整的晨间记录。详情包含对象、活动、时间、观察、处理和后续事项。填写一条新记录并保存，再刷新打开。这个结果需要页面、接口、后端处理和持久化协作完成。页面漂亮或出现成功提示，都不能独立证明流程完整。

2. 应用结构与运行位置

浏览器负责收集输入和展示状态；后端验证身份、权限与输入，再执行业务规则；数据库保存记录；对象存储保存文件；外部 AI 服务是后端可能调用的依赖。代码放在同一个仓库不代表都在浏览器运行。SSR 页面生成也需要服务端环境。

3. 访问地址与网络

URL 包含 scheme、host、port、path 与 query。localhost 指向当前发起访问的机器或运行环境。浏览器、容器和远端服务器看到的 localhost 可能不同。DNS 把名称解析为可访问目标的信息；端口定位目标上的服务。HTTPS 还需要有效证书和握手，域名能解析不等于服务可达。

4. API Contract

对接前先确认动作、路径、输入、身份、成功结果与失败结构。路径、字段和状态码由实际实现决定。path 通常定位资源，query 用于筛选或分页，body 提交内容，headers 携带格式和身份等附加信息。JSON 字段名称、字符串与数字、缺失和 null 的区别都可能影响校验。不要把凭据放进 URL。

5. 从状态码到业务结果

本课 POST 成功返回 201 和新记录；400 表示字段不符合约定；401 表示没有有效会话；403 表示当前身份没有写入权限；404 表示资源或路径未找到。429 与 5xx 需要结合服务与重试约定判断。其他项目可能使用 200 加业务 code 表达失败，因此必须同时看响应正文和实际结果。

6. 身份、业务权限与云权限

用户 token 或 cookie 用于识别应用中的身份；editor/viewer 控制是否能写记录；IAM role 是运行服务访问 AWS 资源的身份。三者不同。前端隐藏按钮只是交互，后端仍需校验权限。不要把 provider API key 或数据库密码当成用户登录凭证。

7. 用 Network 观察

在开发者工具选择 Network，清空列表，保留 Fetch/XHR，然后只执行一次保存。找到 POST /api/notes，读取 Headers、Payload、Response 与状态码，记录 X-Request-ID。若页面未发请求，优先看事件与前端错误；若请求存在，先判断到达哪一层，再决定改哪里。分享证据前移除 cookie、token 与个人信息。

8. 接口独立验证

打开实操里的 API request panel，发送 GET /api/notes，再发送正文合规的 POST。复制响应中的 id，通过详情 API 重新读取。接口面板会走真实 HTTP；业务表单与独立请求工具是两个入口。命令行工具不受浏览器相同的 CORS 读取约束，因此工具成功不能替代浏览器验证。

9. CORS 与网络错误

Origin 由协议、主机与端口共同决定。部分跨域请求会先发 OPTIONS 预检，浏览器检查服务端允许的来源、方法和 headers。CORS 控制浏览器对跨域响应的读取，不是 API 鉴权。某些请求已被服务端处理，但浏览器不能读取结果。不要盲目重试写入，也不要将允许所有来源作为默认修复。

10. 持久化与文件

页面状态可能仅存在内存；localStorage 属于浏览器；数据库是后端持久数据来源。保存后应通过 GET、刷新和详情验证读取。后端容器内的文件不应默认当成长期存储。数据库通常保存对象关系和文件引用，S3 保存文件对象；两者需要各自的访问控制、备份与生命周期策略。

11. 配置与环境

同一份代码可能连接开发、测试或生产环境。API base URL、数据库地址和日志位置先对照环境确认。进入前端构建产物的变量可被用户查看，不能用于保密。服务端凭据由运行环境或秘密管理服务提供；构建期和运行期配置的生效方式不同，修改后是否需重新构建或重启应查框架实际行为。

12. AWS：先找到资源

先核对 AWS account 和 region，再看资源标识。AZ 是区域内隔离的位置；某些服务是全局性质，不能一概按区域查找。Region 选择要考虑延迟、数据要求和服务可用性。课堂只读懂拓扑与诊断材料；资源创建属于另一项实践。

13. AWS：请求与计算

主线后端架构为 ALB → ECS/Fargate → RDS。ALB 接收并按规则转发 HTTP/HTTPS，target group 健康检查帮助判断目标是否可接收流量。ECS 编排容器，Fargate 提供运行计算。EC2 提供虚拟机控制；Lambda 适合事件驱动函数，需核对运行限制。API Gateway 是另一类 API 入口能力，不能仅因名称含 API 就强制添加。

14. AWS：网络与前端托管

VPC 划定网络；子网与路由决定流量路径；Security Group 控制允许的来源与端口。主线公网 ALB 转发到私网 task，再访问私网数据库。把数据库端口开放给全网不是常规修复。私网后端访问公网模型 API 还需要合适出口。静态前端可用 S3+CloudFront；SSR 前端需要计算环境。Route 53 负责 DNS，ACM 提供 HTTPS 证书，CloudFront 提供内容分发。

15. AWS：数据与权限

RDS 是托管关系型数据库；S3 是对象存储；DynamoDB 是另一种 NoSQL 选择，并非自动更适合所有 AI 应用。IAM policy 应限定 action 与 resource。ECS task role 供应用访问 AWS，execution role 则用于拉镜像、发送日志等执行职责。优先使用临时凭据，避免把长期 key 放进源码或镜像。

16. AWS：秘密、日志与费用

Secrets Manager 管理秘密配置的生命周期；更新后如何被运行中的应用使用需核实注入或读取机制。CloudWatch 可收集日志、指标并配置告警，但需要正确接入。计算、数据库、入口、NAT、存储、日志保留和流量都可能产生费用。AWS Budgets 通知可能延迟，不能当作自动费用硬上限。

17. 从源代码到运行版本

Git 记录源代码；构建产生可运行产物；镜像封装应用与依赖；容器是启动后的实例；部署替换目标环境里的版本。代码提交后可能触发自动流程，也可能不触发，取决于仓库配置。版本验收要核对实际产物与行为。回滚应用版本不必然回滚数据库变更，迁移需考虑兼容性。

18. AI 服务的失败与费用边界

浏览器将请求交给应用后端，再由后端调用模型、RAG 或 Agent 服务。后端负责权限、凭据和费用控制。SSE 等方式可以逐步返回结果；断流或超时不代表外部服务未执行。遇到 429、网络错误或 5xx，需按约定决定重试、退避与幂等，避免重复业务操作和重复费用。

19. 让 AI 根据证据修复

先复现并找到第一个失败边界，再提供脱敏请求、响应、日志和时间。要求 AI 解释证据、提出最小修复和验证步骤。不要只说“帮我修好”，也不要接受关闭权限、放开所有网络或全项目重构来掩盖问题。修复后重新走正常保存、失败反馈和数据重读。

Infrastructure as Code（IaC）

IaC 把需要的基础设施写进可版本管理的配置：网络、子网、安全组、计算服务、数据库，以及它们的参数和连接关系。团队可以审阅差异、复用配置，并让工具通过平台 API 管理资源。

Terraform 使用配置描述期望状态，Plan 预览变更，Apply 执行变更；CloudFormation 使用模板描述 AWS 资源，可通过 Change set 预览变更。配置文件存在，不代表资源已经创建。

应用代码处理业务；Dockerfile 定义镜像中的应用与依赖；IaC 管理承载应用的资源；CI/CD 编排检查、构建与发布。这些职责可以协作。

执行前核对账号、区域以及新增、修改、删除或替换的范围。Terraform State 可能含敏感值，应保护访问并考虑团队共享与锁。配置回退不能自动替代数据备份与恢复。

CI/CD：应用、镜像与基础设施怎样搭配

1. CI、Delivery 与 Deployment

CI（Continuous Integration）对改动执行约定的测试与构建验证。Continuous Delivery 保持版本可发布，并按策略保留发布决策；Continuous Deployment 可在满足策略后自动部署。检查通过、产物可用和生产业务正常，需要分别确认。

2. 三条交付路径

客户端 React：源码 → 检查与构建 → HTML/JS/CSS → 静态托管或 CDN。SSR 前端需要相应计算环境。Node.js 后端：源码 → 测试与 Docker 构建 → Registry → 应用运行服务。IaC：配置 → Plan/Change set → Review → 按授权 Apply → 网络、权限和数据等基础设施。应用每次更新不必重建全部基础设施。

3. 同一版本，不同环境

记录 commit、版本和 artifact digest；晋级时使用同一个经过验证的产物。Development、Staging 和 Production 分别管理地址、数据、角色与秘密配置。前端公开构建配置要通过选定的构建/运行策略处理，不能把服务端凭据放进客户端产物。

4. 用 GitHub Actions 编排

Event 触发 Workflow，Workflow 包含 Job，Runner 执行其中的 Step。检查、构建、产物保存、环境发布、业务回读之间设置明确依赖。环境保护、审批和分支限制按仓库能力与发布策略设计；具体功能可用性需核对套餐和仓库类型。云访问采用受限身份，避免在源码和镜像中保存长期密钥。

5. 发布验证与回滚

部署后先核对实际运行版本，再检查 Health、关键业务路径以及错误和延迟。失败时停止扩大影响，并按演练方案切回上一可用产物。Rolling、Blue-green 与 Canary 是可选择的发布策略。数据库迁移需要新旧版本兼容和恢复方案；回滚应用不等于恢复数据或撤销外部副作用。

Firewall：哪些流量可以进入服务

Firewall 根据策略控制流量。常见检查项包括来源或目标地址、协议、端口和方向；不同产品也可能检查更高层内容。访问地址正确，不代表网络规则允许连接。

AWS Security Group 控制关联资源的入站和出站流量。它只有允许规则，未获允许的流量被阻止；它是 Stateful，允许连接的响应流量由连接跟踪处理。网络 ACL 在子网边界工作，是 Stateless，支持按顺序匹配允许或拒绝规则，返回流量也需符合相应规则。

WAF 关注 HTTP/HTTPS 请求特征；IAM 控制云资源操作；应用负责登录与业务授权。放行某个端口不等于用户有权读取数据，也不能替代 Web 请求防护。

排查连接时同时核对路由、监听端口、规则和日志。超时不一定来自防火墙；网络阻断也不一定返回 HTTP 403。仅开放必要来源和端口，数据库通常只接受指定应用来源。

CORS · Cross-Origin Resource Sharing

CORS 的全称是 Cross-Origin Resource Sharing，跨域资源共享。Origin 由协议、主机和端口共同决定；浏览器依据服务端的允许来源响应头，决定是否让页面 JavaScript 读取跨域响应。它不能替代登录与业务授权。

Console 常见红字

Missing header：“No 'Access-Control-Allow-Origin' header is present on the requested resource.” 请求可能已经到达服务端，但响应没有允许当前页面来源的头。打开 Network，核对实际响应、页面 Origin 和 API 或代理的配置。

Preflight：“Response to preflight request doesn't pass access control check”。浏览器先发送 OPTIONS 检查方法与请求头是否被允许。检查 OPTIONS 的状态和响应头；预检未通过时，浏览器不会继续发送对应的实际请求。

Credentials：“must not be the wildcard '*' when the request's credentials mode is 'include'”。带凭据读取跨域响应时，允许来源应明确指定，不能用 *，并需正确配置 Access-Control-Allow-Credentials。Cookie 还受 SameSite 等规则影响。

页面代码可能只拿到 TypeError: Failed to fetch；具体原因要看 Console 与 Network。mode: no-cors 会限制请求并产生不可读取内容的 opaque 响应，不能当作读取 JSON API 的修复。浏览器主题和版本可能改变红字措辞与颜色。

Agent 运行环境：Process、Container、VM 与 microVM

Agent 是执行中的程序：组织上下文、调用模型、处理工具结果并保存成果。Node.js 或 Python 是代码运行时；Strands、LangGraph 等框架组织 Agent 逻辑；远程 Model API 提供推理。调用模型不等于模型运行在你的容器里。

隔离边界怎么理解

Process 是运行中的程序。常见 Linux 容器把应用和依赖组织起来，以进程和文件等机制隔离，但共享所在系统的内核。VM（Virtual Machine）有自己的 Guest OS / Kernel，通过虚拟化承载。microVM 仍有独立 Guest Kernel，面向特定工作负载精简设备模型和开销。Firecracker 是一种基于 KVM 的 microVM VMM，它不等同于 AgentCore 服务。容器和 VM 可以组合；Docker Desktop 也可能在 Linux VM 中运行容器。

Amazon Bedrock AgentCore Runtime

AgentCore 提供一组 Agent 基础能力，Runtime 是承载 Agent 或工具代码的服务。microVM 计算模式为不同 Session 分配隔离的执行环境。应用后端仍需认证、维护用户与 Session 的对应关系，并检查外部工具、文件和业务数据的访问权限。

当前官方文档也提供 Instances 计算模式：在账户内由 AWS 管理 EC2 运行环境，面向长运行、特定硬件或协作会话。它与 microVM 的隔离单位和持久化语义不同，不能把所有 AgentCore 运行方式都概括为同一种模型。

会话与长期数据

在 microVM 模式下，同一活动会话可保留执行上下文；环境终止后，不应把原内存或临时文件当成长期数据。任务状态、业务成果、文件和记忆需按用途显式保存，例如业务数据库、对象存储或 AgentCore Memory。持久会话存储需明确配置，Instances 的停止/恢复与持久卷模型也需按相应文档设计。冷启动、超时、幂等、日志、工具权限和网络出口仍要考虑。
