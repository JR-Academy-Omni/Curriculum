# 第一部分：理解搜索获客

## 1.1 从业务结果倒推搜索的作用

假设 Maya 搜索预约工具。她可能只是要查一个时间，也可能正在比较软件，还可能已经购买工具、只需要排错。相同的“预约”主题可以对应完全不同的需求。

如果 Maple Slot 只关注“预约”一词能带来多少流量，就可能写很多与当前产品无关的内容。访问者来到页面后仍无法得到所需结果，经营者也无法承接他们的需求。流量增长和商业进展因此可能脱节。

先定义三件事：

- **目标客户**：有跨地区预约需求的小型工作室经营者，而非所有需要日历的人。
- **可交付结果**：当前能提供一种检查预约时间显示的方法；未来软件能力还没有实现。
- **合理行动**：当前读完完整指南并使用检查表；产品就绪后，才考虑进入真实产品演示、正式注册和付费。

这给第一轮内容划定了范围。免费工具排名、自动提醒配置和“减少爽约率”的效果文章，暂时都缺乏能力或证据支持。

### 案例产物 1：获客目标简报

| 字段 | 已填内容 |
|---|---|
| 项目 | Maple Slot，拟开发的预约工具 |
| 首轮受众 | 有跨地区预约的小型教学工作室经营者 |
| 触发场景 | 发现顾客和自己对时间/日期理解不同 |
| 当前交付 | 可阅读、可复核的 Brisbane 时间显示检查指南与表格 |
| 主要行动 | 完成一次自己的时间显示检查 |
| 后续假设 | 一部分读者可能需要相关产品，尚待验证 |
| 不作承诺 | 自动提醒、所有时区正确、降低爽约率、软件已开放 |

这个简报会约束后续关键词、页面文案、CTA 和测量指标。不能第一章决定“先帮助检查”，第三章却突然引导用户购买不存在的产品。

## 1.2 搜索引擎在这条路径里做什么

搜索引擎需要发现页面、取得内容、理解内容并决定是否索引，以及在某次查询下如何展示。一个阶段成功不意味着下一个阶段必然成功。[SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)

```mermaid
flowchart LR
  A[客户产生具体需求] --> B[发起搜索]
  B --> C[搜索系统展示候选内容]
  C --> D[用户判断是否点击]
  D --> E[页面兑现需求与承诺]
  E --> F[用户采取合适行动]
  F --> G[经营者验证结果并改进]
```

从站长角度，可把页面状态分为：地址存在、可以取得、内容完整、允许索引、已经索引、产生搜索展示、产生有效行动。不要把这些状态压成一个“SEO 已做好”。

最低技术准入涉及 Googlebot 不被阻止、有效的 HTTP 200 响应以及可索引内容；符合条件也不保证索引。[Search technical requirements](https://developers.google.com/search/docs/essentials/technical) HTTP 200 只说明一次请求按成功状态返回，不能证明页面内容有用、产品可用或客户购买。

Maple Slot 当前连真实站点都不存在，所以此时能交付的是内容与验收设计，不能报告收录或排名。预检留到第五部分实际说明；在真实项目中应在大量写作前先查严重阻断。

## 1.3 SEO、付费搜索和直接触达怎样分工

自然搜索不按每次自然点击向搜索引擎支付广告费，但内容、开发和维护仍有成本。付费搜索需要单独的广告预算、账户、投放策略与落地页；用户访谈、合作和直接触达又是不同的获客动作。

对早期项目，SEO 可以积累有用内容和需求证据，却不能自动解决所有验证问题。需要短期确认客户需求时，可以另行设计获授权的访谈或其他实验；不要以“发更多文章”代替确认客户是否存在该问题。

本课程采用一个工作原则：每项投入都写清预期解决哪一个瓶颈。内容不能被取得时，先修取得问题；有人读但没有需要时，回到需求；有需要但产品不支持时，回到产品。

# 第二部分：理解客户需求

## 2.1 从用户的一句话还原任务

下面是为课堂编写的情景记录，不是真实采访：

> Maya：我看到的是明天凌晨一点，学生却说是今天。预约是不是记错了？
>
> Maya：我想先确认显示有没有问题，再决定要不要换工具。
>
> Maya：如果换工具，我需要知道已有预约是否会变，而不只是看一个漂亮日历。

第一句反映日期与时区的困惑，第二句说明她尚未进入购买决策，第三句说明比较工具时关心已有数据与迁移风险。

把用户表达拆成“触发事件、要完成的任务、成功标准、担忧、下一步”，比直接把“预约软件”当作主关键词更有帮助。一个页面应完成一个可解释的主要任务，同时支持必要的相关步骤。

### 案例产物 2：需求卡

| 观察 | 教学分析 | 尚不能推断 |
|---|---|---|
| 看到不同日期 | 需要分清存储时间与显示时区，检查跨日 | 不能断言系统真的出错 |
| 先确认、再换工具 | 先需要方法指南 | 不能当成已准备购买 |
| 担心已有预约变化 | 选型需要数据/迁移标准 | 不能宣称 Maple Slot 已支持迁移 |

真实项目的需求卡还需要来源、时间、授权与适用范围。访谈原话、工具估计、个人推测应分开；有个人资料时先脱敏。

## 2.2 从任务到候选搜索表达

客户未必使用你的产品术语。了解技术的人可能搜索 UTC，刚遇到问题的人可能只会描述“预约日期错了”。Google 能理解一定范围的词义和变体，不要求为每种措辞各造一页。[SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)

本案例形成下面十条候选表达。它们没有真实搜索量或排名数据，意图是教学假设。

| ID | 候选搜索表达 | 主要任务 | 第一轮安排 |
|---|---|---|---|
| Q01 | appointment booking software for small studios | 选择工具 | P1 适配与状态页；能力先核验 |
| Q02 | booking system timezone display | 理解显示 | P2 指南 |
| Q03 | check appointment times across time zones | 检查流程 | 合入 P2 |
| Q04 | UTC to Brisbane appointment time | 换算与核对 | P2 示例 |
| Q05 | booking app wrong day | 排查跨日 | P2 错误分支 |
| Q06 | appointment booking software comparison | 比较选择 | P3 选型方法 |
| Q07 | shared calendar vs booking tool | 比较工作方式 | P3，待核相关性 |
| Q08 | booking reminder setup | 配置提醒 | 暂不做，无产品与步骤 |
| Q09 | reduce appointment no shows | 改善业务表现 | 暂不作效果承诺 |
| Q10 | free appointment scheduling app | 寻找免费工具 | 暂不做，价格方案未定 |

Q02–Q05 的措辞不同，但围绕同一个检查任务。写一份完整指南可能比四篇重复短文更合理。Q06 与 Q07 属于选择任务，可以接在检查之后；Q08 不能因为看起来有商业价值就编出设置教程。

## 2.3 结果页观察怎样改变判断

候选意图需要验证。观察目标地区、语言、设备与时间下的实际结果页，记录自然结果、广告、本地结果、视频等分别出现了什么；查看代表页面究竟提供什么结果。搜索界面会变化，单次观察不是永久结论。

观察记录至少包括：候选词、观察环境、时间、代表 URL、结果类型、页面满足的任务，以及自己能增加的有用内容。关键词工具给出的搜索量或难度要附工具和口径，不能伪装为 Google 内部指标。

本次没有为 Q01–Q10 执行真实查询。因此不在这里虚构竞品排名。课堂可用下面的**条件情景**练习决策：

| 如果实际观察到 | 可以形成的下一步 | 不能直接得出的结论 |
|---|---|---|
| 结果大多是排错指南 | 优先做可执行检查与例外说明 | 每个用户都不想买工具 |
| 结果以本地商家为主 | 检查是否属于本地服务需求 | 纯在线软件应虚构当地门店 |
| 结果多为软件比较 | 建立相同标准和来源的比较框架 | 写自己第一名即可胜出 |
| 结果与预期不一致 | 改写需求假设，再选页型 | 一定是“竞争太激烈” |

## 2.4 选题优先级：相关、可交付、有证据

不把搜索量等同收入。优先选择与目标客户相关、当前能够解释或交付、已有材料能支持、并且有合理下一步的需求。资料不足就先做研究，不用虚构数字把表填满。

Maple Slot 第一轮先写 P2，因为它已有明确方法和可以复核的固定数据。P1 应说明真实项目状态，P3 先提供选型方法。Q08–Q10 暂缓，是一种合理的范围控制。

# 第三部分：设计能够满足需求的页面

## 3.1 先分配页面职责

Maya 的路径是“检查是否出错 → 理解选择标准 → 判断产品是否适合”。三个任务可以用三个互相支持的页面承接。

| 页面 ID | 职责 | 核心成果 | 主要连接 |
|---|---|---|---|
| P2 检查指南 | 完成有限的时间显示检查 | 三条输入、预期、步骤和限制 | 解释为什么这些标准影响 P3 选型 |
| P3 选型方法 | 按同一标准比较方案 | 需要核对哪些能力和证据 | 回到 P2 检查，查看 P1 当前状态 |
| P1 项目适配与状态 | 准确认识 Maple Slot 及能力边界 | 面向人群、当前可读材料、未开放能力 | 进入 P2；未来产品完成后再接真实体验 |

P1/P2/P3 是教学材料编号，不是已发布 URL。真实项目应先检查现有页面能否承担职责，不因练习改动线上地址。

页面之间的链接应解释下一步的价值。“查看工具时区选型标准”比含义不明的“点这里”更容易理解。面包屑帮助理解位置，正文内链帮助继续任务，两者职责不同。

## 3.2 从页面提纲写成完整内容

页面草稿先确定主要任务和标题，再准备正文、证据、例外与行动。Title 是搜索展示可能使用的信息之一；H1 是可见主标题；meta description 是摘要候选。三者可以措辞不同，但应承诺相同的实际结果。[Title links](https://developers.google.com/search/docs/appearance/title-link)[Snippets](https://developers.google.com/search/docs/appearance/snippet)

不要把某个固定字数当排名门槛；也不要用夸张标题换来点击，再让正文兑现不了。Google 可能重写搜索标题或摘要，页面作者不能保证最终展示。[Title links](https://developers.google.com/search/docs/appearance/title-link)[Snippets](https://developers.google.com/search/docs/appearance/snippet)

下面直接给出 P2 的完整教学稿，后面的可信度、技术和测量都针对它继续工作。

### 案例产物 3A：P2 完整页面稿

**文稿性质：虚构课堂材料。下列文字可作为内容审稿对象，尚未发布。**

**页面标题候选：** Brisbane 预约时间检查：用三条记录核对日期与时区

**可见主标题：** 如何检查预约时间是否按 Brisbane 时间显示

**摘要候选：** 用三条固定记录核对上午、傍晚与跨日显示，记录列表、详情和保存后的结果。包含检查步骤、预期值与适用限制。

**作者与责任：** 创业营练习团队（虚构教学身份）；未进行真实软件测试，未发生专家审核。文稿编写日期：2026-10-17。

#### 这份检查能帮助你做什么

当存储的预约时间是 UTC，而工作室按 Brisbane 时间查看预约时，可以用一小组固定记录检查显示日期和时间。先确认究竟是哪一层发生变化，再判断是否需要调整工具或配置。

本例只覆盖下面三条时间，不说明任何软件已经正确，也不证明系统适用于全部国家和日期。准备自己的检查时，先确定设备、账户和页面显示的时区。

#### 准备三条记录

以下是练习输入；Brisbane 预期值按本例 UTC+10 换算。别把真实学生资料复制进练习数据。

| 记录 | 存储的 UTC 时间 | Brisbane 预期显示 | 要检查什么 |
|---|---|---|---|
| A-001 | 2026-10-17 00:00 | 2026-10-17 10:00 | 上午、同一天 |
| A-002 | 2026-10-17 08:30 | 2026-10-17 18:30 | 分钟数、傍晚 |
| A-003 | 2026-10-17 15:00 | 2026-10-18 01:00 | 时间跨过午夜后，日期也变化 |

这三条记录不覆盖夏令时、重复/不存在的本地时间或其他地区规则。检查其他地区时，应另外选择相应日期和可靠的时区规则。

#### 执行检查

在获授权的隔离环境中建立练习记录。先在桌面打开预约列表和详情，分别记录时间、日期及页面标明的时区；如果产品支持编辑保存，再保存并刷新检查。接着用手机重复这些观察。

不要只看列表。列表显示正确，详情、编辑框或保存后仍可能不同。每一步都记录实际值，不依赖记忆。没有编辑能力就标为不适用，不能编一个保存成功。

如果工具支持提醒预览，可单独核对预览时间；本练习不要求发送真实通知。预览正确与真实发送成功是两个不同结论。

#### 怎样判断结果

把实际值与表中预期比较。A-003 如果显示为 2026-10-17 01:00，小时看起来像凌晨一点，日期却少了一天；这是这一条数据的检查不符。应记录输入、预期、实际和发生位置，而不是笼统写“时区坏了”。

三条都相符，也只代表本次条件下这三条记录符合预期。它们不能替代其他时区、角色、设备和业务动作的测试。

#### 保存你的检查记录

每条记录写入：UTC 输入、目标时区、预期值、实际值、列表/详情/保存位置、设备、检查时间、截图以及结论。对“不知道系统存储什么”的情况，先向负责人确认，不反推或覆盖原预约。

#### 下一步

如果显示不符，带着记录排查存储值、时区设置、转换逻辑和页面渲染。只有某个页面出错时，先缩小排查范围；不要立刻迁移全部真实预约。

如果准备选择工具，用这些记录检查候选方案，再核对权限、数据导出、价格和支持范围。下一篇《预约工具选型检查表》会把这些标准放到同一张表里。

#### 关于 Maple Slot

## 4.1 E-E-A-T 如何进入这三页

Google 用 E-E-A-T 概括经验、专业知识、权威性与可信度，并强调信任最重要。它不是单一排名因素，没有供站长查询的官方总分；评估员的评分也不直接决定某页排名。对可能显著影响健康、财务或安全的 YMYL 主题，需要更重视可靠性。[Helpful, reliable, people-first content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

对创业者，重要的是让读者判断“这些话为什么可信”。以下是课程对四维的操作化，不是 Google 官方评分表。

# 第五部分：保证内容能够被取得和使用

## 5.1 把技术问题对应到用户任务

Maya 需要读完整指南。如果页面打不开，内容再好也无用；如果返回成功却只有加载动画，用户仍没有得到内容；如果指南有用而页面被错误 noindex，搜索也可能无法正常带来访问。

技术检查应围绕具体失败逐层定位：

| 层 | 先确认什么 | 对 P2 的意义 |
|---|---|---|
| 地址与响应 | URL 正确、状态合适、无错误循环 | 用户能取得这篇指南 |
| 资源与内容 | 主要文字、表格、图片和链接可取得 | 指南不只是空壳 |
| 抓取与索引 | 允许所需访问，索引规则与目标一致 | 公开内容没有误被排除 |
| 版本与语言 | 首选版本、语言对应与链接一致 | 不把用户或信号引向错误页 |
| 用户操作 | 手机、键盘、错误与主要路径可用 | 能完成检查和后续任务 |
| 性能 | 主要内容、交互和布局不妨碍使用 | 操作过程顺畅且可复核 |

真实工作中，前三层的严重阻断应提前检查，避免写完几十篇文章才发现全站不可取得。教学上放在这里，是为了先让学员知道自己要交付什么内容，再理解技术为什么重要。

## 5.2 用 URL 和 HTTP 解释常见失败

URL 可以含协议、主机、路径、查询参数与片段。路径定位页面，参数可能表示筛选、跟踪或不同内容，片段通常定位页面内部位置。不能因为都是参数就一律删除，也不能把所有不同地址都当独立内容。

浏览器请求一个页面，服务端返回状态、响应头和内容。GET 常用于读取；POST、PUT、DELETE 等涉及不同业务操作，排查 SEO 不需要为了测试而提交或删除真实数据。

| 状态 | 在本课程中的理解 | 下一步 |
|---|---|---|
| 200 | 请求按成功状态返回 | 仍需检查正文是否真是目标内容 |
| 301/308 | 永久重定向 | 检查是否到对应内容、有无循环；不自行迁移已有 URL |
| 302/307 | 临时重定向 | 检查是否符合实际意图 |
| 401/403 | 权限或拒绝访问 | 判断内容本来是否应公开 |
| 404/410 | 未找到或已移除 | 已删除内容可能合理；修复本应存在的页面/链接 |
| 5xx | 服务端错误 | 查稳定性与原因，不用空白 200 掩盖错误 |

“软 404”可理解为内容看起来像错误或不存在，却没有按预期提供有效目标内容的情况。不要把正常的删除页一概当成必须恢复，也不要把每次降流量都归因于状态码。

## 5.3 robots、noindex 与权限各管什么

robots.txt 管理抓取访问，不是隐私保护机制，也不能保证 URL 完全不出现在结果里。要让搜索系统读取页内 noindex，不能同时用 robots 把该内容阻止到读不到。[Robots.txt introduction](https://developers.google.com/search/docs/crawling-indexing/robots/intro)

因此，公开指南与私人预约记录需要不同处理：P2 是希望公开取得的内容；真实用户预约记录属于权限边界，不靠 robots.txt 隐藏。搜索优化不能成为开放客户资料的理由。

本案例只规划这些边界，没有更改任何配置。未来检查时，记录规则来自哪里：页面 meta、HTTP header、robots、CDN、防火墙还是认证。多个层次可能互相覆盖，不能只看页面源码的一行。

## 5.4 canonical、站点地图与多语言

同一内容可能有跟踪地址和首选地址。canonical 表达首选版本，Google 仍会判断；它不保证索引，也不适合把不同任务的页面全部归到首页。[Canonical URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

P2 与 P1 的内容不同，因此本案例不把 P2 canonical 到 P1。站内链接、canonical 与 sitemap 应尽量一致。sitemap 是发现与管理页面的辅助，不能保证收录；lastmod 如提供，应来自内容的重要真实更新。[Build a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

中英文若为对应内容，应核对各自语言、可访问性和 hreflang 对应关系，不要把所有翻译都 canonical 到单一语言。[Localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions) 本书用中文教课、英文记录候选搜索表达，不意味着实际中文页应直接使用英文 title；正式面向英文市场时，需要完整的英文内容与相应校验。

原稿强调 URL 结构有启发，但已有可访问地址应保留。迁移是独立工程，涉及映射、重定向与验证，不作为课堂的随手优化动作。

## 5.5 渲染方式只在影响结果时深入

CSR 由浏览器执行脚本形成内容；SSR 在请求时提供服务器生成的 HTML；SSG 在构建时预生成页面。三者可能在同一产品中组合使用。

对稳定的公开指南，预生成可能便于交付；对需要登录、按用户变化的预约内容，需要同时考虑权限和动态数据。选择依赖于更新频率、数据、成本与交互，不存在所有页面通用的优胜方式。

Google 可以处理 JavaScript；实际要检查其取得的内容、资源和链接。不要只因使用 CSR 判为不合格，也不能只因用了 SSR 就宣布内容或体验良好。[JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

读者可见内容与可交互状态也不同。服务端先给出 HTML 后，某些控件仍需脚本；静态页面也可能需要交互脚本。原稿关于“收到页面就立即交互”的图应作为简化说明。

## 5.6 性能与实际体验一起验收

| Core Web Vital | 意义 | 当前 good 目标 |
|---|---|---|
| LCP | 主要内容加载 | ≤ 2.5 秒 |
| INP | 交互响应 | ≤ 200 毫秒 |
| CLS | 视觉稳定 | ≤ 0.1 |

官方建议按移动端与桌面分别看第 75 百分位，并检查三项。[Web Vitals](https://web.dev/articles/vitals) FID 是旧指标；本课程不再用旧 TTI < 5s 或单次 Lighthouse 满分当整页验收结论。

P2 的关键体验包括：表格在手机上可读、跨日日期不被截掉、链接说明下一步、键盘能操作、错误有反馈。实际产品的 Demo 还要核对已有内容、编辑保存、重置退出和隔离。

没有真实用户数据时，记录缺失；实验室测试可帮助定位，但不能伪装成现场分布。本次只检查教材与确定性练习材料，没有运行真实网站或产品 UI。

## 5.7 结构化数据忠实描述页面

结构化数据帮助表达内容，但必须与读者可见事实一致。验证工具通过，不保证富结果展示；不要添加不存在的评分、作者、价格或库存。[Structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

对本例，P2 可以先把方法、署名和状态写清，再按未来真实页面的类型选择适用标记。没有专家审核就不写 reviewedBy，没有实际用户评价就不写 AggregateRating。

当前 FAQ 富结果已退役：官方更新记录说明自 2026-05-07 起不再显示，6 月移除文档。[Search documentation updates](https://developers.google.com/search/updates) FAQ 正文依然可以帮助读者，但不应以“添加 FAQPage 必出展开结果”作为目标，也不混淆 FAQPage 与用户问答型 QAPage。

## 5.8 Google AI 搜索回到同一内容与技术基础

Google 的当前优化指南强调独特有用的内容、常规 SEO 基础和良好体验；不要求 llms.txt、专用 schema、固定短切块或某种特殊写作口令。[AI search optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

对 Maple Slot，最有用的准备是把输入、方法、跨日错误和限制解释清楚。把同一个小问题改写成几十篇“AI 友好”短文，会失去完整性，不能保证引用。

当前官方帮助还提供 Search generative AI 控制项：检查 Include/Exclude 或父属性继承，和普通索引、Google-Extended 训练控制分别理解。[Search generative AI control](https://support.google.com/webmasters/answer/16908024) 这些是网站管理选择；本课只读说明，未改任何实际账户。

效果测量见下一部分。面对不同 AI 平台，要单独核对其抓取和数据能力，不能把 Google 的结论推广到全部服务。

### 本部分练习

# 第六部分：验证获客是否有效，决定下一步

## 6.1 先定义动作，再解释数字

页面能被取得，只解决了路径的一部分。Maya 是否找到内容、看懂方法、完成检查，以及是否需要产品，是不同的问题。

测量前先写“什么事情发生才记一次”。按钮点击只能证明某种点击；表单提交必须确认是否真正保存；合格线索要按预先定义的条件确认；付款要看可信业务状态。GA4 可以把重要行为对应事件标记为关键事件，但仍需要实际事件与适当权限。[GA4 key events](https://support.google.com/analytics/answer/13128484)

### 案例产物 6A：事件与结果字典

下表为设计，不代表已经接入任何分析系统。

| 记录 | 触发定义 | 去重/范围 | 能说明什么 |
|---|---|---|---|
| P2 访问会话 | P2 主要内容已显示的一次目标会话 | 同一练习窗口、目标渠道与页面范围 | 有机会阅读，不等于读完 |
| checklist_complete | 用户完成并确认一份独立检查记录 | 每会话计一次，排除演示自动填充 | 方法被实际使用的一种信号 |
| P3 阅读入口 | 从 P2 进入选型方法页 | 同一范围内去重会话 | 表示继续了解选择标准 |
| P1 阅读入口 | 从内容进入项目适配与状态页 | 同一范围内去重会话 | 表示了解项目，不等于需求或购买 |
| 成功反馈/询盘 | 真实表单已保存成功 | 预设去重与测试排除 | 仅在该能力实现并获授权采集后可测 |
| 合格线索 | 负责人确认需求匹配当期可服务范围 | 与成功询盘对应且去重 | 不能把所有访问者算作客户 |
| 付款 | 业务系统确认真实支付，并处理重复/退款口径 | 明确订单和观察周期 | 不能由前端点击代替 |

当前 P1 没有表单和软件，后面三项不能填“0 说明没人要”，应写未采集或不适用。先有能交付的动作，才谈相应转化。

采集还要明确内部测试、Demo、机器人与真实访问的区分，记录日期、时区、归因窗口和数据来源。不把无需收集的姓名、邮箱或私人记录塞进分析字段。

## 6.2 用合成场景练习诊断

下面设想**未来仅内容网站完成发布并具备对应测量**后的两个相等观察窗口；不是 Maple Slot 的实际进展，也不是从 Search Console 或 Analytics 导出的数据。软件仍未开放，P1 仍如前文说明项目状态。

课堂假设两个窗口都能用同一规则识别从 P2 开始的目标会话，并在窗口内对继续行为去重。真实跨平台报告通常不能直接一一相连，需要先核对口径。本练习已设定可比条件，只为计算与讨论。

| 指标 | 窗口 A，14 天 | 窗口 B，14 天 | 数据性质 |
|---|---|---|---|
| 常规搜索曝光 | 1,000 | 1,200 | 合成 Search Console 类计数 |
| 常规搜索点击 | 60 | 72 | 与曝光同一模拟报告范围 |
| P2 目标访问会话 | 58 | 70 | 合成网站分析会话，和点击不强行等同 |
| 完成检查表的去重会话 | 12 | 24 | 同一 P2 会话群内的事件 |
| 继续进入 P3 的去重会话 | 8 | 18 | 同一 P2 会话群内的后续行为 |
| 继续进入 P1 的去重会话 | 6 | 12 | 同一 P2 会话群内的后续行为 |
| 成功询盘 | 未采集 | 未采集 | 相关入口未实现 |
| 合格线索 | 未采集 | 未采集 | 没有对应数据 |
| 真实付款 | 不适用 | 不适用 | 没有开放销售 |

完整字段见 [practice/measurement-scenario.csv](practice/measurement-scenario.csv)。

### 可以计算的结果

- 同一模拟搜索报告中的 CTR：A 为 60 / 1,000 = 6%，B 为 72 / 1,200 = 6%。
- 同一模拟 P2 会话群的检查完成比例：A 为 12 / 58 ≈ 20.7%，B 为 24 / 70 ≈ 34.3%。
- 同一模拟会话群进入 P1 的比例：A 为 6 / 58 ≈ 10.3%，B 为 12 / 70 ≈ 17.1%。

同一会话可能完成检查后再访问两页，不能把这三种行为相加当成三个不同的人。58 与 60 的差异也不能直接叫“流失 2 人”，因为会话与搜索点击的定义不同。

### 这些结果支持什么判断

在设定的练习范围内，B 有更多会话完成检查并继续看相关页面，搜索 CTR 没有变化。可以提出“检查流程更容易使用”的假设，并查看是否存在相应改动或来源变化。

但这里没有随机对照、没有真实观察，也没有商业数据。不能宣称完成率变化由某一项 SEO 修改导致；更不能宣称营收上升。即便数据是真的，访问者构成、渠道、设备、季节和事件采集变化也可能影响比较。

### 案例产物 6B：已填诊断结论

> 本模拟中，内容使用行为的比例提高，搜索点击率保持相同。现有数据不能验证产品需求或付费意愿。下一步先检查事件口径与来源构成，再观察用户能否按方法得到结果；若计划增加适配反馈或产品体验，应先明确实际交付能力并取得相应实施与采集授权。当前不把进入 P1 计为合格线索。

这是一份完成了推理的教学诊断，不是把所有未知都勾成成功。

## 6.3 出现问题时，沿路径往回查

| 观察到的现象 | 先回到哪一层 | 可能的验证动作 |
|---|---|---|
| 页面无曝光 | 准入、发现、索引、需求与报告范围 | 核对属性/URL、实际内容、阻断和观察时间 |
| 有曝光，点击少 | 需求匹配与展示 | 查看查询、设备、结果类型，检查标题摘要是否准确 |
| 有访问，方法少人完成 | 页面内容与使用体验 | 检查表格、理解成本、控件、事件是否漏采 |
| 看项目的人多，实际需求不明 | 目标与产品适配 | 获授权后取得真实反馈，不把访问当购买意愿 |
| 询盘多，合格需求少 | 承诺、来源与资格定义 | 检查是否吸引错误人群或误导服务边界 |
| 突然掉流量 | 数据、范围与变更 | 先核对采集异常、受影响页面、技术变更与季节，再讨论算法 |

Google 的排查建议强调观察时间、受影响范围和趋势，不鼓励因短期波动激烈改站。[Debugging traffic drops](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops) 本课程不设“发布七天必收录”“三十天必提升”的统一期限。

## 6.4 Google AI 搜索怎样测

当前 Generative AI performance report 提供 Google AI Overviews、AI Mode 的曝光，可按页面、国家、日期和设备查看；曝光不足时可能没有报告。官方日期口径为 PT。不要补造其未提供的独立转化或排名指标。[Generative AI performance report](https://support.google.com/webmasters/answer/16984139)

这类曝光与普通报告可能有重叠口径，不能相加成“总搜索人数”。对某次 AI 回答的人工观察，也要记录日期、环境、问题和引用原页；一次出现不能代表稳定覆盖，未出现也不证明永远不会出现。

Maple Slot 当前没有报告，因此本书不提供 AI 搜索数字。前面的合成 CTR 仅用于常规搜索模拟，不混入 AI 报告。

## 6.5 把迭代写成明确任务

复盘的输出应是下一轮工作，而非单纯截图。每个任务至少包含：触发证据、影响用户、改动范围、责任人、验收方法、所需权限和复核条件。

### 案例产物 6C：下一轮任务单

| 优先级 | 任务 | 原因 | 完成判断 |
|---|---|---|---|
| P0 | 清除所有无证据功能和效果承诺 | C02–C04、C06 不成立 | 正文、标题、摘要、标记一致，项目状态明确 |
| P1 | 验证 Maya 代表的需求是否真实且有范围 | 当前用户记录为虚构 | 有获授权、可定位的真实材料与适用条件 |
| P1 | 核对未来页面的可取得性与测量定义 | 尚无真实站点 | 取得实际证据；未做不得标通过 |
| P1 | 产品若继续开发，单独定义 Demo 和功能验收 | 内容方案不等于产品完成 | 正式路径、已有资料、核心操作、隔离和退出实际通过 |
| P2 | 根据真实阅读反馈完善 P2/P3 | 需要找到理解或操作瓶颈 | 修改能对应实际问题，不为篇幅扩写 |
| 待测 | 业务结果是否受益 | 未采集询盘和付款 | 能交付与获授权后建立一致口径 |

30 天可以用来安排这些动作，但不是排名期限。建议第 1 周确认需求与资料，第 2 周完成内容与证据，第 3 周在另行授权后实施、发布并验收，第 4 周读取可用数据和安排下一轮。权限或能力没有就保留当前状态，不用假成功填补时间表。

维护时关注功能、价格、规则、步骤和证据是否仍准确；并非每篇文章每周都需要更新。保留仍服务独特任务的内容，更新过期部分，合并真正重复的内容前先做迁移方案。删除、重定向与账户变化仍受授权约束。

## B. AI 内容生产的编辑流程

AI 可以协助整理结构，但发布前仍需要查事实、方法、引用、价格与字段；人工审核应覆盖标题、摘要、图片说明和结构化数据。大量生成缺乏增量价值的页面可能违反 scaled content abuse 政策。[Using generative AI content](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)

在本案例中，AI 可以整理 C01–C06 台账，却不能替 Maple Slot 创造一个实际测试、客户或审核者。研究、引用与真实执行必须有各自记录。

5. 技术/体验检查记录，清楚区分已执行、未验证与不适用。
6. 测量字典、可比数据的诊断与下一轮任务。

读者应能从你的输入找到页面，从页面找到证据，从证据找到检查，再从检查和数据找到下一步。任何一个数字、案例、截图和主张都不应突然出现在流程中、却没有来源。

本书交付的是完整可阅读教材、文稿示例与练习资料。没有开发 Maple Slot，没有实现 Demo 账号，没有读取真实账户或验收索引/排名。真实产品 Demo 和正式发布需要按实际项目执行。本文本、练习数据与报告不冒充已上线能力或客户成果。
