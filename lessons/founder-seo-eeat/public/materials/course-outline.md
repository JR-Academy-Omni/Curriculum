# AI 时代的 SEO / GEO 基础与实战：完整授课大纲

版本：讨论稿 v1 · 2026-10-18（Australia/Brisbane）  
主讲：Lightman  
范围：授课设计与备课清单；尚未修改、替换或重新制作课件和海报。  
适用：网站经营者、营销与内容人员、个人品牌经营者，以及需要理解 SEO 的开发者。

## 1. 课程定位、目标与边界

课程系统讲解 SEO 应该掌握的基础，覆盖内容、技术、可信度、个人网站、AI 辅助和 GEO。原 PPT 中的技术内容仍是全员需要理解的基础；代码用于帮助看懂问题、验证结果和提出准确的修改要求，不要求学员在课上搭建完整框架或云环境。

主线：理解搜索如何工作 → 找到用户需求 → 做好页面内容 → 保证技术交付 → 建立可信证据 → 使用 AI 辅助工作 → 理解 GEO → 测量与迭代。

学员完成课程后应能：

1. 说明抓取、渲染、索引、展示、访问和业务行动的区别。
2. 对一个真实页面做内容与技术检查，记录问题、证据、建议和验证方法。
3. 为个人或企业整理作者身份、实际经验、项目成果、来源及相关外部记录。
4. 使用 AI 做有依据的整理、审稿与诊断，并核验输出。
5. 区分 Google 与其他 AI 搜索平台的规则，设计可重复的 GEO 观察。
6. 根据实际数据排出下一轮优化任务，不把相关变化直接解释为因果。

课堂采用多个真实案例分别解释知识点。Maple Slot 不再作为本大纲的贯穿案例。原 PPT 的房产、手袋和历史网站图片按原有来源使用，讲解时标明历史性质；不把历史排名、价格或图表数量当作当前项目成绩。

课程成果：一份页面检查记录、一份页面修改简报、一份 E-E-A-T / 个人网站实施计划、一份 GEO 观察记录，以及一份有验证条件的优化待办。它们是课程拟训练的产物；本大纲不宣称已经完成这些真实网站的优化或取得排名提升。

## 开场：用一份检查记录说明课程要解决的问题（10 分钟）

**讲什么**：页面能打开、页面有内容、内容值得看、搜索能取得、用户完成任务是不同判断。先展示一份“观察—证据—建议—验证”的记录结构。

**怎么做**：打开 C4，定位状态说明、示例和来源；让学员看到一条有依据的结论应该链接到具体内容。随后打开 C3，只记录可观察页面现象，把未检查的技术项和后台数据留作未验证。

**案例与讲解边界**：MDN 文档讲的是 HTTP 404，页面标题不代表它自己返回 404。这个例子引出全课习惯：不能只根据标题、AI 摘要或一个分数下结论。

**本段产物**：一条记录示例：观察“正文解释404语义并给请求响应样例”；证据“具体段落”；下一步“Network核实本页实际响应状态”；当前结论“不推断本页响应码或Google收录”。

**接下一段**：知道怎样记录证据后，先判断页面应服务哪种搜索需求。

## 第一部分：搜索机制、需求与关键词（25 分钟）

### 1.1 搜索如何工作

- SEO、自然搜索与付费搜索；SEO 的内容、技术和维护投入。
- 发现链接 → 抓取资源 → 处理与渲染 → 索引 → 对查询组织结果。
- 排名、CTR、访问、有效行动分别回答什么；搜索量与商业价值的区别。
- 原稿 TACA（Technical / Audience / Content / Authority）保留为教学检查框架；原“Content Score × Link Score”不能讲成 Google 公布的算法。

### 1.2 关键词表达与搜索意图

- 品牌、通用、地点、长尾查询；方法、比较、产品、导航和本地服务需求。
- 一种任务可以有多种问法；同一关键词也可能有混合意图。
- 同一域名里，买房与洗衣房灵感可能服务完全不同的任务。

**怎么做**：先用 C2 两种历史结果识别任务，再选 C3 的一个真实内容主题。课上实际搜索时记录查询、日期、地区/语言、设备与结果类型；查看代表页面实际提供什么，不只读摘要。将观察、关键词工具估计与学员假设分列，不能填造搜索量。

**AI 运用**：让 AI 对给定查询做任务分组并给出理由；人逐组打开代表页面复核。没有搜索能力或实际数据时，AI 的分组是候选解释。

**真实案例**：C1 手袋困惑→养护内容；C2 房产购买与装修灵感对照；C3 指南型页面与品牌导航需求。

**练习（英文）**：Classify the supplied queries by user task. Select one page type and record the evidence and unresolved assumptions.

**产物 / 验收**：需求表至少包含查询、任务、页面类型、来源、日期、证据状态与下一步。能够解释为什么两种表达合并、两种任务分开。

**接下一段**：明确需求后，检查页面是否兑现它承诺的答案。

原稿对应：15–23、25–26、33 页。

## 第二部分：内容与 On-page SEO（30 分钟）

### 2.1 把内容写成用户可使用的答案

- 标题与页面任务匹配；简介、方法、输入、步骤、证据、限制和下一步各有什么作用。
- 信息文章、服务页、课程页与商品页的内容要求不同。
- 原创信息、实际经验与引用的职责；引用不是免除自己解释与核验的理由。

### 2.2 页面结构与搜索展示

- HTML title、可见 H1、H2/H3、meta description、URL 与搜索摘要的关系。
- 结构让人读懂；不把唯一 H1、固定字数或 title 字符长度讲成普适排名处罚/合格线。
- 图片体积、格式、文件名、alt、caption；信息图、装饰图、可见图注分别处理。
- 正文链接、目录、面包屑与页脚各自的阅读任务；锚文本与目标页面一致。
- 关键词堆砌、隐藏内容、门页、低价值批量改写和购买操纵性链接等错误做法。

**怎么做**：对 C3 做“需求→现有内容→缺少的证据或步骤→下一步”的修改简报。用 C2 房产与厨房图片演示 alt/caption 的差别；用 C4 的分节与代码样例说明准确结构。修改建议先保存在文稿，不直接写入案例网站。

**AI 运用**：提供真实正文与目标读者，让 AI 标记含糊、重复、缺少依据和未回答的问题；输出每项建议对应的原段落。人判断是否需要修改，不接受无根据的关键词密度或字数目标。

**真实案例**：C2、C3、C4。历史搜索结果用于解释组成；实际搜索展示是否改写，需要另观察。

**练习（英文）**：Revise the supplied title, summary, headings, image description, and one internal link. Explain how each change supports the reader's task.

**产物 / 验收**：一份可实施的页面修改简报：目标任务、标题与结构、两项证据补充、图片说明、内链目标和验证方式；不改既有生产 URL 来追求“漂亮地址”。

**接下一段**：页面内容合理以后，核对搜索引擎实际能取得哪个版本及哪些内容。

原稿对应：27–29、31–33、39–47、75–78 页。

## 第三部分：技术基础——URL、响应、抓取与索引（35 分钟）

这部分所有学员都需要理解；不会写代码也应能看懂证据并向开发者提出明确问题。

### 3.1 地址、请求和响应

- URL 的协议、主机、路径、参数与 fragment；跟踪参数、筛选参数和内容差异不能混为一类。
- GET 与响应头、Content-Type、缓存的基础含义。认识其他 HTTP 方法即可，不在课堂对真实业务发起写入或删除。
- 200、301/308、302/307、401/403、404/410、5xx、soft 404 与重定向循环。
- 打开 Chrome DevTools：Network 看请求状态/响应/跳转，Elements 看 DOM，Console 看相关错误。

### 3.2 抓取、索引与内容保护

- robots.txt 是抓取规则，noindex 是索引指令；内容被禁止抓取时，不能依赖爬虫读取页面内 noindex。
- Sitemap 提供发现线索；提交或请求索引不等于已经索引。
- 私人资料需要认证与访问权限；robots/noindex 不作为隐私保护措施。
- `<a href>` 内链、孤立页面、层级与发现路径；认识 `nofollow`、`sponsored`、`ugc` 的链接关系，不能把它们当作目标页面的索引或权限控制。

依据：[robots说明](https://developers.google.com/search/docs/crawling-indexing/robots/intro)、[noindex说明](https://developers.google.com/search/docs/crawling-indexing/block-indexing)。

### 3.3 Canonical 与结构化数据

- 区分重复内容的首选版本、真正的页面迁移和不同任务页面。
- canonical、站内链接、Sitemap与重定向表达应一致；canonical是信号，不能保证索引或让无关页面变成等价内容。
- 认识 JSON-LD、Microdata、RDFa。按真实页面类型选择 Article、BreadcrumbList、Product、Organization 或 ProfilePage 等；核对当前 Google 支持范围与适用条件。
- Schema Validator 的语法检查、Rich Results Test 的资格检查与实际展示是不同层次。

依据：[Canonical官方文档](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)、[结构化数据通用要求](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)。

**怎么做**：用 C3 入口及章节页记录实际跳转链、最终 URL、title/canonical/robots 与正文；在授权账户有相应资料时再打开 URL Inspection。用 C4 解释“文档主题”和“实际状态”区别；用 C2 的历史 canonical 错误/修正解释同内容版本。没有实际响应证据时不填状态码。

**AI 运用**：给定脱敏响应头、规则与 HTML，让 AI 逐项提出假设和检查路径；每条必须引用提供的字段。AI 看不到 Google 后台时，不能确认索引状态。

**练习（英文）**：Separate availability, crawlability, indexability, and privacy. Record the observed evidence and one next check for each unresolved item.

**产物 / 验收**：检查记录包含请求地址、最终地址、状态/跳转、正文、抓取规则、索引规则、canonical、Sitemap/内链及证据位置。未检查项标未验证；不要把正常退役页面的404一概当成故障。

**接下一段**：响应与规则正确后，还要判断正文怎样到达用户、页面是否真正能用。

原稿对应：2–7、24、34–38、41–43、48、60–61、75–78 页。

## 第四部分：技术基础——渲染、性能、移动端与架构（30 分钟）

### 4.1 CSR / SSR / SSG 与实际交付

- 先理解原始响应 HTML、执行 JavaScript 后的 DOM、数据请求和交互就绪。
- CSR 在客户端组装，SSR 在请求时生成，SSG 在构建阶段预生成；认识水合与缓存的基本作用。
- Next.js 是实现例子；选择框架不等于完成 SEO。Google 能处理 JavaScript，仍需要检查资源、正文与链接取得情况。

依据：[Google JavaScript SEO基础](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。

### 4.2 页面速度与实际体验

- 加载顺序、主内容出现、交互响应和内容位移。
- 当前 CWV：LCP≤2.5秒、INP≤200毫秒、CLS≤0.1；按设备看第75百分位。
- 区分 Lighthouse 实验室诊断、PSI现场数据和实际任务体验；现场数据不足要如实记录。实验室 TBT 不是现场 INP 的同义词。
- 选择一项实际问题解释原因：过大主图、第三方脚本、未预留尺寸、阻塞或失败的资源。

依据：[Web Vitals](https://web.dev/articles/vitals)。

### 4.3 移动端、真机和基础架构

- 响应式、移动端正文/链接一致性、阅读、表格、导航和操作。
- 保留原稿 Safari Web Inspector、Chrome Android 远程调试的方法目的；安装路径按当前官方设备文档准备，旧 Xcode/Genymotion 界面作附录。
- 用原79–80页解释 DNS/CDN/负载均衡/反向代理/服务器/API/数据库的请求路径，以及缓存、慢响应、5xx与部署错误可能发生的位置。明确它是历史架构，不介绍为当前生产架构。

**怎么做**：用 C6 机制图理解三种交付方式，再在 C3 或 C4 实际比较响应、DOM及资源。用 C7 观察加载/位移，不要求读手机帧中的小字。课堂前保存一个真实页面的PSI结果并记录URL、日期、设备和报告类型；结果未知前不填分数。手机用读正文、查表格、打开内链这一具体任务验收。

**AI 运用**：把实际资源瀑布和诊断项交给 AI 整理为“问题→可能原因→验证→修正”，再逐条核对。不能凭 screenshot 或框架名自动断言Google看不到正文。

**练习（英文）**：Compare the response HTML, rendered content, and mobile task. Identify one observed issue and a repeatable verification step.

**产物 / 验收**：一项渲染或体验问题的证据与优先级；能说明修正后要重新检查什么。模拟器与真实手机、实验室分数与现场分布分别标明。

**接下一段**：技术保证内容被取得和使用；内容中关于作者、方法和效果的主张还需要可信证据。

原稿对应：8–14、49–59、62–74、79–80 页。

## 第五部分：E-E-A-T、个人网站与外部声誉的具体实施（45 分钟）

### 5.1 先回答 Google 怎样判断，以及我们能知道多少（8 分钟）

- 用 Experience、Expertise、Authoritativeness、Trust 理解内容质量，信任是关键。
- Google描述的是自动化系统使用多种因素；E-E-A-T不是一个独立排名因素。质量评估员用于评估系统效果，其评分不直接控制页面排名。
- 把“官方说明”“可观察页面证据”“自己的优化假设”分开；不出售所谓Google官方E-E-A-T分数或内部权重。
- 个人网站、作者页、Schema可以承载和描述事实，不能据此保证获得排名。不同主题对经验、专业资格和准确性的要求不同；尤其要识别高风险主题。

依据：[Google实用可靠内容指南](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)。

### 5.2 从四个概念变成实施动作（12 分钟）

| 维度 | 实施动作 | 页面应出现的实际材料 | 怎样核对 |
|---|---|---|---|
| Experience | 记录亲自做过的过程 | 原始截图、步骤、环境、日期、输入/结果、失败与修正 | 材料是否确实来自该次工作，别人能否理解观察范围 |
| Expertise | 展示解释与判断能力 | 原理、取舍、适用条件、代码或方法、重要例外、可靠来源 | 结论能否推导，事实是否正确，资历是否相关真实 |
| Authoritativeness | 整理相关的独立记录 | 他人引用、实际演讲、合作记录、独立报道、真实评价 | 谁发布、何时发布、原始链接、语境及商业关系；自述与独立记录分列 |
| Trust | 让责任和边界可追查 | 准确署名、联系入口、来源、利益披露、实质修订、限制 | 是否存在夸大、假审核、假资历、不可验证数字或与正文不一致信息 |

实施对象包括作者、网站与具体页面。不会要求每篇个人经验分享都找“专家审核”；确需专业审核时，必须真实发生并说清审核范围。

### 5.3 个人网站怎么做才有用（12 分钟）

建议站点结构及职责：

| 页面 | 应放什么 | 与其他页面怎样连接 |
|---|---|---|
| 首页 | 你的主题范围、能提供什么、代表成果和当前实际服务 | 进入About、项目、文章与联系入口 |
| About / 作者页 | 真实身份、相关经历、领域、方法及可核实记录 | 文章署名指回这里；重要经历链接到证据 |
| Projects / 案例页 | 背景、本人角色、做法、产物、依据、限制和日期 | 链到实际作品、代码、文章或获授权外部记录 |
| Articles / 专题内容 | 用户问题、原创解释、第一手材料、来源及范围 | 关联项目、相关主题、作者和有用下一步 |
| Talks / Publications | 真实演讲、活动、出版或公开分享 | 链主办方/原始页面，说明本人实际身份 |
| Contact / Disclosures | 有效联系渠道、业务范围、赞助/合作等必要披露 | 从作者页及有利益关系的内容可发现 |

为每条自我介绍配证据，例如“负责过某项目”应说明本人角色及可公开产物。只有头像、职位、公司Logo和一串形容词，不能替代具体材料。无权限公开的客户数据先脱敏或不用；不能编造评价填空。

**结构化实施**：在符合条件的作者/About页面理解 `ProfilePage` 与 `Person`，文章作者关联同一人物，真实外部身份可用相关链接表达。标记与可见页面一致，避免把所有页面都标成个人档案，也不添加虚构资历。参考：[ProfilePage官方文档](https://developers.google.com/search/docs/appearance/structured-data/profile-page)。

### 5.4 真实案例拆解与修改计划（8 分钟）

打开 C5：先读 About 与披露，再进入一篇经验文章，沿文中的项目/代码链接检查材料怎样支持叙述。观察作者如何交代做法、遇到的问题和边界；不把本人简介当成独立背书，不宣称这些页面结构导致某个排名。

Lightman可在备课时选择一项本人真实项目/授课经历，准备“简历式主张→实际材料→适用范围”对照。当前没有确认个人网站地址，也没有核实整套对外经历，因此不在大纲中伪造个人网站或具体履历。默认公开示例C5已可用于讲解；获得资料后可换成本人案例，不影响知识结构。

**AI 运用**：提供已经确认的身份和项目材料，让AI找出需要证据的主张、缺少的范围及链接；AI不能扩写出未发生的工作、资格、获奖、媒体认可或专家审核。

### 5.5 怎么知道实施有用（5 分钟）

分三层检查：实施层看材料真实、可读且连得起来；读者层用非作者本人检查是否理解身份/依据/限制；表现层记录修改范围与日期，跟踪相关查询、目标页面与有效行动。排名变化受多种因素影响，不能把任何上涨都归为“E-E-A-T提升”。

**练习（英文）**：Choose three claims from the supplied author or project page. Link each claim to evidence, state its limits, and propose one concrete revision.

**产物 / 验收**：三条主张证据记录＋个人网站页面清单；每项任务有材料来源、负责人、缺口、验收方式。能区分本人自述、第一手证据和独立来源。

**接下一段**：这些原始材料也是AI工作的可靠输入；资料不足时应暴露缺口，而不是生成更响亮的说法。

原稿对应：28、30–32 页；个人网站与E-E-A-T实施为补充。

## 第六部分：AI 辅助 SEO 的具体工作方法（20 分钟）

**讲什么**：把AI接入已经理解的SEO任务：需求归类、页面审阅、技术证据整理、主张核验、优化任务草案。重点是输入材料和验证，不教一个万能“SEO提示词”。

**操作流程**：

1. 准备真实查询/正文/HTML/脱敏报告，写清页面目标、当前范围与不能改变的约束。
2. 要求每条发现引用材料中的具体段落或字段；把观察、推测、未知分开。
3. 先做少量建议，人工打开引用、检查代码或材料，再决定实施。
4. 保存原稿、AI建议、人工取舍、最终稿及验证记录。

**课堂AI操作指令（英文）**：

> Review only the supplied page and evidence. Return: observation, evidence location, uncertainty, proposed change, and verification step. Do not invent rankings, traffic, author credentials, search volume, or test results. Mark anything not supported by the input as unverified.

**怎么做**：用 C3 的一小段真实正文及页面任务先审一轮，再让AI根据C4给定事实检查技术表述。逐条核对引用和建议；如果AI工具没有网页访问能力，就只分析实际提供的内容。演示在已获授权的订阅交互中进行；本次备课不通过付费模型API批量生成。

**真实案例**：C3/C4作为输入；C5经验文章可用于讨论“已有专业知识怎样帮助判断AI输出”。不把该作者的开发结果当成SEO效果案例。

**练习（英文）**：Review the supplied AI suggestions. Accept, revise, or reject each item using the original evidence.

**产物 / 验收**：至少一条有依据的采纳建议、一条因证据不足被拒绝/退回的建议。若实际输出没有错误，不人为编造“AI现场犯错”；可另用明确标注的人工编写反例练习。

**接下一段**：使用AI辅助工作，与让自己的内容在AI搜索中出现，是两项不同任务。后一项进入GEO。

## 第七部分：GEO——AI 搜索中的可见性（25 分钟）

### 7.1 理解机制和平台边界（7 分钟）

- SEO与GEO各关注什么；理解检索、来源、生成回答及链接呈现的基本过程。
- 区分被抓取、进入索引/检索库、在回答中被引用、品牌被提及和实际带来访问。
- Google官方AI搜索指南继续以SEO基础为出发点；面向人提供独特材料，保持内容可取得、清楚和有用。[Google AI优化指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)
- 不把llms.txt、特殊GEO Schema或固定“切块字数”讲成Google准入秘诀；其他服务若使用某文件，按该服务资料核对。

### 7.2 核对实际控制与技术条件（6 分钟）

| 平台 / 项目 | 课堂需要认识什么 | 不应混淆什么 |
|---|---|---|
| Google普通搜索 | 抓取、索引、摘要及页面质量 | 页面可打开不等于已索引 |
| Google AI搜索 | Search Console的Search generative AI设置，及其包含/排除/继承关系 | 普通索引规则、AI搜索控制与训练控制不能互相代替 |
| OpenAI搜索与训练 | OAI-SearchBot和GPTBot的用途及独立控制 | 不把拒绝训练解释为拒绝所有搜索用途 |
| 其他AI平台 | 先读该平台当前发布的机器人、索引及报告说明 | Google规则不直接套用到所有平台 |

依据：[Google AI搜索控制](https://support.google.com/webmasters/answer/16908024?hl=en)、[OpenAI官方爬虫说明](https://developers.openai.com/api/docs/bots)。课堂讲解与只读核对，不现场擅自更改网站控制设置。

### 7.3 怎样做内容与观察（9 分钟）

- 从C3/C5选择一个真实问题，检查关键结论、限定条件、原始来源与实际经验是否清楚；将“可改善的表达”与“排名/引用假设”分开。
- 明确比较表的对象、时间、条件与来源；价格、功能等易变事实保留日期和更新责任。提供高质量图像与方法材料，不能只把段落重写成问答就称完成GEO。
- 设计三类观察：信息问题、比较问题、品牌事实问题。每次保留完整问题、平台/模式、日期、地区/语言、回答、链接、是否实际支持相关说法。
- 同一问题多次、跨时间记录，观察引用变化；没有出现一次不能证明长期无可见性，出现一次也不能证明策略成功。不要从一次手工查询算“AI市场占有率”。

**真实案例**：C3与C5可作为被比较的真实内容；模型到底引用谁，只能按实际查询记录。若当前没有授权可访问的搜索型AI或没有保存结果，就演示官方机制与观察表，不编造引用截图。

**练习（英文）**：For each observed AI answer, record the exact query, platform, date, linked source, supported statement, and one limitation of the observation.

**产物 / 验收**：一份平台控制区分表与可重复执行的观察方案；有实际查询证据才填写回答和引用。留3分钟归纳内容/技术/身份中应先修的一项。

**接下一段**：手工观察说明具体场景；持续效果需要结合平台报告和站内行为判断。

## 第八部分：测量、优先级与课程收束（20 分钟）

### 8.1 看对数字（7 分钟）

- Search Console的查询、页面、曝光、点击、CTR与平均排名；站内会话、关键动作、询盘/订单分别定义。
- 区分技术诊断分数、第三方工具估计、实际搜索数据和业务记录。
- 当前Google的Generative AI performance report（Search）主要查看AI搜索曝光与页面/国家/日期/设备等维度；以账户实际可用字段为准。与其他报表可能存在包含关系，不能相加为独立总人数。[报告说明](https://support.google.com/webmasters/answer/16984139?hl=en)
- 看不到报告可能与曝光不足等有关；缺失、隐私隐藏及导出值的语义先核对，不自行当作真实零结果。

### 8.2 从现象形成行动（8 分钟）

| 现象 | 优先检查 | 合格的下一步 |
|---|---|---|
| 页面没有被取得 | 响应、权限、robots、资源 | 复现具体URL和错误，记录修正后同一条件的结果 |
| 有内容但未索引 | 索引规则、版本、内容与状态 | 区分技术阻碍与Google选择，留实际Inspection证据 |
| 有曝光但点击少 | 查询任务、展示类型、标题与摘要 | 选定页面/查询组提出一项修改，保留时间和范围 |
| 有访问但用户没完成任务 | 正文、导航、手机体验、行为采集 | 先检查用户动作是否被正确记录，再定位页面摩擦 |
| AI回答事实错误或引用不准确 | 原始页面事实、外部资料、实际回答证据 | 修正自身错误信息并持续观察；不保证模型立刻改变 |

用C7历史报表说明范围与错误类型，再结合授权脱敏的真实报告教学。当前未取得本场所需GSC/GA4报告；没有数据时只做阅读演示或留空记录，不制造“优化前后增长”。

### 8.3 优先级与收束（5 分钟）

按影响页面/用户、证据确定性、业务重要性、实施成本与依赖排列；先修阻断取得和明显错误，再补内容与证据。每项记录问题、证据、影响、建议、负责人、复核条件和观察日期。

**练习（英文）**：Choose three next actions. For each, state the evidence, expected user benefit, owner, verification step, and what cannot yet be concluded.

**产物 / 验收**：可以交给自己或开发/内容同事实施的三项任务。没有实际索引、引用或业务数据时，不能写成已经提升。

原稿对应：18–19、53、60–61页；事件、AI搜索报告和验证口径为补充。

### 按网站类型补充的基础分支

主课把以下项目放进网站检查清单，选择与学员实际网站相关的一项说明；需要完整操作时使用课后材料，不另造第二套SEO原理。

- **多语言网站**：不同语言页面之间的对应、各自内容与canonical，以及适用时的 `hreflang`。双语页面不应仅因主题相同就全部canonical到一种语言。[Google多语言说明](https://developers.google.com/search/docs/specialty/international/localized-versions)
- **本地服务**：先确认业务模式与Google Business Profile资格，再核对名称、服务信息、地址/服务区域及真实评价。不能因为读者在某城市，就给纯线上项目虚构门店。[Google商家资格与信息规范](https://support.google.com/business/answer/3038177?hl=en)
- **电商**：商品、价格、库存、配送、退货及评价须与实际业务一致；产品页和编辑性比较文章分别检查。结构化数据不创造不存在的交易事实。
- **链接关系**：自然相关引用、广告/赞助链接与用户生成链接分别处理；引用语境与目标页面一致。[Google出站链接属性说明](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links)

## 7. 课后产物模板与验收

### D. GEO观察记录

字段：平台/模式、日期、地区/语言、完整查询、实际回答或截图、引用URL、引用支持的具体说法、品牌提及、来源准确性、重复观察情况、可改自身信息、不能推断的内容。

字段：问题、证据位置、影响范围、优先理由、行动、负责人、完成条件、观察时间、未解决限制。
