## 第 2 部分 · 一个还是多个（7–15′）

### 6 · 过渡（7′）

读出问题：「什么理由，才值得多付一个 Agent 的钱？」

### 7 · 四个站得住的拆分理由（7′）

「拆分只有四个站得住的理由，每个对应一种收益。」

- 「① 能并行的独立工作：六位住户互不依赖，可以同时写。赚的是墙钟时间。」
- 「② 不同的工具或权限：检查员只能读，不能写 Draft。赚的是安全边界。」
- 「③ 专门的上下文：每位住户的记录不用挤进同一个窗口，协调者的上下文保持干净。赚的是注意力。」
- 「④ 少数难步骤要更强的模型：只在难的地方咨询 advisor。赚的是质量，钱只花在需要的地方。」

读绿条：「说不出是这四个里的哪一个，就先别拆。」

### 8 · 站不住的拆分理由（9′）

「再看三个站不住的理由。最常见的是第一个：按职位拆。」

「“护士 Agent”“经理 Agent”“家属沟通 Agent”，听起来很像一个团队。但如果它们用的是同一个模型、同样的工具、同样的权限、同样的数据，那就是同一个模型换了三段 system prompt。没有谁比谁多知道一点东西。」

「公司分职位，是因为人有限制：一个人学不会所有事，也不能同时做所有事。模型没有这些限制。按职位拆，好处一个都没有，成本一样不少：多了转述，多了上下文丢失，出了错也不知道是谁的。」

💬「问大家：这几个 Agent 的工具和权限有什么不同？答不出来，就是同一个 Agent。」

「第二个：Agent 越多越聪明。不会。多一个 Agent 不会多出新知识，只多一次转述，多一次出错的机会。」

「第三个：为了好看的流程图，五个框连成一条线。这是 Workflow，用代码写更好。」

读黄条：「Anthropic 的建议是：先用最简单、可组合的做法，确实需要时才加复杂度。」

### 9 · 拆开以后，多付的是什么（11′）

「拆了以后，账单是这样的。」重点讲 token 一行：

「每个线程都要重新读一遍任务和资料，协调者还要读所有回报。一个 Agent 读一次的东西，拆成六个就要读六次以上。」

其他几行快速带过：延迟、出错的地方、排查、责任。

「收益要盖过这些成本才成立。第 7 部分我们用同一组任务实测，不凭感觉。」

### 10 · 检查点 2（13′）💬

「聊天框打字母，可以多选。」等 30–40 秒。

答案 **B 和 C**。

「A 是按职位拆：“护理总监 Agent”，又是一个名字。B 是权限不同，检查员不能有写权限，这是站得住的理由。C 是上下文放不下，也站得住。D 只有一件事，拆了只会多花钱。想要更可靠，先给工具、加检查、提高 effort。」

## 第 3 部分 · 编排模式（15–27′）

### 11 · 过渡（15′）

读出问题：「拆开以后，谁等谁？」

### 12 · 五种编排模式，一张表（15′）

「五种模式放在一张表里。每一种都按同一个顺序读：它解决什么、必须配什么、CareKind 里长什么样。」

- 「Sequential：后一步依赖前一步，常见的是写完再独立检查。CareKind 里 drafter 写，checker 只读核对，不能改。注意：如果顺序完全由代码决定，那是 Workflow，不需要第二个 Agent。」
- 「Fan-out / synthesis：量大、能并行。今天 demo 的主模式，下一页单独讲。」
- 「Specialization：工具、权限、模型不同才拆，不是名字不同。Checker 只读，用便宜的 Haiku。」
- 「Escalation / advisor：少数难步骤才往上交。往上交有两种：交给更强的模型，叫 advisor，它只给建议；交给人，是因为要有人负责。CareKind 里措辞拿不准问 Opus 5.5，R-106 要不要上报交给 RN。」
- 「Dynamic workflow：规模事先不知道时，由 Agent 写计划、平台去跑。危险在于计划和规模都是模型定的，没有预算就没有上限。今天只有六位住户，demo 里关掉了。」

指最右一列：「W7 第 8 部分我们看过 Google Cloud 的设计模式指南，这一列是它的叫法。有两格写的是“接近”：我们的 advisor 只给建议，不打回重写；dynamic workflow 是 Agent 写计划、平台去跑。」

读黄条：「真实系统常常组合使用。今天的 demo 是 fan-out 加 specialization 加 advisor，再加上交给人。指南里还有 Loop、Iterative refinement 和 Swarm。Swarm 没有中心协调者，Agent 之间直接发消息，成本最高，还可能不收敛。」

### 13 · Parallel fan-out / synthesis（18′）

「展开讲 demo 的主模式：分头做，再汇总。」

「协调者把工作拆成独立的子任务，每个子任务开一个线程同时跑，最后协调者合并、去重、找冲突。」

「什么时候用：子任务互不依赖，数量多，单个读起来很重。」

「什么时候别用：子任务要互相看结果，或者只有一两件事。每派一次活，都要重新交代一遍。」

「CareKind：六位住户，每位一个 drafter 线程。Shift lead 只读回报，不读原始记录。」

### 14 · Agent 之间怎么传信息：发消息，还是共享黑板（20′）

「模式定了，还要决定 Agent 之间怎么传信息。有两种做法。」

「Message passing：协调者发任务，子 Agent 回报。好处是谁对谁说了什么一清二楚，上下文天然隔离。风险是每转述一次就可能走样，而且所有东西都经过协调者，它会成为瓶颈。」

「Shared blackboard：大家读写同一个地方，可以是文件、数据库，或者一块白板。好处是不用层层转述。风险是同时写会冲突，还得管清楚是谁写的、哪一版、过没过期。」

读“必须配”一行：「消息要配契约和固定的回报格式；黑板要配写入规则：谁能写哪一块、要带来源和版本、用完要清掉。」

「CareKind 两种都用了：派活和回报走消息；Draft 存在后台，checker 拿到 draft_id 自己去读。线程之间还共享容器里的文件。」

读黄条：「常见做法是两种混用：消息里只放任务和引用，事实放在共享的记录里。」

### 15 · 经典多 Agent 架构（24′）

「这一页快速过一下。今天讲的这些问题，研究界几十年前就有名字。面试被问到，要能接得上。」

- 「BDI：Belief、Desire、Intention。Agent 有它认为的世界是什么样，有目标，有决定去执行的计划。对应到今天：信念就是工具查到的事实。它会过期，要能追到来源。LLM 不会自己存这些，要我们写进 state。」
- 「Contract Net Protocol，1980 年提出：管理者公布任务，承包者投标，管理者选一个，承包者回报结果。我们的协调者派活就是简化版：roster 是固定的，不用投标。只有事先不知道谁能做、谁更便宜的时候，才需要投标。」
- 「Blackboard，来自 1970 年代的 Hearsay-II 语音理解系统：多个专家读写同一块黑板，由控制器决定下一个谁上。就是上一页的共享黑板，那些写入规则全都适用。」

读黄条：「名字换了，问题没变：谁知道什么、谁来派活、在哪里共享。」

## 第 4 部分 · Agent SDK 与 Managed Agents（27–42′）

### 16 · 过渡（27′）

读出问题：「同一个想法，两种托管方式。」

### 17 · 两条 Anthropic 的路（27′）

「Anthropic 有两条路。Agent SDK 你们在 W7 用过：循环跑在我们自己的进程里。Managed Agents 是今天的 demo：循环跑在 Anthropic 的服务上，每个 session 一个容器，我们只负责回答工具调用、读事件流、设预算。」

挑三行读：循环跑在哪、子 Agent 怎么定义、隔离单位。

读黄条，一定要读：「Managed Agents 是 Anthropic 的 beta 托管服务，不是跨厂商的开放标准。框架会变，我们学的是编排思想。」

### 18 · SDK 里，子 Agent 是一段配置（30′）

时间紧可跳过。

「这是示意代码，课上不跑 SDK 版。子 Agent 就是一个 AgentDefinition，四个字段：description、prompt、tools、model。」

读黄条：「description 写给协调者看，它靠这句话决定派给谁。tools 写给系统看，子 Agent 只能用这些。」「这两句话对 Managed Agents 的 roster 一样适用。」

### 19 · Coordinator、roster、thread（32′）

「Managed Agents 里有三个词，分别对应三个问题：谁决定派活，能派给谁，派出去以后在哪里跑。」

- 「Coordinator：session 绑定的那个 Agent。它会自动拿到派活工具。」
- 「Roster：它能派活的名单，最多 20 个，每一项可以写死版本。」
- 「Thread：每派一次活，就开一个线程，有自己的对话历史、模型和工具。线程之间共享容器里的文件，不共享对话。」

下排三格：「只有一层委派；每个 session 最多 25 个子线程，预算是整个 session 共用的；派活和回报都是事件，我们看得到。」

读黄条：「版本固定的意义在于：子 Agent 改了 prompt，协调者不会在你不知道的时候用上新版本。」

补一句：「大纲里写的是 coordinator。新版 API 的类型叫 `multiagent_20261001`，旧的 coordinator 类型不能跑 workflow。」

### 20 · 协调者的配置（34′）

「这是 demo 里真实的配置。指三处：」

- 「固定版本：roster 里写了 id 和 version。」
- 「`inline_agents` 关掉：不许它临时造一个新的 Agent。」
- 「`workflows` 关掉：不开 dynamic workflow。」

「这三处都是在控制规模，让行为可以预测。advisor 开着，用 Opus 5.5。」

读黄条：「Agent 只创建一次，然后存下 ID。每次运行只引用 ID 和版本。」

### 22 · 刚才那次运行，经过了哪里（40′）

「三栏从左到右走一遍。左边是我们的进程：开 session、设 3 美元上限、读事件流、回答工具调用，15 分钟墙钟上限。中间是 Anthropic 跑的：协调者线程、每位住户一个 drafter、一个 checker、需要时咨询 advisor。右边是 CareKind 后台：查权限、只返回已确认的记录、Draft 幂等、写审计。」

读黄条：「关键在于：子线程的工具调用也会转发到主事件流，带着它的 thread id。所以我们知道是谁在调用，就能按调用者检查权限。」

## 第 6 部分 · 委派契约与汇总（52–59′）

### 29 · 过渡（52′）

读出问题：「子 Agent 什么都不知道，任务里要写什么？」

### 30 · 派活契约：W7 的交接单，反过来用（52′）

「W7 我们讲过交接单：Agent 停下来，把工作交给人，接手的人不用回头问就能开工。今天派活是同一个标准，只是方向反过来：协调者把工作交给子 Agent。子 Agent 看不到对话，任务里没写的，它就不知道。」

左表逐行读：

- 「case：哪位住户、哪个班次。」
- 「context：只给 ID，让它自己用工具去读原件，不要把内容贴进去。每转述一次就可能走样，还多一份 token。」
- 「next_step：要它做的一件具体的事。」
- 「done 和 side_effects 变成回报格式：写了哪份 Draft，还是 NOT COVERED。」
- 「reason_code 变成失败怎么报。不说清楚，失败就会被藏起来，子 Agent 会想办法交差。」
- 「trace_id 变成 observation ids：每一句都能追到来源。」
- 「最后一行是 W7 没有的：能用什么工具、多长时间、多少钱。这些不写在消息里，写在 Agent 配置和我们的代码里，靠系统保证。」

💬 指黄条：「“帮我处理一下 R-102 的情况。”聊天框说说，这条缺了什么？」等 30 秒，挑几条读出来。

「缺班次；不知道“处理”是写还是查；不知道回报格式；不知道失败了怎么报。和 W7 那张差的交接单一样，接手的一方只能从头查。」

指右边：「这是 prompts.py 里要求协调者写的格式，原文是英文。注意子 Agent 的回报本身就是一张小交接单：做了什么、没做成什么、为什么、依据是什么。」

### 31 · 汇总不是拼接（56′）

「协调者拿到回报以后，不是把它们拼起来就完事。正常情况下：每位住户一行；检查员报 ISSUE，保留原 Draft，把问题和条款一起交给 RN；疑似可上报事件只交给 RN，不写结论。」

指最后一行：「重复、矛盾、缺回报，这些都是失败。我们放到第 7 部分一起讲。」

读黄条：「交班表上的每一行，都要能追回到一条记录或一次工具调用。」

## 第 7 部分 · 失败模式与上线以后（59–74′）

### 32 · 过渡（59′）

读出问题：「W7 的每个问题，乘以 N。」

### 33 · 多 Agent 才有的七种失败（59′）

「这一部分把所有失败模式放在一起，这一页是总表，一共七种。逐行读最右一列：怎么解决。错误累积下一页细讲。」

- 「Partial failure：一位住户的系统不可用。不可重试，就列 NOT COVERED，写明原因，其他人照常。」
- 「Duplicate work：两个 drafter 写了同一位住户。协调者汇总时去重；就算去重漏了，后台的幂等键 `resident:shift` 也保证只有一份 Draft。」
- 「Conflicting results：drafter 说没事，checker 说缺项。不悄悄选一个，两种说法都写进交班，交给 RN。」
- 「Stalled thread：一个线程一直不回报。墙钟上限到了就 interrupt，没回报的住户列进 Not covered。」
- 「Runaway fan-out：协调者开了几十个线程。roster 固定，不许临时造 Agent，不开 workflow。」
- 「Error compounding：只读一句，下一页细讲。」
- 「Coordination overhead：协调比干活还贵。判断方法很简单：派活、等待、汇总花的 token 和时间比干活还多，就是拆得太细了。解法前面都讲过：合并成大块，见第 13 页 fan-out；传引用，见第 30 页的契约；说不清好在哪，就退回单 Agent 基线实测，本部分后面会讲。」

读黄条：「重试和幂等 W7 讲过：读可以重试，写要有幂等键，而且键由代码生成。」

### 34 · 错误累积：一个坏输出，污染整条下游（61′）

「这是多 Agent 特有的一个风险。看左边这条链：drafter 把未确认的转写当成事实写进去；checker 读的是协调者的转述，不是原件；协调者把“看起来没问题”汇总成结论。每过一手都更像真的，越往下越难发现。」

「右边是怎么挡。重点讲前两条：每个交接点用代码校验，比如 schema、只认已确认的记录；下游读原件，不读转述。后面几条：独立检查，最好换一个模型；出错就标出来，停下这一支；每个结论都能追到来源。」

读黄条：「CareKind 里，R-102 那条未确认的语音转写在后台就被挡掉了，模型根本看不到。Demo 2 里有对应的测试。」

### 35 · 谁来叫停：四层，都在模型外面（64′）

「四层叫停，都在模型外面：钱，是整个 session 的预算；时间，是我们代码里的墙钟上限；规模，是平台限制：一层委派、子线程有上限、roster 固定；最后是正常结束，协调者交出交班表。」

读红条：「预算只能在创建 session 时加上，之后补不了。到了上限是暂停，不是结束：对话和容器都还在，把上限调高或者取消，它会自动接着跑。但不管你发什么消息，它都不会继续。」

### 36 · 交给人，并且留下记录（66′）

「这是审计日志的示意，一次工具调用一行。第一行是失败：R-103 的系统不可用。第二行是交给 RN：R-106，带着理由和观察 ID。」

读黄条：「每一行都知道是哪个 session、哪个线程、哪个 Agent。被拒绝的调用也要记。出了事，要能拼回谁在什么时候、根据什么、做了什么。」

### 37 · Demo 2：失败场景写成测试（68′）▶

切到终端：`uv run pytest -v`。几秒钟，不调 API。

「这些测试不调用模型，每次结果都一样。」照着测试名念：「权限、重复、部分失败、未确认的事实、AI 不下结论。」

「这就是真实项目的做法：失败场景写成测试，每次改代码都跑。」

### 38 · 怎么证明拆了更好（71′）

「方法：同样的工具和模型，只换架构，single 对 team，一位住户和六位住户各跑一遍。」

「质量只用代码检查，不让模型打分：每位都有 Draft 或者列进 Not covered；R-103 没被编造；R-106 和 R-104 交给了 RN；没用未确认的转写。」

如果表格还是“待实测”：「数字要课前跑 `eval_compare.py` 才有。我不口头编数字。」

如果已经填了数字：读一位住户和六位住户两组的差别。

### 39 · 收益要盖过成本，Multi-Agent 才成立（73′）

「三个问题：质量有没有更好？并行省下的时间，比派活和汇总花掉的多吗？多出来的 token、线程、审计和排查，团队负担得起吗？」

读绿条：「答案取决于任务的形状。同一个系统，一位住户和六位住户，可能该用不同的架构。」如果实测里一位住户时 single 更便宜、更快：「这正好说明了这一点。」
