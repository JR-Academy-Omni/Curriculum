## 1. 规则仓库怎么写

### 1.1 一条规则的最小完整形态（五要素）

从参考系统里所有"真的在起作用"的规则反推，每一条都有这五样。缺任何一样，那条规则就只是一段文字。

| # | 要素 | 反面例子 | 正面例子 |
|---|---|---|---|
| 1 | **断言** 一句可以被反驳的话 | "我们要重视代码质量" | "建记录和改记录不是同一种行为" |
| 2 | **标记 + 日期** confirmed / proposed / to supply | "SLA 大概一天吧" | "`[proposed]` 1 个工作日，待批" |
| 3 | **权威归属** 哪份文件是这条规则的唯一出处 | 三个文件都写了，版本不同 | 一处写，其余指向 |
| 4 | **触发条件** 什么时候适用 | "必要时需要审批" | "五个触发器，一个都不中就自己决定" |
| 5 | **强制点** 谁或什么会挡住违反 | 无 | CI / 分支保护 / hook |

**要素 5 是全节的枢纽。** 前四个学员写完会很有成就感，然后两周后没人遵守，因为第五个是空的。

### 1.2 文件只有四类，第四类不进这个仓库

| 类 | 例 | 变化频率 | 进规则仓？ |
|---|---|---|---|
| 指令文件 | `AGENTS.md` / `CLAUDE.md` | 低 | 是 |
| 权威文件 | `governance/*` | 低，改动要批 | 是 |
| 结构文件 | `roles/` `sops/` `templates/` `schemas/` | 中 | 是 |
| **状态文件** | 日更、工单、报告、会议记录 | **每天** | **否** |

第四类进了规则仓，整个系统就废了。原因见 §2.1。

### 1.3 每类文件的固定节（固定节的真正价值是"能被脚本检查"）

| 文件类型 | 固定节 |
|---|---|
| SOP | owner · trigger · scope · roles · inputs · steps · outputs · acceptance criteria · exceptions · escalation · evidence · version · review date（13 节）|
| 角色 charter | accountable outcomes · authority boundaries（再分"独自决定"/"必须报批"）· dependencies · exclusions · metrics · escalation（6 节）|
| AI skill | trigger · 数据源 · 必需输入 · 输出结构 · 具名审批人 · 写操作白名单 · 失败重试 · 审计 · 隐私边界 · 验收测试（10 节）|
| 人员文件 | 7 节，**顺序固定**，脚本逐节校验 |

> 固定节不是为了好看。
> **自由格式的文件不可能被机械检查，也就永远停在强制力第 0 级。**
> 参考系统的校验脚本能检查人员文件，正是因为它的 7 节顺序是死的。

### 1.4 三标记，且绝不编造

```
[confirmed]  锁定，来自源文档或用户当面确认，并标日期
[proposed]   待签字的建议
[to supply]  还没有人提供
```

铁律：**绝不用合理的猜测去填 `[to supply]`。**

> 空着的缺口是信息。编造的值是一个看起来像进展的缺陷，
> 而且更糟，因为它让所有人不再追问。

参考系统的 CI 会数出当前有多少个未填缺口，贴在每次 PR 摘要里，并附一句"这是故意的"。
**把缺口计数做成 CI 输出，是让"诚实"变成可维护的唯一办法。**

### 1.5 权威优先级必须写在文件里，且必须是全序

参考系统在四个地方声明了冲突裁决：

| 声明位置 | 规则 |
|---|---|
| `AGENTS.md` | 与 `governance/` 冲突时，`governance/` 赢 |
| `governance/README.md` | 与 charter / SOP / template 冲突时，本目录赢 |
| `docs/HANDBOOK.md` | 与详细文件冲突时，**详细文件赢**（手册是摘要，摘要会漂移）|
| `AGENTS.md` | 已确认上下文与花名册冲突时，**花名册赢**（前者是原始设计，后者是今天谁戴什么帽子）|

合起来构成一个确定的顺序：**治理 > 角色/流程/模板 > 手册**，横向另有"花名册 > 历史上下文"。
任意两份文件打架，都有确定答案。

### 1.6 反面：参考系统自己漏了一格，代价可查

`AGENTS.md` 只规定了"与 `governance/` 冲突"的情形。
但有一次冲突发生在 `AGENTS.md` 和一份**角色 charter** 之间，而 charter 在 `roles/` 下，
**那条裁决规则够不着这个组合**。

后果被原样记录下来：

> "某时点该仓库的每一个 PR 都是自己开、无人批准、自己合并，11 个里 11 个。
> 在第一种读法下这是正常运行，在第二种读法下这是 11 次违反控制。
> 而必需审批人数配置为 0，所以无论哪种读法，都没有任何东西会把差别暴露出来。"

**教学结论：优先级表必须覆盖所有目录，不能只覆盖一部分。**
漏掉的那一格，就是将来那场事故的位置。

### 1.7 冲突的正确处理：不删，补范围

参考系统遇到两条相隔一天、互相矛盾的 `[confirmed]` 规则时的做法：

1. 两条**都不删**
2. 补一条**范围限定**，让两条同时成立（"合并审查覆盖产品仓库，不覆盖运营仓库"）
3. **把矛盾期间的后果写出来**（上面那段 11/11）
4. 注明"这条范围限定本身不该由写它的那顶帽子自批"，指明需要谁追认

> 删掉一条的代价：将来没人知道为什么会有过那条规则，同样的冲突会再发生一次。

## 2. 怎么分：三刀

### 2.1 第一刀：按"变化速度 + 谁能写"分仓，不按主题分

**学员默认会按主题分（工程规范 / 销售流程 / HR 制度），这是错的。**

正确的切分依据是三个问题的答案：

| 问题 | 规则仓 | 记录 |
|---|---|---|
| 改一次要不要审？ | **要** | 不要 |
| 改错了多久能发现？ | 可能几个月 | 当天 |
| 写它的人会不会 git？ | 会（少数人）| **不一定**（所有人）|

三个答案不同，**它们对分支保护的需求就是相反的**：

| | 规则仓 | 记录 |
|---|---|---|
| 写权限 | 极少数人 | 全员 |
| main 强制 PR | **开** | **故意不开** |
| 理由 | 规则要慢、要审、要可回溯 | 一开，网页端提交就被迫走 PR，不会 git 的同事那条路就废了 |

> 参考系统明确算过这笔账：
> 更严格的方案（每篇日更走一个 PR）被**考虑过并否决**，
> 理由是"它会毁掉这个闭环赖以存在的九十秒提交，而且有两顶帽子根本没理由装 git"。

**把规则和状态塞进一个仓库，是这类系统最常见的死法。**

### 2.2 第二刀：仓内按"权威高度"分层，不按部门分

| 分法 | 跨部门的规则放哪 | 两份文件冲突怎么办 |
|---|---|---|
| 按部门（工程/销售/HR）| **没地方放** | **无解** |
| 按权威高度 | 放最高层 | **自动有解**（§1.5 的全序）|

权威高度从高到低：

```
governance/   谁决定、谁批准、什么禁止      ← 声明自己最高
roles/        每顶帽子答应什么、能定什么
sops/         活怎么干（必须有 trigger）
templates/    重复填的结构
schemas/      字段合同
```

### 2.3 第三刀：规范与可执行分离

| | 放什么 | 回答什么 |
|---|---|---|
| `ai-skills/<name>.md` | 规范 | 为什么有这条规则？什么被禁？谁批的？ |
| `.agents/skills/<name>/SKILL.md` | 可执行技能 | 做什么、什么顺序、用哪条查询 |

连接方式：`.claude/skills/` 用**相对符号链接**指向 `.agents/skills/`，**只有一份拷贝**。

**课堂必须给降级方案**（Windows / 不支持 symlink / 网页端）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A symlink | 参考系统的做法 | Windows 需开发者模式或管理员 |
| B 单目录 | 直接把技能放 `.claude/skills/`，规范文件在旁边指过去 | 少一层通用性 |
| C 构建步骤 | 一条 `cp` 脚本 + CI 校验两边一致 | 多一个会忘记跑的步骤 |

B 是课堂默认。A 作为进阶展示。**C 要明确说它比 A 差在哪**：它把"单副本"变成"两副本 + 一条检查"。

### 2.4 目录准入测试（决定一个新文件该放哪）

学员建第 20 个文件的时候就会迷路。给他们这张表：

| 问自己 | 答"是" → 放这里 |
|---|---|
| 这条被违反时，有人有权说"不行"吗？ | `governance/` |
| 这句话在描述一顶帽子**答应什么**？ | `roles/<帽子>/charter.md` |
| 这句话在描述一顶帽子**每天干什么**？ | `roles/<帽子>/responsibilities.md` |
| 这个流程有 trigger 吗？ | `sops/` |
| 没有 trigger？ | **它不是 SOP，是文档** |
| 这是每次重复填的结构吗？ | `templates/` |
| 这是字段定义吗？ | `schemas/` |
| 以上都不是？ | **它多半是状态，不属于这个仓库** |

## 3. 权限怎么隔离

### 3.1 四个层次，学员只想到第一个

| 层 | 控制什么 | 参考系统的配置 |
|---|---|---|
| 1 **写权限** | 谁能 push | 规则仓 2 人；记录全员 |
| 2 **分支保护** | 有写权限的人**能做什么** | 规则仓强制 PR + 禁 force push + 管理员也受约束；记录只禁 force push 和删分支，放行普通 push |
| 3 **决策权** | 谁能**批准改这条规则** | 审批矩阵，按帽子不按人 |
| 4 **读权限 / 数据边界** | 谁能看到什么、什么不许入库 | 数据处理规则 + 个人数据不入库 |

**四层互相不等价，最典型的证据：** 规则仓写权限只有 2 人，
但**改规则的提案路径根本不走 PR**，走周会。见原则 1。

### 3.2 原则 1 · 写权限窄，提案路径宽

参考系统的原文理由：

> "要改变我们怎么运作，在周会上作为 SOP 变更请求提出。
> 这条路径**刻意是一场对话而不是一个 diff**：被规则约束的人不都是 git 用户，
> 而要求用 PR 才能质疑一条规则，等于**按工具而不是按价值过滤提案**。"

**代价也要讲：** 规则演进的吞吐量因此绑在一次周会上。
团队规模不同，这个选择不能照抄，要教**判断依据**：

```
你的规则使用者里，不用 git 的占比是多少？
> 一半  → 提案路径必须离开 git
< 两成  → PR 提案可以接受，但要有一条非 git 的兜底
```

### 3.3 原则 2 · 分支保护是一组独立开关，不是一个"越严越好"的滑块

这是本节**课堂价值最高**的一格。

参考系统记录的配置看起来自相矛盾，实际上是精算过的：

| 开关 | 记录 | 为什么 |
|---|---|---|
| 强制 PR | **关** | 一开，网页端提交路径就废了 |
| 禁 force push | **开** | 归档必须不可改写 |
| 禁删除分支 | **开** | 同上 |
| 管理员也受约束 | **开** | "两个最有能力改写历史的人能绕过去的保护，不算保护" |
| 普通快进 push | **放行** | 这是日常流程本身 |

原文把这个取舍写得很清楚：

> "什么必须变得不可能：**无痕地抹掉或改写已提交的内容**。
> 什么仍然可能：**通过追加来更正它**，这样两个版本都活着。
> 为什么不干脆禁止修改：那会让每篇日更付出一个 PR 的代价。"

**教学动作：** 让学员当场列出自己那条规则的五个开关分别该开该关，并说出每一个的理由。
不许写"全开"。

### 3.4 原则 3 · 职责分离要能抵抗"一人多帽"

小公司必然一人多帽。参考系统的做法**不是假装没这回事**，而是四步：

**a) 把冲突写进文件。** 同一个人既批准 AI 写权限、又建造 AI 写权限，
这个冲突在**五个不同文件**里被重复记录。

**b) 对最危险的那一类，把批准人上移一级。**
"第一次启用 AI 自动写"由 **CEO 追认**，不由 CPO 自批。

**c) 缺席代理必须不对称。** 这是最容易被漏掉、也最值钱的一格：

| 方向 | 效果 |
|---|---|
| CPO 不在 → CEO 代 | 干净。没有任何东西是为了被 CPO 以外的人检查才路由给 CPO 的 |
| CEO 不在 → CPO 代 | **必须挖三个口子。** 否则 CPO 获得了"本来用来制衡 CPO"的权限 |

**d) 明确哪些事"等人回来"，不转授。** 三类：
第一次启用 AI 写权限 / 自己提出或拥有的风险接受 / 任何自己是交易对手方的决定。

原文的结论值得原样讲：

> "单点故障是**移动**了，不是消失了。
> 除了两顶帽子被刻意对立的那些情形，覆盖是存在的，而那些情形仍然会在 CEO 不在时停下来。
> **这是正确的结果**，另一种选择是一个悄悄溶解职责分离的代理制度，
> 但它应当被读成一个已知的限制，而不是完整覆盖。"

### 3.5 身份数据隔离：合规和可用的真实两难

参考系统的选择：GitHub handle、工作邮箱、聊天 ID、工单账号 ID **都算个人数据，不进这个仓库**。

后果是真实的：

- 所有依赖身份映射的自动化**全部阻塞**
- 权限漂移检查只能**数个数**，不能说出是谁

但这里有个反直觉的收获，值得做成一页：

> **限制逼出了更强的检查。**
> 因为不能按人查，脚本改成查策略不变式，比如
> "**一个不是组织成员的协作者**"，
> 不需要任何人知道那是谁，就能抓到一条离职残留的授权。

其他同类的"不需要身份就能查"的不变式（可直接抄）：

```
在职人数 vs 组织账号数           不一致就报，谁缺账号让人去查
规则仓可推送人数 == 约定的 N      多一个就是漂移
规则仓 main 保护三项配置          读出来跟期望值逐项比
记录可写人数 == 组织账号数      少一个就有人交不了日更
记录 main 保护                  存在即是漂移（它故意不该有）
仓库协作者 ⊆ 组织成员             组织移除不会清掉仓库级授权
外部协作者数 == 0
久未接受的邀请                    未接受的邀请不携带账号，人仍然拿不到权限
```

### 3.6 访问登记册：列定义在库里，行不在库里

参考系统踩过的坑原样记录：

> "第一版这个文件**自相矛盾**：它印了一张空表，同时又禁止任何人去填。"

正确切法：**列定义（schema）进规则仓，行（数据）不进。**

| 列 | 内容 |
|---|---|
| 系统 | 一个系统，**绝不是一个列表** |
| 人 | 通过身份目录解析，不在这里写成标识符 |
| 访问路径 | 门户 URL，或邀请发到了哪里 |
| 权限级别 | **用持有人能据以行动的大白话写** |
| 授予方 | 帽子 |
| 授予日期 | |
| 移除日期 | 留空，直到离职流程走到它 |

### 3.7 离职要回答的是**反问题**（这张表学员当场能用）

> 授权登记册回答的是"我们给过这个人什么"。
> 离职需要回答的是相反的问题："**这个人可能还在哪里有权限**"。
> 而后者**无法从授权行重建**，因为**你只能移除你记得存在的东西**。

所以登记册必须配一张**系统清单**，离职时**走清单，不走行**。
最容易漏的类（脱敏保留，原因逐条给）：

| 类 | 为什么容易漏 |
|---|---|
| 身份提供商 / SSO 门户 | 用户名就是公司邮箱，除非停用账号否则权限一直活着。**移除应用权限不等于移除 SSO 权限** |
| 通过 SSO 进的云控制台 | 从门户进去的，不是按人授予的，所以它在任何授权记录里都不出现 |
| 代码组织 + 仓库级协作者 | **组织移除不会清掉仓库级协作者，也不会清掉待接受的邀请** |
| 邮件组 / 分发列表 | 一个受限发送列表就是一项权限。残留成员能群发全公司 |
| 共享盘里给了**管理/编辑**权的文件夹 | 共享是加在文件夹上的，按文件审计时看不见 |
| 周期性日历邀请 | 是对会议、会议链接和会议记录的长期权限，在未来的场次上继续存活 |
| 聊天工作区（含私有频道） | 成员资格跟邮箱和 SSO 是分开的 |
| 财务 / 薪资系统 | 持有人少，所以没人想起来查 |
| 工单 / 知识库账号 | 常常跟身份系统分开计费 |
| 客户侧系统 + 共享凭据 | **共享凭据无法按人撤销，只能轮换** |

> **先停用身份账号是单步价值最高的一步**，因为上面多数行都通过它认证。
> 但它不充分：共享凭据、仓库级授权、外部系统会活得比它久。

## 4. 硬政策：怎么保证一定会执行

### 4.1 强制力阶梯六级（全节最重要的一张图）

```
L6  服务端拒绝 + 管理员也受约束     连最有权限的人也绕不过去
L5  分支保护                        有写权限的人绕不过去
L4  CI 挂进 PR                      红了合不了  ← 第一道真正的硬政策
─────────────────── 上面是硬政策，下面是约定 ───────────────────
L3  本地校验脚本                    要人主动跑
L2  SessionStart hook               每次会话提醒，可以被忽略
L1  写进 AI 指令文件                AI 会读，但可以不照做
L0  写在文档里                      靠人记得。默认失效
```

**每条规则都要标自己在第几级。** 大多数公司的 SOP 全部停在 L0。

参考系统自己的诚实记录，正好是 L3 和 L4 的分界证据：

> L3 阶段："**在开 PR 之前跑一下校验脚本。目前没有任何东西自动跑它。**"
> 升到 L4 时的 commit 说明："这让 PR 这道关卡**成为一次真正的检查，而不只是一条记录**。"
> 触发原因："**有四个 PR 在自己的描述里说了这件事。**"

### 4.2 什么能机械化，什么不能（升级转化器）

| 能（形状）| 不能（判断）|
|---|---|
| 存在性：每顶帽子都有 charter 和职责文件 | 这顶帽子的权限划分对不对 |
| 唯一性：单人帽子恰好一个持有人 | 这项职责该归帽子还是归人 |
| 格式：人员文件 7 节且顺序固定 | 这个阈值合不合理 |
| 引用完整性：被引用的文件都存在 | 这条 SOP 的步骤是不是真的可执行 |
| 反向引用：存在的文件都被索引引用 | |
| 派生值没被手写第二遍 | |
| 禁用词：某小节里不许出现个人标识符 | |
| 状态一致：标了 approved 的文件不许残留未填缺口 | |

参考系统明确写了这条边界，而且**拒绝假装**：

> "任何需要判断的事：一份 charter 的权限对不对、一项职责该归帽子还是归人、
> 一个阈值合不合理。**那些需要人，而校验器刻意不假装能做。**"

**学员的动作：** 把自己写的规则逐条过一遍，凡是落在左列的，**当堂写成检查**。

### 4.3 写一个校验器的实战规格

从参考系统的脚本里抽出来的骨架，可以直接给学员：

```bash
#!/usr/bin/env bash
set -uo pipefail
cd "$(dirname "$0")/../.." || exit 1

fail=0
hdr()  { printf '\n%s\n' "$1"; }
bad()  { printf '  FAIL  %s\n' "$1"; fail=1; }   # 硬失败
note() { printf '        %s\n' "$1"; }           # 只提示，不失败

# ... 检查项 ...

exit "$fail"
```

四条设计规格，每一条都有代价：

**规格 1 · 硬失败和提示必须分开。**
不变式失败 → `exit 1`；"计划中的文件还没建"、"缺口分布" → 只打印。
> **这是校验器能活下来的关键。** 全部当失败 = 天天红 = 没人再看它。
> 参考系统的原话："一顶没人戴的帽子是一次失败的不变式，不是提示性输出。"

**规格 2 · 检查项从"已经发生过的错"来，不从想象来。**
> "第一次自动运行**就立刻发现一顶帽子没被登进它自己的索引**。"

**规格 3 · 检查"人做了什么动作"，不只检查"值对不对"。**
例：参考系统专门抓"有人在个人文件里手写了产能占比"这个**动作**，
因为那个值本该从工时推导。值可能碰巧是对的，动作仍然是错的。

**规格 4 · 检查禁用词。**
例：某小节里不许出现邮箱格式的字符串，因为那类映射必须存在外部目录。

### 4.4 现场教材：它自己漏掉的那条检查

**这是 L13 第四幕最好的动手环节。**（做课件时用虚构名字重现同一个场景。）

参考系统的铁律之一：

> **"角色文件从不写人名。"**
> 理由：一个人离职只动一个文件。
> 治理目录也重申过：**"审批行写帽子，绝不写人。"**

**而它的一份治理文件里出现了 6 处真实人名。校验器没抓到。**

这条规则 **100% 可机械化**，一行就够：

```bash
# 花名册里的人名，不许出现在 governance/ 和 roles/ 下
for n in $(roster_names); do
  grep -rilE "\b$n\b" governance/ roles/ && bad "「$n」出现在规则文件里，应改为帽子"
done
```

**课堂动作：** 当场写这一行 → 跑 → 红 → 修。
**这就是 L0 规则和 L4 规则的差别，用一个真实系统自己的仓库演示出来。**

呼应参考系统自己写下的那条铁律（它自己违反了）：

> "**禁令约束你写的东西，不只是你做的事。**
> 在一个文件里写下禁令、又在另一个文件里违反它，是完全可能的，这里已经发生过一次。"

同类的现成反例还有一个：全库声明"只用英文"，但校验脚本输出是中文，
指南只好补一句"看退出码，别看最后一行的措辞"，
并把"这条规则管不管工具输出"标成未决。

### 4.5 分支保护必须被"试"出来，不是"读"出来

参考系统的验证方式：**开一个一次性分支，配上相同设置，真的去做三个动作。**

| 动作 | 期望 | 实测 |
|---|---|---|
| 强推、回退分支 | 拒绝 | **被拒**："Cannot force-push to this branch" |
| 删除分支 | 拒绝 | **被拒**："Cannot delete this branch" |
| 普通快进 push（日常流程）| **必须成功** | **成功**，as it must |

**第三行和前两行一样重要。** 只测拒绝不测放行，等于可能把日常流程也锁死了，
而且要等到第一个同事交不了日更才会发现。

并且记录了一个看起来像通过、实际不是的测试：

> `git push --dry-run` **不是这个的测试**。
> 它报告客户端**会发送什么**，根本到不了服务端钩子，
> 所以对一个实际上会拒绝这次推送的分支，它返回成功。
> **记录下来是因为它看起来像一次通过的测试，而它不是。**

还要写清楚分支保护**盖不住**什么，免得被当成比它更多的东西：

- **删除整个仓库**：组织级动作，完全在分支保护之外
- **谁持有写权限**：保护约束的是"有写权限的人能做什么"，不是"该不该是这些人有"

### 4.6 硬政策的三个反模式

**反模式 1 · 把人工审批当作保障。**

参考系统的论证很反直觉，值得整页讲，三条理由，第三条是被测量到的：

> 1. **那个按钮从来就不是控制点。** 文件早就记录了这些仓库不要求审批、也没有自动检查。
>    一次为了等人而扣住的合并，增加的是延迟，不是审查。
> 2. **它不是一次审查。** 没有人在读这些 PR。
>    **一个被执行、却从不被真正行使的步骤，会训练所有人把它当成形式，这比没有它更糟。**
> 3. **被扣住的合并会让仓库说谎。** 一个 PR 挂了三天，
>    在那三天里记录的技能文件写着"只起草，不发送"，
>    而 agent 正在依据一份**已经合并**的授权在发送。
>    **那次延迟什么也没阻止，它生产了一份有据可查的自相矛盾。**

结论：

> **真正起作用的限制不在谁按合并键，而在一项批准立在什么上面。**
> 后者读者可以核查，按钮不能。

**反模式 2 · 检查全是硬失败。** 见规格 1。

**反模式 3 · 只测拒绝，不测放行。** 见 §4.5 第三行。

### 4.7 一节课能做完的交付顺序

| Step | 动作 | 达到 | 当堂证据 |
|---|---|---|---|
| 1 | 写一条规则 + 一句断言 | L0 | 念给同桌，对方能照做 |
| 2 | 写进 `AGENTS.md`，`CLAUDE.md` 只放指针 | L1 | 问 agent"这件事谁批"，答对 |
| 3 | 写 3 到 5 条不变式的 `check.sh` | L3 | **当堂跑出一个 FAIL** |
| 4 | 挂进 CI，提一个违规 PR | L4 | **PR 被挡住，红的** |
| 5 | 开分支保护，三个动作实测 | L5 | 两拒一放，逐条截图 |
| 6 | 打开"管理员也受约束"，用管理员身份再试 | L6 | 仍然被拒 |

**Step 3 到 Step 5 是本节高光。**
从"我跟它说过"到"它绕不过去"，与 L12《Claude Hook》同源的立论，
但对象从一个 agent 换成了**整个团队**。

## 5. 需要讲师拍板 / 需要先验证的

### 5.1 必须先验证（我不能凭记忆断言）

**V1 · 学员的 GitHub 账号能不能开分支保护。**
私有仓库的分支保护历史上跟付费计划相关，规则集（rulesets）推出后的当前策略我**不确定**，
**必须实测后才能写进蓝图**。这直接决定 Step 5 和 Step 6 能不能做。
如果免费账号不行，备选：公开仓库演示 / 组织试用 / 改用服务端 hook 演示同一个概念。

**V2 · 国产平台的等价能力。**
Gitee / Coding / 自建 GitLab 的分支保护、必需检查、管理员豁免，
各自能到第几级，需要逐个确认。这是系列惯例里"用不了 Claude Code 怎么办"那一页的对应物。

**V3 · Windows 学员的 symlink 路径。** 决定 §2.3 用 A 还是 B 当课堂默认。

### 5.2 需要你拍板

**Q7 · 一节课做到第几级？**
做到 L4（CI 挡住 PR）已经是绝大多数公司没有的东西，且不依赖仓库 admin 权限。
L5/L6 更震撼，但依赖 V1 的结果。
我倾向：**L4 必做，L5/L6 作为演示 + 课后作业**。

**Q8 · §4.4 那个"它自己违反了自己的规则"的教学环节，用什么素材？**
(a) 完全虚构一个示例公司，重现同一个场景
(b) 用脱敏后的真实片段
我倾向 (a)，因为这个环节要让学员当场 grep 出人名，用虚构名字更干净、也更安全。

**Q9 · §3.4（一人多帽的四步处理）要不要占独立一幕？**
它是小团队学员最会遇到、也最没人教过的东西，但它偏组织治理，不偏编码。
放进去会让课程更有价值，也会冲淡"完整的代码和部署"这个产物承诺。

**Q10 · §3.7 那张离职系统清单要不要发成独立讲义？**
它跟 SOP 系统本身关系不大，但学员当天就能用，是个很强的"这节课值回票价"的物件。
