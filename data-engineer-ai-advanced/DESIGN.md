# AI 数据工程实战课 · 高级班 — 设计说明

> SoT：课时、步骤、时长、价格只写在 public/outline.json；销售页是 public/curriculum.html，海报是 public/poster.html，画像是 PERSONAS.md。本文件记录定位、决策、AI 关系、证据、环境、任务组、翻车点和待核实项，不复述大纲。slug 由旧的 data-engineer-ai-foundations 改名而来。2026-10-11 课程内容整体重写，见决策记录第 9 条。

## 定位

- **学员**：在职数据工程师、分析工程师。已有 SQL、Python、dbt 基础，在一个数仓里建过表，用过 Git 和 Pull Request。
- **他们的处境**（写成情境，不是数据）：上级要 AI 提效；安全团队担心 Agent 碰 prod 和 PII；自己用 AI 写 dbt，有时一次就对，有时把指标口径悄悄改错；团队里没人说得清它到底靠不靠谱。
- **他们买什么**：10 小时里，把一条自己这一类的数据工作流交给 Agent，在受控的前提下跑起来；带走自己测出来的数字，和一页能拿去给上级和安全团队看的方案。
- **主线**：AI-native 运营模式。AI-native 不是「干活时顺手用 AI」，就像 cloud-native 不是「把虚拟机搬上云」。它是把工作重新设计成由 Agent 执行，工程师负责 Agent 外围的五件事：
  1. **意图**：任务写成「要什么 + 怎么算做完」，而不是手写实现。
  2. **上下文**：团队约定、架构、运行手册写成 Agent 读得到的形式（规则文件、skill、文档）。没写下来的知识，对 Agent 来说不存在。
  3. **验证**：生成很便宜，确认它对才是瓶颈。测试、策略检查、计划审查、对账是 Agent 必须一直跑到通过的闸门。
  4. **身份与边界**：Agent 是一个有身份的执行者，最小权限、审批、审计记录、停止开关。
  5. **度量**：Agent 成功率、人工干预率、每任务成本、每任务耗时；每次失败的复盘写回上下文。
- **这五件事的说法是本课作者自己的归纳，不是行业标准术语。** 销售页和课上都这样说明，不包装成「业界公认框架」。
- **形态**：Lightman 本人独自授课。5 节直播，每节 120 分钟，加 30 分钟课前准备（L00，不直播）。满 15 人开班，同一时间只开一个班。价格 $599 含 GST。报名入口待开通。
- **每节课结构**：第一步 LIVE「先看终点」10 分钟；CONCEPT 最多 8 分钟，写成清单，马上用；每节至少 100 分钟动手；每节都有一步重跑任务组；最后一步 PROJECT，描述以「带走：」开头。
- **不是什么**：不是 AI Engineer 转职课；不教模型训练、部署、RAG；不是 Claude Code 或任何工具的功能巡礼；不承诺工作、薪资、升职、签证或收入。

以下是旧版本（合成文档抽取管线）留下的决策，标明现状：

1. 2026-10-11 项目由「交通视频加网页爬虫」换成「合成文档抽取」。**已被第 9 条取代**：文档抽取也离开了本课。交通视频只作为可能的免费公开课演示，这一点仍然有效。
2. 删掉 Spark 和 YOLO。**仍有效**。
3. 编排用最简单的方式，不以 Airflow 为主线。**仍有效**，现在的理由是：闭环的触发放在 CI（GitHub Actions）或云端 Agent 上，不需要另一套编排器。证据说明：中高级广告里没有统计 Airflow，所以不能说「市场不要 Airflow」。
4. 仓库用 DuckDB 本地跑，不要求云账号。**仍有效**。代价：DuckDB 没有行列级权限，L03 用只读挂载加脱敏视图实现边界，并讲清在真实数仓里对应什么机制。
5. AI 的两个身份（写管线的队友、管线里的抽取部件）。**作废**：抽取部件随文档抽取一起离开；现在 AI 只有一个身份，即执行者。
6. 「拿掉 AI 会不会变慢、拿掉领域知识能不能做对」两个检验。**改写后保留**：前者现在由任务组的实测数据回答，后者体现在每节课「你要能判断」一栏。
7. 确定性检查脚本不调用模型。**仍有效，并扩大**：所有验收脚本、对账、标准答案比对、数据差异、度量计算都是普通脚本，可重复，零额外模型费用。
8. 数据全部合成，不用真实公司或个人数据，PII 也是合成值。**仍有效**。
9. **2026-10-11 课程按 AI-native 运营模式整体重写。** 原因：Lightman 否定了此前由其他模型做的分析，要求高级班面向在职从业者推广。在职者要回答的问题不是「怎么用 AI 做某个新项目」，而是「怎么把团队已有的活交给 Agent，并且让上级和安全团队放心」。所以：
   - 全课只改造一条工作流（本地合成电商数仓上的日常数据工作），由 5 个固定任务代表，第一节课跑基线，每节课后重跑。
   - 工具（hook、skill、子 Agent、云端 Agent、OpenTelemetry 或 Langfuse、Bedrock）只在能提高成功率或守住边界时出现，不做巡礼。
   - **离开本课的内容**：PDF、发票、合同、邮件的文档抽取管线；抽取置信度和原文引用校验；RAG 数据准备（脱敏切块、检索）。它们可能成为将来的另一门课。交通视频的想法只保留为公开课演示。
   - **不当卖点**：MCP 和 text-to-SQL。数据工程 JD 样本里两者都是 0 条。只读数仓访问用通用说法描述，不点名某个协议。
   - **数字规则**：销售页、海报、大纲不出现任何成功率、节省时间或成本数字。L01「先看终点」里授课人课前跑出的曲线目前**待实测**，跑出来之前不得引用。
   - 用任务组测成功率和干预率的方法是本课自己的设计，不是 JD 要求，销售页照实说。
10. 2026-10-11 审稿补充：每节重跑任务组改为「并行后台运行、有墙钟和轮数上限、先发车后读数」，并定了额度不足时的降级方式（见「任务组设计」）。T3 和 T5 的验收改为只读约定路径的产出文件，使每一项都能由脚本判定，不依赖 Agent 自述。

## AI 关系

原则：Agent 负责执行，学员负责它外围的五件事。每节课学员都要能讲清：这一轮数字变了，是因为改了哪一件。

| 课 | AI 做什么 | 你做什么 | 你要能判断什么 | 本节重跑任务组看什么 |
|---|---|---|---|---|
| L00 | 帮你排查安装报错 | 跑通数仓、dbt、Claude Code；写下自己团队的一条工作流 | prod 和 dev 两个 schema 的权限是否真的不同 | 不跑 |
| L01 | 无人值守执行 5 个任务；根据现有 dbt 项目起草契约、指标定义和规则文件 | 写 5 条意图，补完第一个验收脚本；逐条改 AI 起草的上下文；给基线失败分类 | 一个任务失败是意图没写清、上下文缺了，还是缺闸门 | 基线，以及只加上下文之后的变化 |
| L02 | 写契约检查、对账、数据差异查询；闸门失败后自己循环修改 | 定阈值和容差；串成一条验证命令；埋坏数据检验闸门；保护测试文件 | 对账是不是在比两个独立算出来的数；Agent 是在修数据还是在改测试 | 闸门加上后，通过数、干预、耗时如何变 |
| L03 | 在受限身份下执行任务；红队环节里被你攻击 | 只读挂载 prod、只写 dev、脱敏视图、权限规则、审批、审计表、停止开关；当红队 | 哪一层挡住了哪次越界；审批带来的干预上升值不值 | 边界加上后通过数有没有掉 |
| L04 | 被告警触发，沿血缘排查，开修复 PR；在 CI 里审 dbt 改动 | 定异常阈值；定 Agent 能做到哪一步；审证据链；加三种翻车的拦截 | PR 里的证据能否复现；「行数恢复」是修好了还是被过滤掉了 | 行数异常任务改走闭环后的变化 |
| L05 | 帮你导出运行记录、起草复盘和方案初稿 | 建运行记录模型和面板；写复盘并改回上下文；写一页方案 | 5 个任务的样本能支持哪句话、不能支持哪句话 | 最终一轮，以及整条曲线 |

## 任务组设计

5 个任务固定不变，L01 跑基线，此后每节课重跑。每个任务都有一条意图、一个藏起来的标准答案（Agent 读不到）、一个验收脚本。验收脚本只输出通过或不通过，以及不通过的原因。

| # | 任务 | 验收脚本检查什么 |
|---|---|---|
| T1 | 新增 dbt 模型：每个客户一行，记录首单日期、首单渠道和首单净额 | dbt build 在 dev 成功；主键唯一且非空（行数等于去重后客户数）；列名和类型与契约文件一致；首单净额总和与标准答案查询一致 |
| T2 | 修正口径错误的指标：现有「月净销售额」把已退款订单和税算了进去 | 指标定义文件已更新；按月结果与标准答案查询逐月一致（容差由脚本写死）；原有 dbt 测试仍全部通过；没有改动标准答案和测试文件 |
| T3 | 回答一个业务问题：上一季度按首单渠道分组的复购率 | Agent 把结果写到约定路径的 CSV、把查询写到约定路径的 SQL 文件、把口径写到约定路径的 YAML（字段：复购定义、时间边界）；脚本检查：CSV 与标准答案查询结果逐行一致（比率容差写死在脚本里）；SQL 文件里引用的表只来自 dev 或 prod 的脱敏视图（脚本解析表名）；YAML 两个字段非空。口径写得对不对由人看，不计入通过判定 |
| T4 | 给一个现有模型补测试：客户维度表缺唯一、非空、取值范围和关联测试 | 规定的测试都存在；变异检查：脚本往 dev 副本里注入已知坏行（重复键、空值、非法渠道、孤儿外键），每一种都必须让至少一个测试失败 |
| T5 | 排查行数异常：某日订单事实表行数比前一日明显下降 | Agent 把根因写到约定路径的 YAML（字段：模型名、列名）；脚本检查：两个字段与答案键一致；修复后订单事实表与原始订单的对账通过；除契约里写明要排除的订单状态外，原始订单里有、事实表里没有的订单 ID 数为零（防止靠过滤数据让行数恢复） |

每个任务的产出都落在约定路径的文件里，验收脚本只读这些文件、git diff 和数仓，不读 Agent 的自述，也不调用模型。

每轮记录：每个任务的通过与否、人工干预次数（初始意图之后任何一次人的消息、批准或重试）、耗时、用量。

样本说明：5 个任务的成功率每次只能以 20 个百分点为一档变化，这是团队内部的信号，不是统计结论。L05 的方案必须写明这一点。

### 每节重跑在 120 分钟和订阅额度内怎么放得下

全课每个学员要跑 6 轮（L01 两轮，L02 到 L05 各一轮），共 30 次 Agent 运行，L02 以后每次还要循环到闸门通过。课上的重跑步骤只有 10 到 15 分钟，所以设计成：

1. **并行、后台、有上限**：一条命令同时起 5 个无人值守运行，每个运行有墙钟上限和轮数上限（数值在授课人试跑后定）。到上限没完成的记为「超时，不通过」，超时本身就是要分析的数据。
2. **先发车，后读数**：重跑在该步开始时发出，学员接着做下一步；结果在本节 PROJECT 步读。本节结束仍未跑完的，在下一节「先看终点」之前读，并在运行记录里标注。
3. **额度不够时的降级**：学员订阅额度不足以跑完整一轮时，只重跑本节改动可能影响的任务，其余在运行记录里标「沿用上一轮」，曲线上用不同标记画出。基线（L01）和最终一轮（L05）必须完整跑 5 个。
4. **开课前必须先完成的试跑**：授课人用一个订阅把 6 轮完整跑一遍，记录每个任务的耗时和用量，据此定上限、定是否需要降级、定报名页写哪一档订阅。这次试跑同时产出 L01「先看终点」的曲线。**状态：待实测。试跑跑完之前，任何物料不得出现这些数字。**
5. 如果试跑表明 5 个任务在 15 分钟内无法并行跑完，先缩小任务（例如缩小数仓规模、收窄 T5 的血缘深度），不先减少任务个数；仍不行再记一条决策。

## 常见翻车点

每一条都必须在开课前用真实运行复现。复现之前状态一律是「未验证」。如果实跑发现 Agent 不这样做，就换掉这一条，不硬凑。

| 课 | 翻车点 | 复现方法 | 通过标准 | 状态 |
|---|---|---|---|---|
| L01 | 没有指标定义时，Agent 照着错误代码抄口径 | 不给上下文跑 T2 | Agent 交出的口径与原错误一致或只改了一半 | 未验证 |
| L01 | Agent 声称完成，但验收脚本不通过 | 基线跑全部任务，对比 Agent 自述和脚本结果 | 至少一个任务出现自述完成而脚本不通过 | 未验证 |
| L02 | 闸门失败后，Agent 改测试或改期望值而不是改模型 | 不保护测试文件，跑 T2 和 T4 | 出现对测试或标准答案文件的改动 | 未验证 |
| L02 | 对账查询拿模型自己的结果和自己比，永远通过 | 让 Agent 写对账，不加约束 | 对账两边来自同一个模型 | 未验证 |

## 报名前自测

五个是否题，与销售页一致：

1. 不借助 AI，你能写出带窗口函数的 SQL（比如每个客户取第一笔订单）吗？
2. 你写过 dbt model，并跑过 dbt test 吗？
3. 你能读懂 Python 的 traceback，并改一个读写文件的脚本吗？
4. 你在某个数仓里建过表、加载过数据，并用 Git 分支提过 Pull Request 吗？
5. 你能说出你团队里一条重复做的数据工作，以及它做完了怎么检查吗？

分流：前四题任何一题是「否」，先上项目班（data-engineer-ai-starter）；第五题是「否」，可以报，但 L00 要多花时间想清楚自己要改造的工作流；五题全是「是」，报高级班。
