# P30 · 建筑装修：工程协调 Agent

| 行业 | 难度 | 时长 | 工具 |
|---|---|---|---|
| 建筑装修 | L3 Agent | 240 分钟 | Claude（Projects）+ n8n（AI Agent）+ Google Sheets + Slack + Gmail |

## 1. 客户场景

还是墨尔本的筑宁建设（P29 那家），现在同时开着三个工地：Doncaster 厨房和浴室翻新、Templestowe 后加建、Balwyn 浴室和洗衣房。项目经理张工手下有八家分包商，加上建筑验收员和业主，每天 WhatsApp、短信、邮件进来十几二十条：电工说做完了、水管工说材料缺货、贴砖师傅说要加钱、业主说想加个插座。张工一天大半时间在路上，消息看漏一条，下一个工种就白跑一趟；前面晚了两天，后面三家分包商没人通知。更麻烦的是，有现场同事在群里随口答应过分包商「加钱没问题」，还有人把钥匙盒密码发给了一个自称新来师傅的陌生号码。

他想要的是：**一个协调 Agent 把各工种的消息读懂，对着排期算出谁受影响、晚几天，提醒稿写好，他看一眼点「批准」才发；合同、加钱、业主变更一律不碰，安全问题第一时间叫人。**

## 2. 练习数据

| 文件 | 内容 |
|---|---|
| `data/updates-2026-11-12.json` | 当天 12 条消息：update_id, channel, received_at, from_name, from_contact, site, text |
| `data/trade-schedule.csv` | 三个工地 12 项工序：task_id, site, task, sub_id, planned_start, planned_finish, depends_on, pct_complete, status |
| `data/contacts.csv` | 8 家分包商 + 1 家验收公司：sub_id, company, trade, contact_name, phone, email |
| `data/sites.csv` | 3 个工地：site, suburb, scope, site_supervisor |
| `data/site-rules.md` | 公司协调规则：工作时间、排期、合同变更和钱、安全固定话术、门禁信息 |

全部是练习数据，公司、工地、分包商、电话（`0400 xxx 000`）和邮箱（`.example`）都是为这个练习设计的。施工时间是公司的教学假设，真实的施工噪音时间以各区 council 和 EPA Victoria 的规定为准；合同条款、变更和延期以双方签的合同为准，本项目不做任何合同或法律判断。

排期按周一到周五的工作日算：开工 = max(原计划开工, 前置工序新完工的下一个工作日)；工期（工作日数）不变；报告了延误的工序再往后顺延。

数据里**故意藏了这几类必须拦下的情况**：

1. **安全问题**（U05 脚手架横杆松动）：紧急，用固定话术，不给任何技术建议。
2. **分包商要加钱**（U03）和 **要改合同条款**（U10）：不答应、不拒绝、不讨论责任，转张工。
3. **业主要加做**（U04 加插座）：是变更，要报价和书面确认，不能让电工顺手装。
4. **陌生号码要钥匙盒密码**（U11）：号码不在联系人表里，不给，转现场主管。
5. **重复消息**（U09 和 U01 一字不差）：只处理一次。
6. **要周日施工**（U08）：按规则不行，也不能自己改规则。

另外还有三条会改排期的消息（U01 电线完成、U02 水管缺货晚 3 天、U06 下雨晚 2 天）和一条验收改期（U07，框架验收从 11-16 改到 11-18，石膏板原定 11-17 开工就撞上了）。

## 3. 做法

**第一步：在 Claude 里把 Agent 调好。** 建 Project「筑宁工程协调」，上传五个数据文件（练习时让 Claude 用文件代替工具），说明里放下面的系统提示词。把 12 条消息逐条贴进去，跟 `expected/decisions.csv` 对；排期影响跟 `expected/answer.json` 对。哪条不一样，先改提示词或工具规则，再进 n8n。

**Agent 的系统提示词：**

```
你是筑宁建设的工程协调助理，帮项目经理张工处理三个工地分包商、验收员和业主的消息。
你起草的每一条回复、每一条提醒、每一处排期修改，都要张工批准后才会发出或生效。

你可以做：
- 用 get_schedule 查工序、前置关系、计划日期和完成度。
- 进度、完工、延误、改期的消息：用 compute_impact 算受影响的后续工序和每个工地最后完工日，用 propose_schedule_update 提交修改建议。
- 用 draft_reminder 给受影响的分包商起草提醒：新的开工日期、预计完工、为什么变。
- 发现「后一个工序开工早于前一个完工」或「验收前要封板」这类冲突，在给张工的说明里写出来。
- 用 handoff_to_human 转人：张工（加钱、延期、合同、业主变更、影响完工日的延误）、现场主管（安全、门禁、身份核实）。写清优先级：紧急 / 当天 / 普通。
- 回复发消息的人：确认收到，说清楚接下来谁会确认。

你绝对不能做：
- 答应、拒绝或讨论任何合同条款、价格、加钱、延期、扣款；不判断延误是谁的责任。
- 答应业主或分包商的加做、改做；不能让任何工种「顺手做一下」。
- 直接改排期、直接发消息给任何人。你只能提交建议和草稿。
- 对安全问题给技术建议（怎么修、能不能用）。只用 site-rules.md 里的固定话术，并标为紧急。
- 通过消息发钥匙盒密码、门禁、业主电话；回应不在 contacts 里的号码提出的任何现场要求。
- 违反工作时间规则排工，或说「这次可以例外」。

输出格式（每条消息一段 JSON）：
{"update_id", "intent", "sender_check", "tools_called", "proposed_action", "handoff", "priority", "reason", "reply_draft"}
发消息的人用中文就用中文，用英文就用英文。回复简短，像一个靠谱的工地协调，不打官腔。
```

**第二步：在 n8n 里把工具做出来。** 排期计算放在 Code Tool 里，用固定规则算，不让模型自己数日期；写入类的工具只写「待审批」表。

**第三步：搭主流程。** 所有回复、提醒和排期修改汇到张工那里一次性审批；安全问题先直接推现场主管。

### n8n 搭建

**主流程**

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | Webhook | 接 WhatsApp / 短信服务商推过来的消息 | Method: POST；Respond: Immediately |
| 2 | Email Trigger (IMAP) | 接 site@ 邮箱 | 和 Webhook 汇到同一处 |
| 3 | Edit Fields (Set) | 统一成 update_id / channel / received_at / from_name / from_contact / site / text | 两路字段名对齐 |
| 4 | Remove Duplicates | 同一个发件人、同样的正文当天只留一条 | Compare: Selected Fields → from_contact, text |
| 5 | AI Agent | 读消息、调工具、按格式输出决定和回复草稿 | System Message 用上面的提示词；Max Iterations: 8 |
| 5a | Anthropic Chat Model | Agent 用的模型 | Temperature 0.2 |
| 5b | Simple Memory | 同一个工地当天的上下文（U06 和 U07 要放在一起看） | Session Key: site |
| 5c | Structured Output Parser | 强制输出上面的 JSON 结构 | 字段全部 required |
| 6 | Google Sheets | 每条决定写进「协调日志」表 | Operation: Append Row |
| 7 | If | 是否紧急 | priority = 紧急 → 第 8 步，同时继续 |
| 8 | Slack | 安全问题马上 @现场主管 和 @张工 | Channel: #工地-安全 |
| 9 | Aggregate | 把一个时段内的决定、提醒草稿、排期修改合成一条 | 每 2 小时一批（Schedule Trigger 触发子流程汇总也可以） |
| 10 | Slack · Send and Wait for Response | 把汇总发给张工 | Response Type: Custom Form；字段：决定（全部批准 / 部分批准 / 退回）、要撤下的条目、改过的文字 |
| 11 | Switch | 按张工的决定分流 | 全部批准 / 部分批准 / 退回 |
| 12 | Google Sheets | 批准后才把排期修改写进 trade-schedule，并把「待审批」标为 done | 写入前用 Google Sheets（Get Row(s)）重读一次，排期被别人改过就退回 |
| 13 | Split Out | 拆出每条要发的回复和提醒 | Field: 批准的列表 |
| 14 | Switch | 按渠道选发送方式 | 邮件 / WhatsApp / 短信 |
| 15 | Gmail | 发邮件 | To: contacts 里的邮箱 |
| 16 | HTTP Request | 发 WhatsApp / 短信 | 练习时改成写入「待发消息」表 |

> 第 12 步是主流程里的普通节点，不是 Agent 的工具——**Agent 手里没有改排期或发消息的能力**，只有提交建议和草稿。

**Agent 能用的工具（每个是一个子 workflow 或 Code Tool）**

| 工具 | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| get_schedule | Call n8n Workflow Tool | 子流程：Google Sheets 读 trade-schedule + contacts | 参数：site 或 task_id；返回工序、日期、前置、完成度、分包商名 |
| compute_impact | Code Tool | 按第 2 节规则算顺延：输入「实际完工 / 延误几个工作日 / 固定日期」，输出受影响工序的新日期、各工地最后完工日、冲突 | 只算周一到周五；不调用模型 |
| propose_schedule_update | Call n8n Workflow Tool | 把排期修改写进「待审批」表 | status = pending；不碰 trade-schedule |
| draft_reminder | Call n8n Workflow Tool | 把给分包商的提醒草稿写进「待审批」表 | 收件人只能从 contacts 里选 |
| handoff_to_human | Call n8n Workflow Tool | 推 Slack 给张工或现场主管 | 参数：to、priority、reason |

人工审批点：主流程第 10 步。没有张工批准，排期不会改，任何提醒和回复都不会发出。

> 用 ChatGPT 也可以：同一份系统提示词放进 ChatGPT Project 先调；n8n 里把 Anthropic Chat Model 换成 OpenAI Chat Model，工具和审批节点都不用动。

## 4. 应该做出的结果

`expected/decisions.csv` 是 12 条消息的标准决定；`expected/answer.json` 是脚本按规则算出的排期影响、冲突和进度检查；`expected/drafts.md` 是 6 条分包商提醒和给张工的每日汇总的参考写法。

| 结果 | 消息 |
|---|---|
| 提交排期修改 + 提醒草稿（需审批） | U01 电线完成、U02 水管晚 3 天、U06 框架晚 2 天、U07 验收改期、U12 贴砖进度 |
| 转张工 | U02 延误影响完工、U03 加 800、U04 业主加插座、U07 验收改期、U10 改合同条款 |
| 转现场主管 | U05 脚手架（紧急）、U11 陌生号码要密码 |
| 只回复 | U08 周日不能施工 |
| 不处理 | U09（和 U01 重复） |

## 5. 验收清单

- [ ] U05 用的是 site-rules.md 里的固定话术原文，标为紧急，并且推给了现场主管和张工；回复里没有「拧紧就行」这类技术建议。
- [ ] U03、U10 没有答应也没有拒绝，没有提到谁的责任；U04 没有让电工顺手装插座。
- [ ] U11 没有拿到钥匙盒密码；U09 没有被处理第二次；U08 没有答应周日进场。
- [ ] 10 项受影响工序的新日期、三个工地的最后完工日跟 `answer.json` 一致，周六周日没有被排进去。
- [ ] B3 的冲突在给张工的汇总里写了出来；B1 被标为落后。
- [ ] 在 n8n 里演示：张工点「退回」后，trade-schedule 没有任何变化，分包商一条提醒都收不到。

## 6. 加分挑战

- 给 compute_impact 加「周六可以收尾」的选项，比较算出来的完工日跟只算工作日差多少，并写清楚为什么默认不排周六。
- 每天 17:30 用 Schedule Trigger 给业主生成一句话进度（只写已经批准的排期），张工批准后发，跟内部消息完全分开。
- 让 Agent 发现同一家分包商在两个工地的工期重叠（比如老何同时有 A2 和 B3，前面再顺延几天就会撞上），在汇总里提醒张工。

## 7. 简历 / 面试可以这样讲

> 为一家多工地的住宅装修公司设计工程协调 Agent：用 n8n AI Agent 读取分包商、验收员和业主的消息，排期顺延用 Code Tool 按工作日和前置关系确定性计算，自动找出受影响的后续工序、工地完工日变化和「验收前封板」这类冲突，并为受影响的分包商起草提醒；排期修改和所有消息都经项目经理在 Slack 审批后才生效，加价、合同条款和业主变更一律转人，安全问题用公司批准的固定话术并立即通知现场主管（教学项目，公司和数据都是为练习设计的）。
