# P04 · 房产 / 物业：租客报修 → 分类派单 → 完工回访

| 行业 | 难度 | 时长 | 工具 |
|---|---|---|---|
| 房产 / 物业 | L2 Workflow | 150 分钟 | Claude + n8n + n8n Form + Google Sheets + Gmail + Slack |

## 1. 客户场景

安居物业是布里斯班 Sunnybank 的一家小型物业管理公司，物业经理 Jenny 一个人管着几十套出租房。租客报修有的走网站表单，有的直接发邮件，中英文都有。Jenny 每天早上先把报修一条条看完，判断急不急、该找水管工还是电工、这个房东授权她花多少钱，再打电话约师傅，修完还要记得问租客满不满意、核对师傅的发票。一忙起来就会漏：同一个租客报了两次被派了两次单，煤气味的报修排在了滴水龙头后面，师傅的发票比报价翻了一倍也照付了。

她想要的是：**报修一进来就自动分好类、标好急缓、配好师傅和预估费用，Jenny 只需要点确认；超过房东授权的先问房东；修完自动核对发票、两天后发回访。**

## 2. 练习数据

都是练习数据，公司、租客、房东、师傅、电话和邮箱都是为这个练习设计的。

| 文件 | 内容 |
|---|---|
| `data/requests-2026-11-10.json` | 14 条报修：编号、收到时间、物业编号、租客、邮箱、渠道（表单 / 邮件）、描述原文、照片张数 |
| `data/properties.csv` | 8 套在管物业：地址、区域（南区 / 西区 / 东区）、房东、房东邮箱、`approval_limit` 房东授权物业经理直接花的额度 |
| `data/tradies.csv` | 11 家合作师傅：工种、服务区域、上门费、是否首选 |
| `data/cost-guide.csv` | 各工种常见小修的预估费用（教学假设），紧急单另加 120 加急费 |
| `data/completions-2026-11-17.csv` | 一周后的完工记录：完工日期、发票金额、师傅备注 |

数据里**故意藏了 5 处问题**：

1. 一条燃气味报修（R04）：涉及人身安全，必须马上打电话，不能按普通工单排队；
2. 同一个租客第二天又报了一次同样的滴水龙头（R08）：应合并，不能再派一次单；
3. 一条「想装电视挂架」（R09）：这是改动房屋，不是维修，要房东同意，不派单；
4. 一条报修的地址不在公司管理的物业里（R10）：不派单，回复租客找实际的管理方；
5. 屋顶维修的发票（J-R07）比预估高了一倍多：完工核对时要暂停付款，等 Jenny 核对。

**教学假设，以昆州 RTA（住宅租赁管理局）规定和管理合同为准：** 紧急维修按 RTA 列出的类型判断，本项目用到的有：燃气泄漏、热水系统故障、唯一厕所堵塞、严重屋顶漏水、门锁失灵导致房子无法上锁。紧急维修在本项目里走「物业经理电话确认后立即派单，事后通知房东」；非紧急维修的预估超过房东授权额度，要先问房东。

## 3. 做法

**第一步：在 Claude 里把分类规则跑通。** 建一个 Project「安居物业报修」，把 `properties.csv`、`tradies.csv`、`cost-guide.csv` 放进项目文件，说明里写：

```
你是安居物业的报修分类助手。我会给你一批报修（JSON）。逐条输出一行，字段：
request_id, is_repair(是/否), category, urgency, summary, handling, needs_human_reason。
- category 只能用：水管、电工、燃气、门锁、电器、屋顶、虫害、杂项、空调。
- urgency 只能用：紧急（人身安全或下面列表里的情况）/ 尽快（24–48 小时）/ 常规（7 天内）。
  紧急：燃气味或燃气泄漏、完全没有热水、唯一的厕所堵塞、屋顶或天花板漏水、门锁坏导致无法上锁、漏电或冒火花、水管爆裂。
- 先查四件事，再决定派不派单：
  1. property_id 不在 properties 里 → 不派单，handling 写「回复租客联系实际管理方」。
  2. 同一租客邮箱在 72 小时内报过同一个问题 → 标为重复，handling 写「合并到 Rxx」。
  3. 不是维修而是添置、改装（装挂架、打孔、换颜色等）→ is_repair = 否，handling 写「转房东征求同意」。
  4. 燃气味 → handling 写「安全升级：立即电话联系租客 + 派燃气工」。
- summary 用一句中文概括问题，不加原文没有的细节。
- 你只做分类，不承诺上门时间，不回复租客，不联系师傅。
```

把 JSON 粘进去，拿结果和 `expected/decisions.csv` 对。分类和急缓对了，再进 n8n。**选师傅、算预估、判断要不要房东批准都是规则，放在 Code 节点里算**，不要交给模型：

- 选师傅：工种 + 区域匹配，`preferred = yes` 优先，再选上门费低的；
- 预估 = cost-guide 里该工种的预估，紧急单 + 120；
- 非紧急单的预估 > 房东授权额度 → 先问房东；
- 完工发票 > 预估 × 1.2 → 暂停付款；回访日 = 完工日 + 2 天。

### n8n 搭建

分两个 workflow：A 接报修派单，B 完工核对和回访。

**Workflow A · 报修 → 派单**

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | n8n Form（Form Trigger） | 租客报修表单 | 字段：物业地址（下拉，值为 property_id）、姓名、邮箱、问题描述、照片 |
| 2 | Email Trigger (IMAP) | 同时接 repairs@ 邮箱的报修邮件 | 只读未读邮件；读完标已读 |
| 3 | Edit Fields (Set) | 两路统一成同一套字段 | request_id、received_at、property_id、tenant_name、tenant_email、channel、description |
| 4 | Merge | 两个入口合成一路 | Mode: Append |
| 5 | Google Sheets（读历史报修） | 读 `requests` 表近 72 小时记录，用来查重 | Get Row(s)，按 received_at 过滤 |
| 6 | Text Classifier + Anthropic Chat Model | 按 category 分类 | 9 个类别，每类写一句说明；Temperature 0 |
| 7 | Information Extractor + Anthropic Chat Model | 抽出 urgency、is_repair、summary、是否重复 | 用第 3 节的提示词；输出字段固定 |
| 8 | Code（规则） | 查物业是否在管、选师傅、算预估、判断审批路线 | 读 properties / tradies / cost-guide 三张表 |
| 9 | Switch | 按处理方式分路 | 安全升级 / 紧急 / 普通派单 / 需房东批准 / 不派单 |
| 10 | Slack（安全升级） | R04 这类：@Jenny 加急提醒，附租客电话 | 只发给内部频道；租客那边由 Jenny 本人马上打电话 |
| 11 | Slack（Send and Wait for Response，派单确认） | 紧急和普通单都发给 Jenny：问题、师傅、预估、审批路线 | Response Type: Approval；紧急单超时 30 分钟再提醒一次 |
| 12 | Gmail（Send and Wait for Response，房东批准） | 需房东批准的单，Jenny 确认后发房东 | 写清问题、师傅、预估、授权额度；Approval |
| 13 | If（是否全部批准） | 没批准的写回表格 status = on_hold | |
| 14 | Gmail（派单给师傅） | 批准后发工单邮件给师傅 | 地址、租客电话、问题、预估上限 |
| 15 | Gmail（回复租客） | 用固定模板告知已派单、师傅会直接联系；重复 / 非维修 / 非在管的回复也走这里 | 模板由 Jenny 事先审定；AI 写的个性化回复必须先进第 11 步审批 |
| 16 | Google Sheets（写工单） | 记录 job_id、状态、谁批的、几点派的 | Append Row |

**Workflow B · 完工 → 核对 → 回访**

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | Schedule Trigger | 每天 17:00 | Australia/Brisbane |
| 2 | Google Sheets（读完工记录） | 读当天新增的 completions | |
| 3 | Code（核对发票） | 发票 ÷ 预估 − 1 > 20% → 标 hold；算回访日 | |
| 4 | If（是否 hold） | hold 的走 5，正常的走 6 | |
| 5 | Slack（Send and Wait for Response） | 把超额发票和师傅备注发给 Jenny，等她决定付不付 | Approval；不批准就不进付款表 |
| 6 | Google Sheets（付款待办） | 写入待付款表，财务付款前仍由 Jenny 确认 | 本流程不直接付款 |
| 7 | Wait | 等到回访日 | Resume: At Specified Time = follow_up_date 09:00 |
| 8 | Basic LLM Chain + Anthropic Chat Model | 写一条简短回访消息：问修好了没、满意吗 | 不超过 80 字；不承诺赔偿或费用 |
| 9 | Gmail（Send and Wait for Response） | 回访草稿先发给 Jenny 批量确认 | Approval |
| 10 | Gmail（发给租客） | 确认后发出 | |

> 用 ChatGPT 也可以：Project 规则照搬到 ChatGPT；n8n 里 Text Classifier、Information Extractor、Basic LLM Chain 下面的模型换成 OpenAI Chat Model 即可。

## 4. 应该做出的结果

`expected/decisions.csv` 是每条报修的分类和处理（参考答案），`expected/answer.json` 是脚本按规则算出的派单、审批和发票核对，`expected/tenant-replies.md` 是几条特殊情况的回复参考。

- 14 条报修，派出 11 张工单，3 条不派单：R08 合并到 R01、R09 转房东征求同意、R10 非在管物业。
- 5 张紧急单：J-R02 热水、J-R04 燃气（同时安全升级）、J-R05 门锁、J-R07 屋顶、J-R12 唯一厕所。
- 1 张非紧急单要先问房东：J-R14 空调，预估 420 超过房东授权 400。J-R07 和 J-R12 的预估也超过了房东授权，但属于紧急维修，按「先派单、事后通知房东」处理。
- 11 张工单预估合计 3,810 澳元。

## 5. 验收清单

- [ ] 燃气味报修 R04 走了安全升级：Jenny 收到加急提醒，没有和普通工单一起排队。
- [ ] R08 没有再派一次单，而是合并到 R01；R09、R10 都没派单，并且给租客的回复写清了原因。
- [ ] 派出的 11 张工单，师傅和预估跟标准答案一致；J-R14 在房东批准前不会发给师傅。
- [ ] 所有工单都经过 Jenny 在 Slack 里确认后才发给师傅；点拒绝的单状态为 on_hold。
- [ ] J-R07 的发票被拦下，没有进付款待办；其余 8 张进了。

## 6. 加分挑战

- 租客上传的照片也交给 Claude 看（Anthropic Chat Model 支持图片输入），用照片辅助判断急缓，并在分类结果里写明「根据照片判断」。
- 每周五给每位房东发一份本周维修汇总：哪些单、花了多少、还有哪些在等他批准。
- 同一套房子 90 天内同一类问题报修第三次，自动提醒 Jenny 考虑整体更换而不是继续小修。

## 7. 简历 / 面试可以这样讲

> 为一家物业管理公司搭建报修派单流程：表单和邮件两路报修统一进 n8n，用 Claude 分类别和急缓，规则节点按工种和区域配师傅、按房东授权额度决定审批路线；燃气等安全问题单独加急，重复报修、非维修请求和非在管物业自动拦下；完工后自动核对发票、超额暂停付款，两天后发经确认的回访（教学项目，数据为为练习设计，紧急维修口径为教学假设）。
