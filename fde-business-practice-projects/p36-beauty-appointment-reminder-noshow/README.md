# P36 · 美业 / 美容院：预约 → 前一天提醒 → 爽约跟进

| 行业 | 难度 | 时长 | 工具 |
|---|---|---|---|
| 美业 / 美容院 | L2 Workflow | 150 分钟 | Claude + n8n + Google Sheets + Slack + Gmail + 短信服务（HTTP Request） |

## 1. 客户场景

柚子美甲睫毛（Yuzu Nail & Lash）在墨尔本 Glen Waverley 的商场里，三个美容师，一天二三十个预约。店长 Yuki 最心疼的是爽约：一个睫毛嫁接占一个半小时，客人不来，这段时间就白空着。现在前台每天下班前对着预约表，一条条手动给第二天的客人发短信；有人爽约了，第二天想起来就问一句，想不起来就算了。

出过的问题也不少：有客人回过 STOP，前台照样发短信，客人很生气；有客人明明提前打电话说堵车会晚到，结果被标成爽约，还被提了收费；同一个客人被两个美容师各录了一条预约，提醒发了两遍；还有新同事自作主张给第二次爽约的客人发了「要收 30 元」，店长事先都不知道。

她想要的是：**每天上午自动给明天的客人发提醒，用客人没退订的渠道；联系不上的列给前台打电话；昨天爽约的，第一次就发一条关心消息，第二次以上的「收不收费」由她点头；凡是有疑问的（提前联系过、有投诉、重复预约）都不要自动发，交给人。**

## 2. 练习数据

全部是练习数据：店名、地址、客人、电话（`0400 xxx 000`）、邮箱（`.example`）都是为这个练习设计的。

| 文件 | 内容 |
|---|---|
| `data/appointments.csv` | 18 条预约：11 条是明天（11-13）的，7 条是昨天（11-11）的 |
| `data/clients.csv` | 17 位客人：电话、邮箱、偏好渠道、短信 / 邮件是否退订、90 天内以前爽约过几次、备注 |
| `data/contact-log-2026-11-11.csv` | 昨天客人打来的电话和发来的短信 |
| `data/reminder-and-no-show-policy.md` | 门店的提醒和爽约规则、地址 |

`appointments.csv` 的 status：booked / cancelled / completed / no_show。`reminder_sent_at` 不为空表示已经发过提醒。

今天是 2026 年 11 月 12 日（周四），流程每天 10:00 跑一次：给明天的预约发提醒，处理昨天的爽约。

数据里**故意藏了 6 类要拦的情况**：

1. **退订**：一位退订了短信（要改用邮件），一位两种都退订了（只能前台打电话），一位爽约的客人退订了所有渠道（不发任何消息）。
2. **联系方式不对**：一位新客的电话只有 9 位，又没有邮箱。
3. **重复预约**：同一位客人同一时间有两条预约，分在两个美容师名下。
4. **「爽约」其实不是爽约**：一位客人预约前打电话说堵车晚 20 分钟，前台答应等她，后来却被标成 no_show。
5. **第二次以上爽约**：按规则可以收费，但必须店长批准，批准前消息里不能提钱。
6. **有投诉没处理完**：一位第三次爽约的客人，还有一单睫毛过敏的投诉在跟进，不能发任何自动消息。

另外还有已取消、已经发过提醒、正常完成、提前两天取消的预约，都要安静地跳过。

教学假设：爽约费 30 澳元、「90 天内第二次」这些都是这家店为练习定的规则；能不能收、怎么收以门店和客人确认过的预约条款为准，本项目不构成法律意见。客人退订后不再发同一渠道的消息，是这家店的规则；电子消息相关的具体规定以澳洲官方信息为准。

## 3. 做法

**规则**（先在 Claude 里跑通，再搬进 n8n 的 Code 节点）：

- **明天的提醒**：已取消、已发过 → 跳过。同一客人同一时间两条 booked → 转前台，确认前不发。渠道：先用偏好渠道；退订了或用不了（手机号不是 04 开头 10 位、没有邮箱）就换另一个；都不行 → 前台电话名单。第一次来店的加停车和店门位置。
- **昨天的爽约**：只看 status = no_show。按顺序判断：预约开始前客人联系过 → 转店长；有未处理的投诉 → 转店长；所有渠道都退订 → 只记录；90 天内第 2 次及以上 → 建议收 30 元（待店长批准）；第 1 次 → 关心消息，不收费。

**第一步：在 Claude 里把规则跑通。** 新建 Project「柚子预约提醒」，上传四个文件，项目说明里写：

```
你是柚子美甲睫毛的预约助手。今天是 2026-11-12，现在是 10:00。你只出判断和消息草稿，不发任何消息。
按 reminder-and-no-show-policy.md 处理两件事：
A. 明天（11-13）的每条预约：判断发不发提醒、用什么渠道，起草提醒。
   - 渠道只能用客人没退订的。两个都不能用，就放进「前台电话提醒」名单。
   - 手机号必须是 04 开头的 10 位数字，否则当作短信不能用。
   - 同一客人同一时间两条预约：交前台确认，不发。
B. 昨天（11-11）的每条 no_show：
   - 先查 contact-log：预约开始前客人联系过的，交店长，不发消息、不提收费。
   - 客人备注里有投诉在跟进的，交店长，不发自动消息。
   - 客人所有渠道都退订的，只记录。
   - no_shows_prior_90d + 1 ≥ 2：写「建议收 $30（待店长批准）」，并起草两版消息：批准收费时 / 不收费时。
   - 第 1 次：起草一条关心消息，问要不要改约，不提钱。客人事后发过消息的，回复里要回应她说的话。
消息要像店里的人在说话，短一点，写清日期、星期、时间、项目、美容师；短信不超过 160 字（英文 50 词左右），
客人名字是中文就用中文，英文就用英文。不写任何关于过敏、健康的判断。
输出一张表：appt_id, stage, rule_status, channel, flags, needs_human, message_draft。
```

跟 `expected/decisions.csv` 对，rule_status 和 channel 必须一致；草稿措辞可以不同，但日期、时间、项目、美容师必须对。

**第二步：准备 Google Sheets。** 一个表格四张工作表：`appointments`、`clients`、`contact_log`、`message_log`。

**第三步：按下面的节点搭 n8n。** 判断全在 Code 节点里，Claude 只写消息。

### n8n 搭建

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | Schedule Trigger | 每天 10:00 | 时区 Australia/Melbourne |
| 2 | Google Sheets（读预约） | 读 `appointments` | Operation: Get Row(s) |
| 3 | Google Sheets（读客人） | 读 `clients` | 同上；打开 Always Output Data |
| 4 | Google Sheets（读联系记录） | 读 `contact_log` 昨天的记录 | 同上 |
| 5 | Code（判断） | 按规则给每条预约打 stage、rule_status、channel、flags；查重复、查退订、查手机号、查预约前联系、数爽约次数 | Run Once for All Items；日期用 `$now.setZone('Australia/Melbourne')` 算明天 / 昨天 |
| 6 | Filter | 去掉「跳过」的 | rule_status 不以「跳过」开头 |
| 7 | Switch | 分五路：发提醒 / 关心消息 / 建议收费 / 前台名单 / 转人工（转前台、转店长、只记录） | 按 rule_status 匹配 |
| 8 | Basic LLM Chain + Anthropic Chat Model | 给「发提醒」「关心消息」「建议收费」三路起草消息 | 提示词见下；Temperature 0.3 |
| 9 | Aggregate | 把今天所有提醒和关心消息合成一条审批 | Aggregate: All Item Data |
| 10 | Slack · Send and Wait for Response（前台审批） | 前台看一遍提醒和关心消息，逐条选 发 / 改了再发 / 不发 | Response Type: Custom Form |
| 11 | Slack · Send and Wait for Response（店长批准收费） | 「建议收费」的每一条单独发给 Yuki：客人、这是 90 天内第几次、两版草稿 | Response Type: Custom Form；选项：收费 / 不收费只问候 / 不发；超时 1 天按「不发」处理 |
| 12 | Merge | 把两路审批结果合回来 | Mode: Append |
| 13 | Switch（按 channel） | sms → 第 14 步；email → 第 15 步 | 只处理批准了的 |
| 14 | HTTP Request | 调短信服务商接口发短信 | 练习时改成写进「待发短信」表；发送前再查一次 `sms_opt_out`，防止审批期间客人刚回了 STOP |
| 15 | Gmail | 发邮件提醒 | 同样发送前再查一次 `email_opt_out` |
| 16 | Google Sheets（回写） | 提醒发出后写 `reminder_sent_at`，防止重复发 | Update Row；匹配 appt_id |
| 17 | Slack（前台名单 / 转人工） | 推到 #前台：要打电话的、重复预约；推到 #店长：提前联系过的、有投诉的 | 不给客人发任何东西 |
| 18 | Google Sheets（写 message_log） | 记 appt_id、渠道、谁批的、几点发的、发了什么；「只记录」的爽约也写一行 | Append Row |

第 8 步的提示词：

```
你在帮柚子美甲睫毛写一条发给客人的消息。下面是预约 JSON、客人 JSON（只含名字和渠道）、rule_status 和 flags。
- 提醒：写明天的日期和星期、时间、项目、美容师、地址；要改时间请回复这条消息。flags 有「第一次来店」的，加停车和店门位置。
- 关心消息：语气轻松，不责怪，问要不要改约；flags 里有客人事后发来的话，要接着她的话回。不提任何费用。
- 建议收费：写两版。A 版（店长批准收费）：说明这是 90 天内第二次没来，按预约条款收 $30，会再联系怎么付，仍然欢迎改约。
  B 版（不收费）：只问候和问要不要改约。
短信不超过 160 字。不写过敏、健康相关的内容，不编造优惠。
```

> 用 ChatGPT 也可以：第一步用 ChatGPT Project 跑同样的规则；n8n 里把 Anthropic Chat Model 换成 OpenAI Chat Model，其他节点不变。

## 6. 加分挑战

- 用 Webhook 接短信服务商推回来的回复：客人回 STOP 就自动把 `sms_opt_out` 改成「是」并写日志；回「改期」就推给前台。
- 加一个「当天 2 小时前」的第二次提醒，只发给 90 天内爽约过的客人，并比较这样做会多发多少条、可能少几次爽约（写清这只是假设，要用真实数据验证）。
- 每周一给 Yuki 一份汇总：上周提醒发了多少、前台电话多少、爽约几次、收费建议批了几条没批几条。

## 7. 简历 / 面试可以这样讲

> 为一家美甲睫毛店搭建预约提醒和爽约跟进流程（n8n + Claude）：每天按客人偏好和退订状态选择短信或邮件提醒，联系方式无效或全部退订的转前台电话，重复预约先确认再发；爽约按 90 天内次数分级，第一次只发关心消息，收费建议必须店长单独批准，预约前联系过或有投诉的客人一律转人工；发送前二次检查退订状态，发送后回写记录防止重复（教学项目，爽约规则为教学假设，数据为这个练习设计）。
