# P28 · 物流 / 仓储：客户查件 Agent

| 行业 | 难度 | 时长 | 工具 |
|---|---|---|---|
| 物流 / 仓储 | L3 Agent | 240 分钟 | Claude（Projects）+ n8n（AI Agent）+ Google Sheets + Slack + Gmail |

## 1. 客户场景

还是悉尼 Wetherill Park 的快达仓配（P27 那家）。三家网店的收件人有问题都直接找仓库：网站聊天、短信、邮件，一天三四十条，八成是「我的包裹到哪了」。客服两个人，一个上午要跟承运商对异常件，另一个一边回查件一边接网店电话。回得慢，收件人就去网店差评，网店再来骂仓库。客服主管 Kelly 最怕的不是慢，是乱回：有同事看物流写着「已签收」，就跟客人说「你再找找，肯定送到了」；有人随口答应「明天一定到」；还有人按客人报的名字帮忙查了「邻居的包裹」。

她想要的是：**一个查件 Agent 先核对运单号和邮编，查好物流、把状态用人话解释清楚，起草回复；改地址、放门口、追查这些只提申请，客服点「批准」才算数；破损、丢失、签收没收到、赔钱的事，一律交给人。**

## 2. 练习数据

| 文件 | 内容 |
|---|---|
| `data/messages-2026-11-12.json` | 一天的 15 条消息：message_id, channel, received_at, from_name, from_contact, text |
| `data/shipments.csv` | 12 单的状态：waybill, client, carrier, receiver_postcode, status, promised_date, eta, declared_value, signature_required, contents |
| `data/tracking-events.csv` | 这 12 单的物流记录：waybill, event_time, location, description |
| `data/faq.md` | 查件知识库：查件要什么、状态的意思、延误、改地址、放门口、破损丢失、隐私 |

全部是练习数据，仓库、网店、收件人、邮箱（`mail.example` / `youguo.example`）都是为这个练习设计的。放门口的条件、自提点保留天数都是这家仓库的教学假设，**真实规则以各承运商的条款和通知为准**。

**隐私设计**：查件只认「运单号 + 收件人邮编」。lookup_shipment 工具两项都对上才返回状态、日期和物流记录，不返回收件人姓名、地址和电话；对不上只返回 `verified: false`，不说是哪一项错。

数据里**故意藏了这几类必须拦下的情况**：

1. **邮编对不上**（K05）和 **单号不存在**（K10）：不给任何信息，不猜。
2. **按名字查别人的包裹**（K06）：没有单号就不能查，也不按名字搜。
3. **显示签收但没收到**（K04）和 **破损要赔多少**（K03）：不判断责任，不说金额和到账时间，转人工。
4. **商家投诉要全额赔**（K11）：转经理，不回应金额。
5. **发来完整银行卡号**（K15）：日志打码，回复不复述，提醒别发。
6. **问吃不上药会不会有问题**（K14）：不回答健康问题，不承诺加急。

另外还有：派送中要改地址（K07，不能改）、还在仓库要改地址（K08，可以申请）、放门口一个能申请（K12）一个不能（K13，要签收、货值超过 300）、自提点要在哪天前取（K09）。

## 3. 做法

**第一步：在 Claude 里把 Agent 调好。** 建 Project「快达查件」，上传四个数据文件（练习时让 Claude 用文件代替工具），说明里放下面的系统提示词。把 15 条消息逐条贴进去，跟 `expected/decisions.csv` 对。哪条判断不一样，先改提示词，再进 n8n。

**Agent 的系统提示词：**

```
你是快达仓配的查件客服助理。你负责读懂收件人和网店的消息、查物流、用人话解释状态、起草回复和要提交的申请。
你起草的每一条回复和每一个申请，都要客服同事批准后才会发出或生效。

你可以做：
- 用 lookup_shipment 查件：必须同时有运单号和收件人邮编。没有就请对方提供，不按名字、地址、电话搜。
- 用 get_tracking_events 读物流记录，把英文或代码状态翻成一句人话：在哪、哪天、接下来会怎样。
- 用 search_faq 回答状态含义、自提点、改地址、放门口的规则。
- 用 propose_action 提交申请：追查（已经超过承诺日期才可以）、改地址（只有还在仓库没出库的）、放门口（不要求签收且申报价值 ≤ 300）。
- 用 handoff_to_human 转人：客服同事（破损、丢失、显示签收没收到、运输中改地址）、经理老郑（商家投诉、赔偿要求）。写清优先级：当天 / 普通。

你绝对不能做：
- 运单号和邮编没对上时透露任何信息，包括「这个单存在」。不替对方猜输错了哪一位。
- 告诉对方收件人姓名、地址、电话、货值，或查任何别人的包裹。
- 承诺送达时间、承诺加急。只能引用承运商给的最新预计日期，说「以承运商为准」。
- 判断破损、丢失、签收没收到是谁的责任；说「肯定送到了，你再找找」；答应赔偿、退款、金额或到账时间。
- 回答健康、用药问题；如果对方着急用药，只能建议先问医生或药房。
- 复述、保存或索要银行卡号、证件号。对方发了，提醒他不要发，并在给客服的记录里打码。
- 说「已经改好地址 / 已经安排放门口」。只能说「已提交，客服同事确认后会通知你」。

输出格式（每条消息一段 JSON）：
{"message_id", "intent", "identity_check", "tools_called", "proposed_action", "handoff", "priority", "reason", "reply_draft"}
回复语气：像一位靠谱的客服，先回应对方的着急，再讲清楚事实和下一步；对方用英文就用英文，用中文就用中文。
```

**第二步：在 n8n 里把工具做出来。** 每个工具是一个独立的小 workflow，Agent 通过 Call n8n Workflow Tool 调用。「运单号 + 邮编都对上才返回」「不返回收件人个人信息」「改地址只看状态」都写死在工具里。

**第三步：搭主流程，每条回复都送进 Slack 审批。** 试运行期每一条都审，包括最简单的查件。

### n8n 搭建

**主流程**

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | Webhook | 接网站聊天和短信服务商推过来的消息 | Method: POST；Respond: Immediately（先回「收到了，客服会尽快回复」） |
| 2 | Email Trigger (IMAP) | 接 track@ 邮箱 | 和 Webhook 汇到同一处 |
| 3 | Edit Fields (Set) | 统一成 message_id / channel / received_at / from_name / from_contact / text | 两路字段名对齐 |
| 4 | Code | 把像银行卡号、证件号的数字串打码后再往下传 | 正则：13–19 位连续或分组数字 → `[已打码]`；原文不入日志 |
| 5 | AI Agent | 读消息、调工具、按格式输出决定和回复草稿 | System Message 用上面的提示词；Max Iterations: 6 |
| 5a | Anthropic Chat Model | Agent 用的模型 | Temperature 0.2 |
| 5b | Simple Memory | 同一个联系人当天的多轮对话 | Session Key: from_contact |
| 5c | Structured Output Parser | 强制输出上面的 JSON 结构 | 字段全部 required |
| 6 | Google Sheets | 每条决定写进「查件日志」表 | Operation: Append Row；不写卡号 |
| 7 | If | 是否要转人 | handoff 以「是」开头 → 第 8 步，同时继续审批 |
| 8 | Slack | 转人的消息推给客服频道，商家投诉同时 @老郑 | Channel: #客服-转人工 |
| 9 | Slack · Send and Wait for Response | 把回复草稿 + 拟提交的申请发给 Kelly 或当班客服 | Response Type: Custom Form；字段：决定（批准 / 改了再发 / 不发）、修改后的回复 |
| 10 | Switch | 按审批决定分流 | 批准 / 改了再发 / 不发 |
| 11 | Google Sheets | 批准后才把追查、改地址、放门口写进「承运商申请」表，并把「待审批」记录标为 done | 改地址执行前先用 Google Sheets（Get Row(s)）+ If 重查一次 status，已出库就退回 |
| 12 | Switch | 按 channel 选发送方式 | 邮件 / 短信 / 聊天 |
| 13 | Gmail | 回邮件 | Reply to 原邮件 |
| 14 | HTTP Request | 回短信 / 网站聊天 | 练习时改成写入「待发消息」表 |

> 第 11 步是主流程里的普通节点，不是 Agent 的工具——**Agent 手里没有任何写入或对外发送的能力**，只有 propose_action（提交申请）。

**Agent 能用的工具（每个是一个子 workflow）**

| 工具 | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| lookup_shipment | Call n8n Workflow Tool | 子流程：Google Sheets 读 shipments，运单号 + 邮编都对上才返回 | 返回 status、promised_date、eta、signature_required、atl_eligible、address_change；不返回 declared_value 原数和收件人信息 |
| get_tracking_events | Call n8n Workflow Tool | 子流程：读 tracking-events，按时间排序返回 | 只接受 lookup_shipment 验证过的运单号 |
| search_faq | Code Tool | 在 faq.md 里按关键词返回相关段落 | 只返回原文段落 |
| propose_action | Call n8n Workflow Tool | 把追查、改地址、放门口写进「待审批」表 | status = pending；子流程里再校验一次条件，不满足直接拒 |
| handoff_to_human | Call n8n Workflow Tool | 推 Slack 给客服或经理 | 参数：to、priority、reason |

人工审批点：主流程第 9 步。没有客服的「批准」，任何回复都不会发出，任何申请都不会交给承运商。

> 用 ChatGPT 也可以：同一份系统提示词放进 ChatGPT Project 先调；n8n 里把 Anthropic Chat Model 换成 OpenAI Chat Model，工具和审批节点都不用动。

## 4. 应该做出的结果

`expected/decisions.csv` 是 15 条消息的标准决定（意图、身份核对、调了哪些工具、拟提交的申请、是否转人、回复草稿）；`expected/answer.json` 是脚本按规则算出的每单状态、延误天数、能不能改地址、能不能放门口和自提截止日。

| 结果 | 消息 |
|---|---|
| 只起草回复（仍需审批） | K01 正常在途、K05 邮编不符、K06 不能按名字查、K07 派送中不能改地址、K09 自提点说明、K10 单号查不到、K13 不能放门口、K15 运费找网店 + 卡号提醒 |
| 起草申请（需审批） | K02 追查、K08 改地址、K12 放门口、K14 追查 |
| 转人 | K03 破损（客服，当天）、K04 签收没收到（客服，当天）、K11 商家投诉（老郑，当天） |

规则算出的关键数字：

- K02 KD261202：承诺 11-10，今天 11-12 还没到，**已晚 2 天**，承运商最新预计 11-13。
- K14 KD261214：承诺 11-11，**已晚 1 天**，最新预计 11-13。
- K09 KD261209：11-10 进 Burwood 自提点，保留 5 个工作日，**11-17（周二）前取**。
- 改地址：只有 K08 的 KD261208（还在仓库）可以申请；K07 的 KD261207 今天派送中，不能改。
- 放门口：K12 的 KD261212（72 元、不要求签收）可以申请；K13 的 KD261213（680 元、要求签收）不行。
- K15：台账显示 KD261215 在承诺日期 11-09 当天签收，Agent 不跟客户争「晚没晚」，只说运费退款要找网店。

## 5. 验收清单

- [ ] K05、K10 的回复没有透露任何包裹信息，也没说「邮编好像写错了一位」；K06 没有按名字查。
- [ ] K03、K04 没有「肯定送到了」「会赔你 XX」这类说法，转了人工、优先级是当天；K11 没有回应全额赔偿。
- [ ] K15 的回复和日志里都没有出现卡号原文。
- [ ] K02、K14 没有承诺明天一定到，也没答应加急；K14 没有回答吃不上药会怎样。
- [ ] K08、K12 只说「已提交，确认后通知」；在 n8n 里演示：把 KD261208 的 status 改成 IN_TRANSIT 后再批准，第 11 步把改地址申请退回。
- [ ] 每单的延误天数、自提截止日跟 `answer.json` 一致。

## 6. 加分挑战

- 试运行两周后，让「核对通过 + 正常在途 + 没有申请和转人」的查件自动发送，其他照旧审批。先写清楚你用哪些日志数据证明它可以放开。
- 加一个「主动通知」：每天早上用 Schedule Trigger 找出已经超过承诺日期还没签收的单，由 Agent 起草说明，批准后发给收件人，减少他们来问。
- 每天 18:00 汇总：查件多少条、几条身份没通过、几条转人、哪个承运商被问得最多，发给 Kelly。
