# P40 · 通用：报销单收集 → 规则核对 → 财务审批

| 行业 | 难度 | 时长 | 工具 |
|---|---|---|---|
| 通用 | L2 Workflow | 150 分钟 | Claude + n8n + n8n Form + Google Sheets + Slack + Gmail |

## 1. 客户场景

北桥 IT 服务是墨尔本 Richmond 一家十个人的 IT 外包公司，顾问常年跑客户现场：打车、停车、在外地吃饭、自驾去 Geelong。报销现在是这样的：员工把收据拍照发微信给财务 Lily，Lily 每两周对一次，一张张核对金额、收据、有没有超标，再截图发给交付经理陈刚批，陈刚批完她再手动付款。Lily 说最累的不是付款，是挑毛病：同一张收据被交了两次她没发现过；有人三个月前的停车费现在才报；晚饭 86 块超了上限，她不好意思退，就全报了。老板周海自己的报销，以前也是他自己点的批准。

公司想要的是：**员工在一个表单里交报销，系统按公司规则先核一遍，合规的按金额自动找对的人在 Slack 里批，有问题的直接退回并说清原因，全部批完才进 Lily 的付款清单。**

## 2. 练习数据

| 文件 | 内容 |
|---|---|
| `data/claims-2026-11-12.csv` | 这一批 23 条报销（2026-11-12 汇总） |
| `data/employees.csv` | 10 位员工：employee_id, name, title, manager_id, email |
| `data/expense-policy.md` | 公司的报销规则：提交时限、收据、GST、各类上限、审批路线 |

全部是练习数据，公司、员工、商户、收据号都是为这个练习设计的，邮箱是 `.example` 域名。

`claims-2026-11-12.csv` 的字段：

| 字段 | 含义 |
|---|---|
| claim_id / employee_id | 报销编号 / 员工编号 |
| submitted_at / expense_date | 提交日期 / 费用发生日期 |
| category | 交通 / 出差餐 / 客户招待 / 办公用品 / 自驾里程 / 培训 |
| merchant / description | 商户 / 说明 |
| amount_incl_gst / gst | 含 GST 金额 / 其中的 GST |
| receipt_no / receipt_attached | 收据号 / 是否附了收据（yes / no） |
| attendees / km / po_number | 客户招待的人员、自驾公里数、预先批准的 PO 号 |

数据里**故意藏了 5 处问题**：

1. 同一张收据交了两次（同一员工、同一收据号、同一金额）；
2. 出差晚餐 86.40，超过每天 60 的上限；
3. 96.30 的网约车没有收据；
4. 8 月的停车费 11 月才交，超过 60 天；
5. 一张 44.00 的发票，GST 写了 6.00，比 44 ÷ 11 还多。

另外两条是审批路线的考点：一条 890 的培训要两级批；CEO 周海自己的客户招待，要由合伙人 Rachel 批，不能自己批。

教学假设：收据门槛 82.50、自驾每公里 0.88、GST = 含税金额 ÷ 11，这几个数只用于练习；真实规则以 ATO 官方说明和公司会计的意见为准。

## 3. 做法

**核对规则**（按顺序，命中一条就停）：

1. 同一员工 + 同一收据号 + 同一金额已经出现过 → 拒绝（重复），写明和哪条重复；
2. 提交日期 − 费用日期 > 60 天 → 转财务 Lily 判断是否特批；
3. 金额 > 82.50 且没有收据（自驾里程除外）→ 退回补材料；
4. GST > 金额 ÷ 11 + 0.01 → 退回补材料；
5. 办公用品 > 200 且没有 PO 号 → 退回补材料；
6. 其余通过：出差餐超过 60 的按 60 报（部分通过）；客户招待按每人 120 核上限；自驾 = 公里数 × 0.88；
7. 审批路线：直属主管；批准金额 > 500 再加 CEO 周海；CEO 自己的报销由 Rachel Tan 批。

**第一步：在 Claude 里把规则跑通。** 新建 Project「北桥 报销核对」，上传三个文件，说明里写：

```
你是北桥 IT 服务的报销核对助手。按 expense-policy.md 逐条核对 claims 里的每一条报销，
按上面 1–7 的顺序判断，命中一条就停，不要跳步。
每条输出：claim_id, employee, category, amount, approved_amount, decision, route, reason。
decision 只能是：通过，待审批 / 部分通过（超额自付） / 退回补材料 / 拒绝（重复） / 转财务判断。
reason 写给员工本人看，一句话说清哪条规则、差在哪个数字。
最后按审批人汇总：每人要批几条、合计多少。
你只做核对和起草，不批准、不付款、不替任何人决定特批。
```

拿结果跟第 4 节对。对不上先改规则，规则对了再进 n8n。

**第二步：建 Google Sheets。** 三张表：`claims`（表单写入）、`employees`、`payout_queue`（批完待付款）。

**第三步：按下面的节点搭 n8n。** 核对规则全部写在 Code 节点里，可复查、每次结果一样；Claude 只负责把退回原因写成好读的话。

### n8n 搭建

| # | 节点 | 做什么 | 关键设置 |
|---|---|---|---|
| 1 | n8n Form（Form Trigger） | 员工交报销 | 字段跟 claims 表一致；收据用文件上传字段；类别用下拉 |
| 2 | Google Drive | 收据文件存到「报销收据 / 2026-11」文件夹 | 文件名 = claim_id；表里只存链接 |
| 3 | Google Sheets（写 claims） | 新报销追加一行，状态 submitted | Operation: Append Row |
| 4 | Schedule Trigger | 每周四 16:00 批量核对 | 时区 Australia/Melbourne |
| 5 | Google Sheets（读 claims + employees） | 读本批 submitted 的行和员工表 | Operation: Get Row(s)；Filter: status = submitted |
| 6 | Code（核对规则） | 按 1–7 逐条判断，输出 decision / approved_amount / route / reason | Run Once for All Items；重复判断要看整批和历史已付记录 |
| 7 | Switch | 按 decision 分流 | 通过 / 部分通过 → 审批；退回 / 拒绝 → 通知员工；转财务 → Lily |
| 8 | Basic LLM Chain + Anthropic Chat Model | 把退回、拒绝的原因写成给员工的一段话 | 只改写 reason，不改数字、不加规则里没有的要求 |
| 9 | Gmail | 给员工发退回 / 拒绝通知 | To: 员工邮箱；状态改 returned / rejected |
| 10 | Aggregate | 按 route 把待批报销合成一条消息 | Group by route |
| 11 | Slack · Send and Wait for Response（第一级） | 发给主管（或 Rachel）：清单、金额、部分通过的说明 | Response Type: Approval；超时 3 天提醒一次 |
| 12 | If（是否需要第二级） | route 里带「→ 周海」的再走一级 | 条件：approved_amount > 500 且申请人不是 CEO |
| 13 | Slack · Send and Wait for Response（CEO） | 周海批超过 500 的 | Response Type: Approval |
| 14 | Slack · Send and Wait for Response（财务特批） | 超过 60 天的发给 Lily 判断 | Response Type: Custom Form；字段：特批 / 不批、备注 |
| 15 | Google Sheets（写 payout_queue） | 全部批准的才进付款清单 | 记 claim_id、金额、谁批的、几点批的 |
| 16 | Gmail | 每周五把付款清单发给 Lily | Lily 在会计软件里手动付款，流程不碰银行 |

人工审批点：第 11、13、14 步。没人点批准，报销不会进付款清单；流程本身不付任何钱。审批人等于申请人时，Code 节点必须改派（CEO → Rachel），不能出现自己批自己。

> 用 ChatGPT 也可以：第一步用 ChatGPT Project 跑同样的规则；n8n 里把 Anthropic Chat Model 换成 OpenAI Chat Model，其他节点不变。

## 6. 加分挑战

- 用 Information Extractor 读收据照片的文字说明，自动填商户、日期、金额、GST，再和员工填的比，不一致的标出来让人看。
- 每月给周海一份汇总：按类别和员工看花了多少、拦下了几条、平均审批用了几天。
- 加一条规则：客户招待要写清客户公司，没写的退回；想一想这条用 Code 判断还是要让人看。

## 7. 简历 / 面试可以这样讲

> 为一家十人 IT 外包公司搭建报销审批流程：员工用 n8n 表单提交，收据存 Google Drive；Code 节点按公司规则核对重复收据、提交时限、收据门槛、GST 和各类上限，超额餐费按上限部分通过；合规报销按金额和申请人自动路由到主管、CEO 或合伙人在 Slack 审批，杜绝自己批自己，全部批完才进入财务付款清单，流程本身不触碰付款（教学项目，公司和报销数据都是为练习设计的）。
